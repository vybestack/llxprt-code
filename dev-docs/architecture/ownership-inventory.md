## Shared verification rules

From report section 8, lines 13-15:

All scenarios are Bun behavior tests following the repository's test rules. Three principles keep the tests from proving the wrong thing. First, real objects under test: the scenarios use real reducers, controllers, and agents, and substitute fakes only at external boundaries, meaning filesystem, network, and credential infrastructure. The transaction scenarios do not mock the controller to prove controller transactions, and the isolation scenarios do not mock Agent to prove Agent isolation. Second, observables are captured effects: outgoing provider requests, filesystem mutations, emitted events, and retained handles are recorded and asserted, rather than asserting that a method was called. Third, production configuration: tests run without harness gates, so behavior that holds only when test-oriented defaults are disabled cannot pass, addressing the `process.cwd` and forced confirmation defaults recorded at report HEAD `packages/agents/src/api/createAgent.ts:449-465` (report evidence E12).

The existing suite stays as regression coverage and one part of it already sets the standard: the replaceable-client smoke test drives real public turns with a fake provider and asserts terminality and tool-result correlation, `packages/agents/src/api/__tests__/replaceableClient.smoke.behavior.test.ts:108-227`. What the existing suite does not establish is equally documented: the profile control tests exercise create, read, and delete within one agent and its fixtures, `packages/agents/src/api/__tests__/profiles.spec.ts:12-23`, and prove neither survival past disposal nor cross-client reload (report evidence E04/E12). Cross-client scenarios run the same script through the CLI, ACP, A2A, and SDK adapters against one agent contract, so protocol-specific status handling stays outside the loop under test.

From section 8's suite composition:

Scenario-to-slice gating follows the tables: S1 is gated by C and E; S2 by C; S3 by D; S4 by H; S5 by D and H across its transaction and repository halves; S6 by B and H; S7 by F and H; S8 by J and K, with K adding the A2A fault harness; S9 by E, F, and K across its session, workspace, and eviction scopes; S10 by M; S11 by L; and S12 by E, with S7 and S12 also release-gated at N. Slice A defines these scenarios and captures baseline behavior before implementation; slice N runs the entire suite plus the S7 secret-isolation cases and the S12 soak as release proof. S1 and S8 additionally run per client cutover, because a cutover that regresses its own client is a failed slice even when the shared core is correct.

Two composition rules prevent dilution. Scenario definitions live with the conformance contract from slice A, not inside individual slice PRs, so a slice cannot weaken a scenario to pass. And no partial result promotes: a fake-provider smoke pass or a packed MCP import, the two strongest existing proofs described by the report, each cover exactly their own scope and never stand in for the suite. The full verification cycle runs when code changes land; the report executed none of it, consistent with its read-only scope (report evidence E12/M01).

**Fixture-only profile semantics are current behavior, not the product contract.** Existing fixture tests are retained unchanged. Their names mentioning durable storage do not establish persistence after disposal or cross-client parity.

### Shared lifetime rules from report section 5

A workspace is shared between runtimes only through an explicit lease with declared trust and environment requirements; default construction favors separate runtime objects over implicit sharing. A session can contain a foreground agent and children while sharing only selected services: history stays agent-specific unless a deliberate conversation operation says otherwise, and approval routing carries agent and task identity.

Bootstrap order is declared rather than emergent: validate host input and trust; resolve declarative settings and profile; obtain owned service scopes; install extension, skill, LSP, and tool contributions; initiate MCP discovery under the workspace lifetime; publish the complete tool view; create the provider binding and loop; expose the ready Agent. Disposal runs the inverse with specified ordering: stop admissions, abort active requests and pending auth and approval waits, initiate MCP and trust cancellation, cancel and join child agents and task and shell work, settle recording, release scheduler and listener scopes, close provider bindings, release workspace leases, and close owned buses and host leases last. Borrowed resources are released, not destroyed. Cleanup aggregates failures and is idempotent under concurrent calls; the concrete ordering must be tested against the actual dependency graph rather than inferred by a generic topological container.

Current `AgentImpl.dispose` (`packages/agents/src/api/agentImpl.ts:1306-1428`) instead orchestrates SessionEnd, active-run abort, retained scheduler handles, subscriptions, runtime cleanup, owned Config, LSP, extensions, locks, session recording and OAuth cleanup. Config has its own teardown. This is source-only evidence of the current implementation; the target S9 cancellation/order matrix is not established by reading it.
