The requested canonical file, `dev-docs/workflow/ISSUE-DELIVERY.md`, is not
present on current `origin/main`. This plan applies the bounded issue-delivery

explicit non-goals, bounded vertical slices, expected paths, scope ledger; stop

## Problem and decision

Issue #2128 asks for first-class image generation/editing via the same
`gpt-image-2` backend and ChatGPT/Codex OAuth authentication the Codex CLI uses,
exposed through three entry points (a `generate_image` tool, an interactive
`/image` slash command, and non-interactive CLI flags), backed by a typed
backend-neutral image-generation service with the Codex OAuth adapter as the
first implementation.

The full surface is large and would blow the hard scope budget if delivered in
one PR. The issue itself scopes follow-up backends (OpenRouter/Nano Banana, LM
Studio, local models) to separate issues "built on the same service contract."
Applying the same bounded-slice discipline to the three entry points, this PR
delivers the **foundational vertical slice**: the backend-neutral image service
contract, the Codex OAuth adapter (generate only — edit is deferred), and the
single highest-leverage entry point, the model-callable `generate_image` tool.
The `/image` slash command, CLI flags, edit mode, and inline terminal rendering
are explicitly deferred to follow-up issues that build on the contract landed
here. This keeps the slice within the 25-file / 1,500-line target while
establishing the contract every later slice composes onto.

Decision: introduce a provider-independent image-generation application service
and backend contract in `packages/core`, implement a Codex OAuth adapter in
`packages/providers` that reuses the existing Codex auth (`fetchCodexUsage` is
the proven standalone-fetch precedent), and expose it through a new
`generate_image` tool in `packages/tools`. The active conversational
provider/model is never touched; image generation is a side-capability invoked
through its own tool.

## Verified Codex behavior (from issue)

- Model: `gpt-image-2`
- Generate: `POST https://chatgpt.com/backend-api/codex/images/generations`
- Edit: `POST https://chatgpt.com/backend-api/codex/images/edits` (DEFERRED)
- Auth: existing ChatGPT/Codex OAuth bearer token plus `ChatGPT-Account-ID`
- Extra context: `originator: codex_cli_rs`, optional session ID
- Generate defaults: `background: "auto"`, `quality: "auto"`, `size: "auto"`
- Response: `data[].b64_json`
- A ChatGPT/Codex subscription suffices; must NOT require `OPENAI_API_KEY`

## Architecture grounding (verified in codebase)

- Codex auth surface: `BaseProvider.getAuthToken()` (`packages/providers/src/BaseProvider.ts:344`, `protected`) and
  `OpenAIResponsesProviderBase.getCodexAccountId()` (`packages/providers/src/openai-responses/OpenAIResponsesProviderBase.ts:126`, `protected`).
  Both are already surfaced through `ResponsesExecutorDeps`
  (`OpenAIResponsesProviderCore.ts:42-43`) and through `runtimeNormalizer.ts`
  (`ProviderWithAuth.getAuthToken`, line 44/433).
- Standalone Codex fetch precedent: `fetchCodexUsage(accessToken, accountId, baseUrl?)`
  in `packages/providers/src/openai/codexUsageInfo.ts:129` — pure function,
  `fetch()` with `Authorization: Bearer`, `ChatGPT-Account-Id`, `AbortSignal.timeout(10_000)`.
  This is the exact pattern the Codex image adapter will mirror for the two
  image endpoints.
- `isCodexMode(baseURL)` = `baseURL?.includes('chatgpt.com/backend-api/codex')`
  (`OpenAIResponsesProviderBase.ts:97-99`).
- Tools: `BaseDeclarativeTool<TParams, TResult>` (`packages/tools/src/tools/tools.ts:419`),
  JSON-Schema `parameterSchema` (NOT Zod), registered via
  `registerCoreTool(ToolClass, ...args)` in
  `packages/core/src/config/toolRegistryFactory.ts:367+`. Result type `ToolResult`
  (`tools.ts:484`) carries `llmContent` (a `ContentPartListUnion` of blocks) and
  `returnDisplay`.
- `MediaBlock` (`packages/core/src/services/history/IContent.ts:204`):
  `{ type:'media', mimeType, data, encoding:'url'|'base64', caption?, filename? }`
  — the canonical representation for a returned image.
- Workspace path safety: `validatePathWithinWorkspace(roots, path)`
  (`packages/tools/src/utils/pathValidation.ts`, used by `write-file.ts:468`).
- Cancellation: tools receive `AbortSignal` in
  `ToolInvocation.execute(signal, ...)` (`tools.ts`); `AbortSignal.timeout(ms)`
  is the existing network pattern (`codexUsageInfo.ts`).
- Abort/error surfacing to model: `ToolResult.error: { message, type? }`
  (`tools.ts:484-511`).

## Non-goals (this slice)

- Do NOT implement the `/image` slash command. (Follow-up issue, builds on this
  contract.)
- Do NOT implement non-interactive CLI flags (`--image`, `--image-edit`). (Follow-up issue.)
- Do NOT implement edit mode (`/images/edits`, referenced input images, data-URL
  encoding of inputs, `num_last_images_to_include`). The issue lists edit as a
  distinct request shape; the contract will be shaped so edit can be added
  without rewriting the service, but only generate is implemented now.
- Do NOT implement inline terminal image rendering (Sixel/iTerm2/Kitty). The
  tool returns a saved file path the model/user can open; rendering is a
  separate UI concern.
- Do NOT add system-prompt instruction injection for the tool beyond what the
  tool's own `description` provides. (Codex's `ImageGenerationInstructions`
  fragment is a follow-up.)
- Do NOT add OpenRouter/Nano Banana, LM Studio, or local image backends. The
  issue explicitly scopes these to follow-up issues on the same contract.
- Do NOT change the active conversational provider/model, the model list, or the
  chat-completion pipeline. Image generation must not route an image model
  through chat completions (CodeRabbit's first, rejected proposal).
- Do NOT add a new dependency, workflow, agent-memory change, quality-tool
  change, lint suppression, or unrelated refactor/test move.
- Do NOT require `OPENAI_API_KEY`; a ChatGPT/Codex subscription must suffice.

### Backend resolution (no new public abstraction on the chat provider)

To avoid widening the public surface of the chat providers, the tool resolves
its image backend through a small `ImageBackendResolver` capability injected at
registration (mirroring how `keyStorage`/`settingsService` adapters are injected
for existing tools in `toolRegistryFactory.ts:400-407`). The resolver checks
whether the active runtime exposes Codex auth (`getAuthToken` + a Codex account
id) and returns the Codex adapter or `null`. This is an in-package composition
detail, not a new public API on `BaseProvider`.
