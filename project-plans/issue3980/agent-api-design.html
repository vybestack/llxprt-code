Agent API design

Issue #3980. Status: proposal for review, revised after one architecture review. Date: 2026-10-28.

This page designs the agent API on its own terms, without starting from today's llxprt code. The agent runs and controls the agent loop. It receives a closed, validated definition and a set of host ports, never a configuration object or a service locator. It reaches the outside world only through those ports. Interactive and headless hosts use the same agent; they differ only in how they answer decision requests. Adapting llxprt is later work, and section 17 only shows where today's pieces would land.

1. Principles

  1. The agent runs the loop. It decides when to call the model, which tool calls run, in what order and under which policy, when to retry or fall back, when to compact and when a turn ends. No host sequences any of these steps.
  2. No configuration object, no service locator. The precise rule: no host or application settings object, no getter bag, no provider registry and nothing that carries secrets enters the agent. The agent receives an AgentDefinition, a closed and validated value describing the agent's behavior, and an AgentHost, a fixed set of narrow ports. The definition has no paths, environment, credentials or objects with methods.
  3. Inversion of control. When the agent needs something from outside, it calls a port: model access, tool execution, a decision, storage, time, diagnostics. The host never reaches into the agent. It sends commands and reads events.
  4. Separation of concerns. The agent owns behavior and conversation state. The host owns presentation, input, configuration sources, credentials, workspace access, sandboxing and UI composition. The agent core has no filesystem, network, environment or process access.
  5. One way in, one way out. Changes go in through submit, steer, cancel and typed commands. State comes out through one ordered event stream, a snapshot that carries its stream cursor, and a transcript reader. There are no per-field getters.
  6. Interactive and headless are contracts. Every request for a person goes through one port. A headless port answers immediately and can say that no answer is possible. The agent never offers the model a tool that nobody could answer.
  7. Authority is separate from preference. Restrictions the host imposes (folder trust, organization rules) can never be overridden by approval modes, remembered approvals or a child's policy.
  8. The agent owns only what it creates. Ports are borrowed and the agent never closes them. Every port operation that can wait takes an abort signal, and honoring it is part of the port's contract.

2. Who owns what

The agent owns

  • The loop: steps, tool scheduling, retries, model fallback, limits, loop detection, ending a turn
  • Conversation history, checkpoints and their consistency (every tool call gets a result, including after a cancel or a crash)
  • Policy evaluation, grants from approvals, and the audit record of each decision
  • Plan mode, and the built-in tools that need a person (ask_user, propose_plan)
  • Context management: token accounting, transient context lifetimes, compaction
  • Steering, cancellation and the timing of every command
  • Subagents built from its own templates, and their lifetimes
  • The state machine, the event stream, and its own shutdown order

The host owns

  • Rendering, input, keybindings, dialogs, slash commands, themes and UI composition
  • Reading settings, profiles, argv and environment, and turning them into an AgentDefinition
  • Credentials and authentication flows, inside its model adapters
  • Workspace access, shells, sandboxes and MCP connections, inside its tool adapters
  • Trusted tool metadata: which effects and concurrency class each tool has
  • The authority layer of policy (trust, organization rules)
  • Fetching resources: files, MCP prompts and resources, IDE selections, memory files
  • Answering decision requests, with a person or a headless rule
  • Where sessions are stored and where diagnostics go; closing its ports

Never inside the agent

Settings and profile files, provider registries, OAuth and API keys, MCP clients, the filesystem, shell execution, sandboxing, terminal output, telemetry exporters and debug flags. Each one lives behind a port or never reaches the agent. When the agent needs a fact from one of them, it gets the fact as data in the definition, as content, or as a port's answer.

3. The shape

The host turns its configuration sources into a definition, builds the ports, and hands both to createAgent. After that it only sends inputs and reads output. The agent calls the host only through the ports it was given.

4. The API

Creation is asynchronous and complete

Creation validates the definition, resolves the primary model (so the context window is known), and, for resume or fork, loads and reconciles the session journal (section 13). An agent that exists is always ready. There is no half-built state.

The host: what the agent may call

The agent: one conversation

BusyError stays. One agent is one conversation, and the turn is reserved synchronously inside submit, so two calls in the same tick cannot both see idle. ClosedError takes precedence over BusyError. A host that wants to queue user input keeps its own queue; the host-kit provides one with cancellation.

Events: the only output

Stream rules. Sequences are per session and keep increasing across resume. events({ after }) is exclusive: it starts with the event after after. The agent retains a bounded replay window (the last N events or the current turn, whichever is larger). An after older than the window fails with CursorExpired, and the host re-reads snapshot(). Each subscriber has a bounded buffer. A subscriber that falls behind gets Lagging and must resubscribe from a fresh snapshot. The agent never blocks on a slow reader. Every turn-scoped event carries turn. After agent.closed, every iterator ends.

A UI does this once: read snapshot(), subscribe with after: snapshot.cursor, and fold events into its own store. Text and progress arrive as deltas, and state.changed arrives only on real state transitions, so it is cheap. The snapshot is an operational summary, not the conversation. Message content comes from the stream as it happens, or from transcript().

5. Content and context

  • Instructions are trusted system text. Context items are material the model should know about. Untrusted items (MCP resources, fetched pages, file contents) go to the model clearly framed as data, never as instructions.
  • IDE selections and diagnostics use until-replaced. Setting an item with the same id replaces the old one, so stale selections never pile up. next-turn items drop off after one turn.
  • The host fetches everything: MCP prompts become UserInput, MCP resources become resource parts, memory and skills become instruction blocks or context items. Memory writes are tools, so a write goes through policy.
  • The agent checks each part against ModelClient.info.modalities. A part the active model cannot take is rejected at submit with UnsupportedContent, never silently dropped.

6. The loop

One turn at a time. cancelling lasts until every started operation has settled; only then does the agent accept the next submit. close() is accepted from any state.

One turn, step by step

  1. Admit. submit reserves the turn, appends the user input, pins the turn's tool set (section 7) and emits turn.started.
  2. Prepare. Build the request from instructions, context items, history and tool schemas. If the estimate passes compactAtRatio, compact first. That is automatic compaction, and it happens only here, never during a model attempt or a tool segment.
  3. Reserve and call. Check limits before the call (section 11). Start a model attempt. Streamed text is provisional until model.response commits the attempt. A retryable error discards the attempt and either retries or falls back.
  4. Tool calls. Each proposed call is validated, intercepted, checked against policy and scheduled in segments (section 7).
  5. Boundary. Every step ends at a boundary, including the last one. At the boundary the agent appends results, applies queued commands of the boundary kind, applies queued steering, checks limits and loop detection, and records a checkpoint. If steering was applied, the loop continues even when the model gave no tool calls, so steering is never lost. Otherwise the turn ends when the model gave no tool calls.
  6. Cancel at any point: stop new dispatch, abort the turn signal, wait for every started operation to settle, then record results (section 7) and end with cancelled. Queued steering for the turn is dropped and reported in the result. Queued commands stay queued and apply at the next point where their kind applies.

7. Tools: trust, scheduling, output

Descriptors come from the host, not from the tool

  • Trust. P12/P13 populate required policyIdentity = {name, server?} from the registered builtin name or trusted MCP connection/server namespace and original source tool name, never qualified ToolId parsing or untrusted descriptions/arguments. Validate the closed identity shape, with nonempty name and optional string server, when pinning descriptors; core rejects a nonempty server whose name does not start with server + '__' before dispatch. An absent or empty server retains today's no-server-check behavior. Literal stars remain literal. A tool's effects and concurrency class come from the host adapter that wraps it, not from the tool's own description. The adapter for an MCP server assigns conservative defaults (execute, network, write, exclusive) unless the host's own settings for that server say otherwise. Tool ids are qualified by source, so two servers cannot impersonate each other or a built-in.
  • Policy is not a sandbox. Policy decides whether the agent asks the tool to act. The host's executor and sandbox enforce what the action can actually touch. A path rule is checked against the resolved real path that prepare returns, not against the text the model wrote.
  • Dispatch enforcement. A call naming a tool outside the pinned set gets an error result. Advertising only certain tools is not the enforcement mechanism; dispatch is.
  • Catalog changes. A new or updated tool appears from the next turn. A revocation (server disconnected, trust withdrawn) aborts ToolSet.revoked. Pending decisions for revoked tools resolve as rejected, running calls see their signal abort, and later calls get a revoked error result.

Scheduling within a step

Segment rule. The model's calls are taken in order and split into segments. Each run of consecutive parallel calls forms one segment, and each exclusive call is a segment by itself. Segments run strictly in order. Inside a parallel segment, each call goes through policy on its own. A call waiting on a decision holds up only the end of its segment, while the other calls in that segment run. A later segment never starts before the earlier one finishes. Example: [A exclusive, waiting on approval], [B parallel, C parallel], [D exclusive]. B and C wait for A's segment, and D waits for B and C. Exclusivity covers this agent and its children. Exclusion across separate agents uses resources lock keys, which the host's executor enforces.

Output size and streaming

Streamed output goes through a bounded writer, so a shell or MCP tool cannot fill memory before the agent sees it. The agent applies the per-call and per-step caps before anything reaches the model and records how much was truncated. Progress is for display only; it never becomes part of history.

8. Policy and decisions

Two kinds of policy, evaluated in a fixed order

Evaluation. Core alone evaluates policy. First validate the pinned descriptor's trusted policyIdentity, never infer it from ToolId or model arguments, and apply the non-bypassable destructive-command deny to the raw shell text. At one policy revision and approval-mode snapshot, evaluate independent authority and every source stack's effective restrictions and take the strictest result (deny before ask). Then rank independently editable preferences, source-stack preference copies and remembered approvals by descending priority and ascending insertion order, falling back only if none matches. Layer order supplies stable insertion order, not a priority override. New remembered approvals occupy priority 2.95 after pre-existing rules at that priority. The final result is the stricter of authority and preference. No priority, preset, redirection exemption or grant can override an applicable authority restriction. Shell traversal below is part of this same evaluator, not an executor check.

Priority and authority. The TOML loader uses tier + priority/1000, with integer priority 0..999: defaults 1.000..1.999, user 2.000..2.999, admin 3.000..3.999. Within an admin stack, a higher-priority allow or ask can precede a lower deny today. Preserve that exception by giving each derived admin restriction an unless list containing the complete match predicates of every earlier admin rule in sorted order, including modes. The trusted builder places these predicates and the full ordered admin ask/deny/allow source-rule copy in one PolicySourceStack. Combine all admin files sharing the priority domain into that stack so cross-file exceptions remain intact. Its preference copy ensures an admin ask is not accidentally strengthened by a lower user deny. An admin allow opens only its own authority domain; independent organization/trust restrictions still apply. This derived duplication is builder-owned and tested, not two handwritten policy sources.

Atomic source replacement. set-source-stacks({stacks}) replaces the source-stack collection at one policy application point and one policy revision. Definition and command validation verify that each pair contains the complete ranked source rules and exactly their derived restrictions/exception predicates; reject duplicate group IDs, mismatched pairs or invalid patterns before installing anything. Rule order is the original global insertion order, not field concatenation order. Missing groups or rules are removed from both copies together. The command preserves independent authority, independently editable preferences and approvalMode. set-authority changes only independent authority; set-preferences changes only independently editable layers plus approvalMode. Neither may edit a source-owned copy. Publish the entire replacement before rechecking grants or re-evaluating/settling pending decisions. No observer or dispatch sees a hybrid of old exceptions and new ranked source rules. Invalid replacement leaves the previous revision and pending decisions unchanged.

For example, admin allow 3.9 for a particular operation and deny 3.1 for its tool becomes a deny that excludes the operation, plus the original ranked allow/deny preferences. Admin ask 3.9 likewise masks the lower deny and still asks even under grants. Ordinary user/default tiers cannot outrank admin. Raw PolicyEngine rules have no enforced tier or provenance authority, so a caller-supplied allow at 4 can beat an admin-labelled deny at 3 today. The engine ignores the source label. Andrew chose Q4 Option A: independent authority cannot be overridden by any priority. That exact raw allow-4/admin-labelled deny-3 case changes from allow to deny; an independent ask remains ask. Retain both rules and diagnose the changed outcome with both rules' provenance and priorities. Identify authority from the trusted source owner, never from an arbitrary label. Within-admin exceptions remain as described above. P05a asserts the old and new outcomes separately; P16 identifies affected runtime inputs. This is an explicit behavior change, not parity.

Mode changes. Presets remain preferences, but PolicyDocument.approvalMode is also an input to every rule predicate, including restrictions and their exception predicates. set-preferences atomically updates layers and approvalMode. All inactive rules remain loaded and validated. At the section 10 policy application point, core applies the command, increments policy revision, rechecks grants against the now-active restrictions, and re-evaluates pending decisions. No evaluation combines old-mode authority with new-mode preferences, including across compound segments. Already dispatched effects settle under their prepared token; subsequent dispatch uses the new revision. No two-command authority/preset race is permitted.

Serialized matching. Core serializes final arguments using the existing stableStringify behavior: sorted object keys, stable array order and JSON escaping. The host translator emits strings, never RegExp objects. For the directory TOML loader, argsPattern replaces each literal .* in the pattern source with [^"]*; commandRegex produces "command":"(?:PATTERN) without that rewrite. Both run against the entire serialized argument object, not decoded argv or only the raw command. Preserve even anchor, alternation and escaping consequences. TOML commandPrefix uses JSON-escaped text plus its existing whitespace/quote/end boundary, expressed by serializedArgs. The single-file loader and dynamic rules have different transformations; the plan records them by provenance. New parsed-argv matchers remain available without being substituted for existing text regexes.

Native regex parity. Core compiles PolicyRegex with native JavaScript RegExp, using the same flavor and flags as today's policy engine. Native RegExp is pure computation and fits agent-core's import rule without a new dependency or host callback. Preserve d/g/i/m/s/u/v/y as supported by the runtime, reject duplicate/unknown flags and u+v, and start each test with lastIndex zero, as the existing fresh-RegExp behavior does. Existing stableStringify subjects, loader wrappers and source rewrites stay unchanged. Definition validation compiles all effective patterns, including inactive rules and exception predicates; invalid syntax/flags and source-validation errors fail before effects with sourceId/ruleIndex/field provenance.

Retain MAX_POLICY_REGEX_SOURCE_LENGTH = 1,024 UTF-16 units and the adjacent-quantifier heuristic exactly where each current path applies them. Directory argsPattern validates authored text, compiles it, validates native .source again, then rewrites dot-star and recompiles. Directory/utils commandRegex validates authored text before its grouped wrapper; directory/utils commandPrefix adds no length/heuristic check. The single-file loader first builds its ungrouped commandRegex wrapper or regex-escaped commandPrefix pattern, then validates that generated pattern and compiles; its argsPattern validates authored text once, without the directory rewrite or second source check. Direct/dynamic regexes and dynamic prefixes only compile, with no added length/heuristic check. A direct utils argsPattern validates its supplied native source before rewriting, without a loader-authored check. PolicyRegex.input retains the selected expanded input and path, plus flags for native-source inputs. The shared pure normalizer reproduces these stages and produces effective source/flags; definition and command validation rerun them and reject an effective-pattern mismatch. No caller-provided list of checks can omit a required stage. Empty optional scalar TOML fields produce no matcher as today; preserve array expansion, including empty array elements, exactly as each loader does before per-pattern normalization. Test a 1,024-unit commandRegex rejected by the single-file generated-pattern check (1,035 units), but accepted on the directory path, and 513 forward slashes accepted at the authored argsPattern check but rejected at the directory native-source check (1,026 units). There is no universal pre-wrapper cap, new subject limit or new cap on paths that currently have none. See packages/policy/src/utils.ts:15,62-77, toml-loader.ts:284,584 and policy-engine.ts:19. Catastrophic backtracking behaves as today, including possible delay of cancellation; the source cap and heuristic do not bound runtime. Resource-safe regex evaluation is a possible follow-up issue, outside this plan. No custom interpreter or step budget is included.

Shell traversal and exemptions. Preserve the actual policy-engine branches: a matching deny or ask returns directly; a matching allow evaluates every split subcommand (deny beats ask beats allow), or for a single command asks on redirection unless that winning allow has allowRedirection true. The outer allow's exemption does not transfer to a segment with a different winner. With no match, a non-deny fallback checks compound subcommands and retains an ask fallback even if all segments allow. A single-command fallback allow has no redirection floor today. A matched allow whose nonempty command splits to zero segments asks; do not describe this lightweight splitter as a full shell parser. Pipes are segments, not redirections. Preserve all other arguments when substituting segment command text. Andrew chose Q5 Option A: keep the initial matched whole-command ask, then after approval and before dispatch evaluate every segment under one mode and policy revision. Any segment deny prevents the whole prepared call from dispatching, including echo ok && restricted-cmd. Approval satisfies only asks for that exact prepared compound call, not denied segments or other calls. If the preparation, mode or policy revision changes while waiting, invalidate that approval and re-evaluate the whole call and every segment together before dispatch. This explicitly strengthens post-approval behavior while preserving the initial ask. Grants cover every segment on an allow path and cannot bypass destructive deny or effective authority. Specific human approval can satisfy an ask; it does not install an exemption for unrelated calls.

Grants: what an approval remembers

Approving once binds to the PreparedToken, so it covers exactly the validated final arguments. Wider grants come only from scopes the agent offered in the request and the person chose. When a person edits the arguments, the agent prepares the edited call again and evaluates policy again. If the outcome is allow, it runs. If it is deny, it is rejected. If it is ask, the person's approval of their own edit counts as the decision for that one prepared call, so there is no approval loop. A stale outcome at execution makes the agent prepare again and ask again with the new preview.

Decisions: one port, typed per request

The built-in interaction tools belong to the agent, so every question to a person goes through the agent's pending-decision state and audit record. A host tool cannot close over the decision port, because the port is never given to tools.

Plan mode is agent behavior

  • command({ type: 'set-mode', mode: 'plan' }) enters plan mode. While in it, the agent adds an authority rule that denies write, execute and spawn effects, and offers propose_plan.
  • propose_plan creates a plan decision. Approve leaves plan mode at the boundary and continues the turn in normal mode with the plan as a context item. Revise returns the feedback to the model. Reject ends the turn.
  • When headless, propose_plan is not offered and set-mode to plan is rejected. A headless host that wants a plan asks for one in the prompt and reads the final text.

10. Mailbox and command timing


The agent is an actor with one mailbox. Admission is synchronous: submit, steer, cancel, command and close each decide on the spot whether they are accepted, and that moment is the linearization point. Accepted work is then applied at a defined point. The mailbox never waits on a port. While the loop awaits a model, a tool or a decision, the mailbox still accepts cancel, close, steer and commands, and queues each until its application point. Automatic compaction cannot overlap a model attempt or a tool segment, history cannot change during a model call, and no command can land halfway through shutdown.

11. Models, limits and budgets



    
  
  • Attempts. Each model call is an attempt with an id. Text and thinking deltas are provisional. model.response commits the attempt, and only committed tool calls are scheduled. A retry or fallback after partial output emits model.attempt.discarded first, so a UI drops those deltas and nothing appears twice.
    • 
  
  • Fallback belongs to the agent. On a listed error kind, the agent moves to the next choice whose ModelClient.info supports what the turn needs (tools, the modalities in use, the context size). The adapter stays responsible for credentials and transport. Quota and rate limits are typed errors carrying retryAfterMs, and the agent decides whether to wait, fall back or stop.
    • 
  
  • Budgets. Before each model call and each child start, the agent reserves an upper bound against the turn budget: the input estimate, plus the output cap (parameters.maxOutputTokens, or info.maxOutputTokens when unset), plus the reasoning cap (reasoning.budgetTokens, or the output cap when unset). The cost reservation is price() of that bound, and a cost budget on a model whose adapter has no price is rejected at creation. Unused reservation is returned afterwards. Parallel children reserve from the same budget, so reservations alone can never exceed it. Budgets are soft by at most one attempt: if a provider reports more than was reserved, the overshoot is recorded, and the turn ends at the next check with outcome limit. Retries, failed attempts and compaction count against the budget.
    • 
  
  • Loop detection. The same tool with the same arguments more than maxIdenticalCalls times in a turn, or maxStepsWithoutProgress steps in a row whose results are all errors or repeats, ends the turn with outcome limit and reason loop.

12. Shutdown


close() is idempotent, and it uses two scopes: work is cancelled, and finalization runs under its own signal with a deadline (close({ finalizeTimeoutMs }), default 10 seconds).


    
  
  1. Stop admission. Inputs now throw ClosedError, and queued commands are rejected with reason closing. Status becomes closing.
    2. 
  
  2. Cancel work. The running turn is cancelled as in section 6, pending decisions resolve with by: 'cancelled', and children are closed.
    3. 
  
  3. Wait for started work. Every started port operation (model attempts, tool executions, interceptors, children) settles. Each one's signal is already aborted, so a port that honors the contract settles promptly.
    4. 
  
  4. Finalize under the finalization signal: record results for calls that have none, write the closing records, and wait for SessionStore.append to resolve, which means the records are durable. Unsubscribe from the catalog.
    5. 
  
  5. Report. Emit turn.completed for a cancelled turn, then state.changed with status closed, then agent.closed. Every iterator then ends, and close() resolves with a CloseReport listing what was cancelled, which port operations failed, and whether finalization finished within its deadline. A failure in one step is recorded, and later steps still run.
    6. 



The agent closes no port. The host closes adapters, MCP connections and stores after close() resolves, because only the host knows whether another agent still uses them.




13. Sessions, recovery, rewind, fork



    
  
  • The journal is the source of truth. The agent writes a record before each externally visible step. tool-started is written before execute() is called.
    • 
  
  • Recovery (createAgent(..., { resume })) replays the journal and reconciles anything left open:
    
      
      
    • A turn without turn-ended is closed as cancelled with reason closing.
      • 
      
    • A tool-started without tool-finished becomes indeterminate. The model is told the call may have acted, and it is never re-run automatically.
      • 
      
    • A pending decision is not reissued as-is. The turn it belonged to was closed, so the person sees what was pending in the transcript and can submit again, and the fresh turn evaluates policy against the current tools and authority.
      • 
      
    • Session grants are restored only if the current authority still permits them. Turn grants are dropped.
      • 
    
    
  
    • 
  
  • Checkpoints. Every boundary and every turn end records a CheckpointId. Checkpoints sit only where every tool call has its result, so rewinding never leaves a call without one. transcript() exposes them.
    • 
  
  • Rewind moves the head back to a checkpoint, and later entries are kept in the journal as an abandoned branch. If the target is inside a compacted range, the rewind is rejected, and fork is the way to go back further. Rewind does not undo changes in the workspace; the host's checkpointing tools do that.
    • 
  
  • Fork (createAgent(..., { fork: { from, at } })) starts a new session that copies the journal up to a checkpoint. The source session is untouched.
    • 





Explicit old-session import, approved for 0.12.0. Run llxprt sessions import <old-file> while the source is offline. This host-only subcommand validates the old recording, writes a new journal/session atomically, prints its new ID and leaves the source bytes untouched. It performs no model, tool, hook or network work. It imports only proven content, drops old grants, labels unmatched calls indeterminate without inventing a durable start, and never repeats effects. Malformed histories fail without publishing a session. Compressed summaries stay summaries; missing history, signatures and identity scopes are never invented. Provider replay is active only when its payload and complete scope can be proven. Unscoped historical metadata stays in the imported-history audit blob, never a fabricated scoped replay envelope. Every host reports import-required for an explicitly requested old session, with this command in the message; no automatic legacy load or empty-session fallback remains. The offline reader handles all current event types explicitly, including audit-only refusal and history-replacing refusal_rewrite. Validate each rewrite payload and its resultingHistory before replacing active history, without invoking a reviewer, hook or model. Keep original/rewritten text and reviewer evidence in the audit blob, not appended model history. Fold replacements before checking active call/result uniqueness: a completed pair repeated from the replaced history is not a duplicate, but duplicate results within the replacement or later active tail remain errors. Reject malformed replacements before publication. P14 owns the importer, the complete event-type folding table and seven behavior fixtures.



14. Subagents


    
  
  • Templates. The definition lists subagent templates (name, instructions, tool ids, policy, limits). With any templates, the agent offers the built-in start_subagent tool with the spawn effect, and policy governs it like any other tool.
    • 
  
  • Children belong to the turn that started them. A child runs as a tool call. Several children in one parallel segment run at the same time, up to maxParallelChildren. The parent's turn cannot finish until every child it started has finished or been cancelled and has settled. Cancelling the parent cancels its children, and closing it closes them. There are no detached children. A host that wants background work creates a separate agent and manages it itself.
    • 
  
  • Narrowing is an intersection.
    
      
      
    • The child's tools are the template's tool ids intersected with the parent's pinned tool set.
      • 
      
    • For each call, the child's outcome is the stricter of the parent's outcome and the child's own, ordered deny, ask, allow. Strictness here means the full parent evaluation, with authority, grants and fallback, not just the parent's deny rules.
      • 
      
    • A parent that would ask makes the child ask, through the parent's decision port, with the child's id in the request.
      • 
      
    • Parent policy changes apply to running children at their next evaluation. A grant made inside a child stays in the child.

15. Port contracts and interceptors





ContractDetail


AbortEvery operation that can wait takes a signal and settles promptly after it aborts. Synchronous, non-blocking calls (emit, now, progress) take none. Conformance suites test this for each implementation.


Typed errorsPorts reject with the typed errors above. The agent turns them into outcomes: a model auth error with no fallback ends the turn as failed, reason auth. A tool error becomes a result the model sees. A store error during a turn ends it as failed and is reported in the close report.


No re-entryA port never calls the agent's public methods. Callbacks the agent passes in (progress, catalog onChange) are the only way back, and they only queue information.


CredentialsCredentials live inside model adapters. An auth failure is a ModelError. The host re-authenticates and the user submits again.





Interceptors: constrained hooks at fixed points



D20, approved Q1: retain model-changing hooks within agent ownership. The eight fixed points include BeforeToolSelection and AfterModel as well as the six delivered points. The host runs hooks and translates the existing v2 wire shapes; core applies the effective result, owns selection, attempts, budgets, history and policy, and never delegates the loop. HookEventResult separates that result from the ordered per-hook audit list. Audit every producer, including superseded mutations, informational messages and mutations preceding a final stop/block; never fold audit entries into effective request patches. Persist audit before publishing a result or dispatching effects, including when control stops the turn. Preserve context, tool patches, redaction, lifecycle hooks and observers. A patched tool call retains its attempt's tool restriction, is validated, prepared and evaluated against policy again; redaction retains raw output in an audit blob. afterTurn continuation remains bounded by the same turn.


Aggregation and propagation are distinct. Preserve hookPlanner order after matching/deduplication. Parallel is the default; Promise.all result order, not completion order, determines aggregation. Any matching sequential definition makes the whole event sequential. For BeforeModel and AfterModel, later present top-level fields replace earlier ones and hookSpecificOutput is shallow-merged: a later llm_request or llm_response replaces that entire nested object. Apply only the resulting request patch to the original request; only its settings shallow-merge with original settings. Thus contents from hook A followed by settings-only llm_request from hook B leaves original contents effective. Successful sequential BeforeModel output still updates the next hook's input through mergeHookLLMRequest, independently of final aggregation; sequential AfterModel hooks all see the original frame, not earlier replacements. Failed executions do not propagate inputs, but any output they produced still participates in aggregation. A final response replacement inherits omitted optional finish/raw-stop/usage fields from the source frame, not a superseded hook response. Preserve later allow/deny/continue fields exactly; resolve effective.control only after aggregation using the caller's existing direct or streamed semantics below. Do not collapse simultaneous wire stop/block into a shared stop-first result before that translation. Carry final-field provenance separately from the complete audit, including the producer of a synthetic response. Other events retain their existing event-specific merge rules.


Deadlines belong to individual hooks. For configured hook events, host-kit uses each hook's configured timeout or the existing default and completes sibling cleanup before returning the aggregate. Interceptors.deadlineMs is a single-hook/default deadline, not an outer race around a whole event. Do not impose a batch deadline that can erase completed results or truncate a valid sequential sequence; the turn deadline and cancellation still bound the whole operation. An individual timeout contributes no output, records a diagnostic and leaves completed sibling outputs intact; sequential execution proceeds to later hooks while the turn remains active. Spawn/process failures without output are nonblocking. Aggregate existing outputs even when success is false: exit 2 denies, including with empty stderr, using the runner's default reason; other nonzero exits retain their warning/no-output behavior. Invalid optional wire fields remain decoder no-ops, distinct from typed D20 invariant failures. On turn cancellation/deadline, stop admission, abort and join children, preserve completed audit under finalization, and settle cancelled/limit rather than successful continue. P03 owns this common model-interceptor execution seam; P17 owns subprocess deadlines and aggregation.


Preserve direct and streamed control behavior separately. DirectMessageProcessor._handleBeforeModelHook checks block/deny first, then synthetic response, then request-content changes; it does not check continue: false. A direct BeforeModel stop alone therefore still dispatches the provider with any applied content change; stop plus synthetic returns that synthetic output without dispatch or an AfterModel call. Block/deny, including stop plus block and a synthetic response, instead returns reason text with finishReason stop and rawStopReason, without dispatch. Direct _fireAfterModelAndApply/_applyAfterModelResult reads only getModifiedResponse: AfterModel stop, block/deny or both leave the original response when no replacement exists, or return the request-tool-filtered replacement when present. Those flags do not suppress content or otherwise eligible tool calls, and do not turn that response into a blocking outcome. Preserve these cases as P17 old/new parity, subject to the approved D20 selection, subset, accounting, replay and policy limits. Streamed BeforeModel and AfterModel retain stop-before-block after aggregation; controls prevent synthetic/replacement content and tool effects, BeforeModel prevents dispatch, and AfterModel retains original measured usage and audit. Streamed AfterModel block retains reason-text output and helper fallback 'Execution blocked by AfterModel hook'. Preserve getEffectiveReason: stopReason precedes reason, and an absent or empty selected reason becomes 'No reason provided'. An allowed synthetic response with no blocks retains effective-reason text; helper-only undefined uses 'Execution blocked', while an explicitly empty helper reason stays empty under the existing nullish rule. Preserve optional response metadata and systemMessage independently. Making the three direct controls behave like streamed controls is outside this implementation contract and would require separate approval.


Request changes last for one model call. BeforeModel may add, remove or rewrite request messages without editing committed history or the definition. A tool replacement selects unchanged descriptors from the pinned set and cannot restore tools excluded by BeforeToolSelection; widening or descriptor substitution fails with a typed HookError. A model override is resolved through the active definition's ModelSelection (primary or listed fallback), not passed directly to a provider. A model outside that selection fails with model-not-allowed and hook provenance before provider dispatch; it is not a retryable provider error or a reason to silently fall back. Core checks ModelClient.info against the final request, performs context preparation and budget reservation for the selected model, and uses the configured fallback order and fallbackOn rules. It does not change snapshot.model. Retries and fallbacks rebuild their own requests; no hook patch leaks into a later call. Journal every request/settings/tool/model change and its provenance before dispatch. Request-local edits also exclude D14 replay for changed parts and any entry-scoped replay whose entry changed, without erasing the original history.


Synthetic responses are attempts. BeforeModel may short-circuit provider dispatch. Record a model attempt with source hook and producing-hook provenance, a complete measured UsageReport containing zero for every counter, zero charge and no provider replay data. Do not price or reserve a fictitious provider call; release any unused provisional reservation. The attempt still consumes attempt/step limits and shares the turn deadline. Ignore hook-declared usage for measured accounting, retaining it as audit metadata. Emit hook-sourced attempt and response events, with zero tokens on the synthetic attempt event and complete zero measured usage on its response/accounting records. Validate its tool calls against the narrowed pinned set, prepare them and run normal policy/decision checks before effects. A synthetic response never grants permission.


Source frames and presentation deltas have different jobs. ModelResponseFrame carries the exact ordered source-block projection for one AfterModel invocation, including cumulative thinking snapshots and identical-text completion frames. HookResponsePart specifies append versus replace accumulation and retains stream ID/status. Its versioned, JSON-only hookFields preserves remaining hook-visible block fields, including signature, hidden/redacted/encrypted content and provider metadata; P11/P17 validate the format and map it losslessly without importing legacy types into core. These fields are hook visibility/audit data only, never replay authority, measured accounting or executable calls. Only separately validated D14 envelopes can enter provider replay. Do not reconstruct hook input from presentation deltas or the entire accumulated response. For source snapshots A, AB, completed AB, hooks see A, AB, AB with the exact status/fields, even though append presentation is A, B, then no new text.


AfterModel replacement is supported before commitment. Preserve per-source-chunk invocation and one direct-response invocation. Buffer provider presentation deltas until their frame; apply only the effective hook response and request-tool filter, then fold its parts once. The source frame is authoritative for this fold; never accumulate its content a second time from the deltas. Replace upserts the same thinking stream at its first position, as StreamOutputAccumulator does. A replacement lacking a stream ID uses the existing append behavior; an empty replacement removes this frame's contribution, not an earlier accepted snapshot. Derive visible events from the transformed accumulator: append deltas only for a true extension, otherwise emit model.part.replaced for the full revised provisional part. Identical-text completion updates fields without repeating text. Only finish commits the resulting model entry. For every changed, removed or replaced source part, drop its D14 replay envelopes; any entry-scoped envelope is dropped if that entry changed. Track invalidated targets through the attempt so replay arriving on a later completion cannot revive a changed part. Stable IDs alone do not prove unchanged content. Keep replay only for provably unchanged parts under the same scope, and never accept new provider replay supplied by a hook. Keep originals, projections and every hook output in audit blobs; with a store require blob support before admitting mutating hooks and durably store blobs before their references, publication or dispatch; without a store retain equivalent in-memory audit data. Commit transformed history and validate its tool calls against the originating request subset and policy. Provider usage is charged once from original reports even if hooks change content or declared usage. A later failed attempt discards both original and transformed provisional content, without discarding accounting or audit evidence.


Every call is bound to its originating request. Core freezes the final effective ToolId subset after BeforeToolSelection, BeforeModel and toolChoice, plus the existing stream-only scope-local emitter exception if already pinned. Preserve that binding across response replacement, argument edits, preparation and approval waits. Filter excluded provider calls/results before hook visibility, and filter synthetic/replacement calls/results again before visible publication, history commitment or scheduling. Filter as today: excluded blocks remain audit-only, with no active transcript call/result, tool lifecycle event, decision prompt or execution; retain a filtering diagnostic. Membership in the turn catalog or policy allow is insufficient. The scheduler checks the retained attempt subset again before dispatch, including after argument edits; no later catalog state or hook can restore an excluded tool. Unknown/unpinned calls retain normal invalid-call handling, never execution. Test the pinned stream emitter separately from ordinary restricted tools; an unpinned emitter is never introduced and direct mode has no exception.


Tool choice and settings. Existing toolChoice modes remain auto, required and none; none beats required beats auto, and supplied allowlists intersect with stable sorting and existing name normalization. Translate names to pinned ToolIds in host-kit and carry the result in ModelRequest.toolChoice, alongside the narrowed ModelRequest.tools. It does not fit ModelParameters.extra, which only accepts scalar values. None yields no tools. Preserve the streaming path's scope-local emitter exception only if that emitter was already pinned; it cannot widen the set. The current callers mostly consume none and allowedToolNames, without forwarding required as a provider constraint. D20 carries the declared mode explicitly rather than silently losing it. Existing settings shallow-merge for this call: temperature, topP, maxOutputTokens, responseJsonSchema and reasoning map to ModelParameters; settings.toolChoice maps to ModelRequest.toolChoice; systemInstruction maps to request-local instructions. Required provider system prompts remain in the system prompt. No settings field can bypass model selection, policy or budgets.


Keep llm_request_boundary semantics. The adapter preserves v2 indices over modified contents through an order-preserving message conversion, rather than guessing them from final text. Missing or explicit undefined is absent; present null, false, zero or an empty string is malformed. Unmodified projection uses the caller's pending suffix first, as boundaryRecovery.ts does. For modified contents, structurally valid metadata must have nonnegative integer indices and describe an exact suffix (start plus count equals length; omitted count means the rest). Invalid or malformed metadata obeys onInvalidBoundary: skip-compression by default or throw, with no differential fallback. Only absent metadata permits differential recovery from a pre-hook snapshot: preserve append/modified-pending recovery, duplicate ambiguity, pending-tail validation and the unrecoverable prepend case. Compression preserves the declared pending suffix verbatim but replaces its prefix with compressed real history. An unrecoverable boundary sends the changed request as-is under the context limit and fails clearly over it. Preserve the existing contents-less and empty replacement-array no-op guards in streamRequestHelpers.ts, and detect in-place changes on a detached hook view so they cannot mutate committed history. P17 runs the existing boundary and hook fixtures through both routes.

Decisions taken


D1. One agent is one conversation. Hosts with many sessions create many agents and share their ports.


D2. The agent is an actor with synchronous admission and a mailbox. Every input has one linearization point and one application point (section 10).


D3. No application configuration object and no service locator. A closed, validated definition describes behavior, and ports carry capabilities. Changing what the agent is means a command or a new agent.


D4. Creation is asynchronous and complete. An existing agent is always ready.


D5. Credentials never enter the agent. An auth failure is a typed model error.


D6. Authority is separate from preferences. Effective authority can only deny or ask, and always wins. D19 preserves authority-owned priority exceptions and ranks preferences and remembered approvals. Grants are scoped by what the person chose.


D7. Tool metadata used by policy comes from host adapters, and tool ids are qualified by source. Policy is not a sandbox.


D8. One path to a person. Request-specific responses, plus unavailable for headless failure. The interaction tools are agent built-ins.


D9. Children belong to the turn that started them, and their policy is the intersection with the parent's. There are no detached children.


D10. The journal is the source of truth. Recovery never re-runs a call that may have acted. Approved Q2 Option A adds an explicit offline import into a new journal, with the source untouched; no old runtime or automatic reader survives.


D11. Output is one event stream with a cursor, a snapshot and a transcript reader. Text is provisional until its attempt commits.


D12. Diagnostics are push-only. Debug filtering happens once, in the host's sink.


D13. Configuration loading lives in a shared host-kit, neither in the agent nor separately in each host.


D14. Port completion: provider replay belongs to core history. Replay chunks replace an envelope by id within the provisional attempt; tool-call part ids equal their call ids. Finish commits envelopes with the model entry, and SessionStore preserves them on resume and fork. Discard drops them. The adapter validates versioned payloads for signed thinking, encrypted reasoning, provider ids and Gemini AFC metadata. Core matches provider, model, endpoint and principal exactly; an envelope with a connection identity also requires that same connection. Durable envelopes omit connection identity. A model, endpoint, principal or connection change excludes incompatible envelopes without erasing the journal. Compaction never attaches old signatures to new text. D20 applies the same rule to hook edits: changed parts lose their replay, changed entries lose entry-scoped replay, and synthetic responses carry none. Original responses remain audit blobs, while replacement history contains only still-valid replay. No adapter owns a conversation cache, and replay metadata cannot execute tools.


D15. Port completion: usage is independent of successful completion. Usage reports are cumulative per attempt; later counters replace earlier counters, they are not added to them. Finish supplies its final accounting report, which may still be incomplete; a typed failure may also supply a final report without committing content. Incomplete final usage on a finished, sent or unknown request retains the larger of the reservation and reported usage, component by component, as an explicitly estimated budget charge. A proven not-sent request releases its unused reservation. Reported totals and budget charges stay distinct in attempt-budget records and accounting events; only reported totals enter Usage aggregates. A reservation is journaled before dispatch; recovery settles an unfinished reservation conservatively without resending. Complete reports release unused reservation, including on failure. Invalid or decreasing counters fail conformance, not silently reset.


D16. Port completion: recovery instructions do not issue requests. An adapter returns a scoped ModelRecovery value with the error and stops. Core journals it and discards provisional output. Dispatch authorization covers one attempt only; core retains validated reconstruction instructions for every remaining attempt of the same logical request and compatible scope, including ordinary retries after a repaired successor fails. Each later request is rebuilt from ModelRequest messages plus those instructions, without an adapter conversation/request cache or another repair cycle, with SDK retries disabled. Core clears retained reconstruction state when the logical request ends or the scope becomes incompatible; it cannot transfer to a fallback model. Before every stream call, core separately checks cancellation, retry kind, maxAttempts and budgets, admits the attempt and charges its usage once. Retained instructions grant no extra retry, and repeated repair of the same condition is rejected; reapplying retained instructions is not a new repair cycle. Image repair, rejected Responses parents and transport changes cannot conceal a second generation request; every stream call issues at most one generation. The invalidates list references entry/envelope ids from the request, so core records and applies invalidation without interpreting provider payloads; no retry runs automatically after restart.


D17. Port completion: afterTurn receives a read-only candidate view. The result, committed thinking-only status, settled tool outcomes and continuation ordinal let built-in continuation run without reading an Agent or reconstructing a host model loop. A continueWith response stays inside the current turn, shares its deadline and budgets, and precedes the single terminal turn.completed event. Failed, cancelled and limit outcomes cannot continue. User hooks may be disabled independently of the built-in continuation adapter.


D18. Port completion: shell preparation returns facts, never policy decisions. A host-trusted descriptor requires exact raw final command text, whole-command redirection facts, the current policy splitter's ordered text segments and per-segment redirection facts, plus parsed argv or an explicit parse failure. All are bound to the prepared token and recomputed after edits. Core creates serialized argument subjects and performs every permission decision. Keep policySplit distinct from richer argv parsing to preserve current quoting/separator behavior. Missing or inconsistent facts fail the port contract. D19 specifies exemptions and evaluation branches; no executor calls a second policy engine.


D19. Every existing policy form has a plain-data representation. Approved Q3 retains serialized argument/command regexes, priorities and tiers, stable ties, mode filters on both policy kinds, redirection exemptions, destructive deny and compound traversal. Section 8 defines PolicyRegex with replayable path/input evidence, provenance, priority/order, paired source stacks and authority-owned exception predicates, atomic source-stack and preset/mode changes, and native RegExp compilation with the existing path-specific validation stages and subject handling. Core remains the sole evaluator. Source translation preserves the actual directory-loader, single-file-loader and dynamic-rule transformations, not guessed equivalents. Invalid definitions fail before effects with provenance. Andrew chose Option A for Q4 and Q5. Independent authority wins over every preference/grant priority, with both rules' provenance in changed-outcome diagnostics. Preserve the initial whole-command ask, then check every segment after approval under the same mode/revision and deny the call if any segment denies. Approval covers only asks for that prepared compound call. P05a/P05b/P16 test these explicit changes separately from parity; no policy form is removed. Catastrophic backtracking remains as today and is only a possible follow-up issue. P01 is already delivered by merged PR #4076 (issue4039) with pre-D19 PolicyDocument, PolicyRule, PolicyMatch, ArgMatcher and PreparedShell. P01a amends those types plus required ToolDescriptor.policyIdentity, validation and fixtures before runtime work; P05a/P05b implement evaluation and decisions.


D20. Keep model-changing hooks with request-local authority. Approved Q1 extends section 15 with BeforeModel request changes and synthetic attempts, AfterModel replacement and BeforeToolSelection toolChoice. Requests may rewrite messages and narrow pinned tools, never widen them. Bind provider, synthetic and replacement calls to the final originating request subset through dispatch and edits, in addition to policy. Model changes pass through allowed selection, ModelClient.info, fallback and budget admission; disallowed models fail typed. Synthetic attempts have source hook, zero measured usage and no replay. Exact source frames preserve cumulative thinking and completion fields separately from presentation deltas; hook-only fields never authorize replay. Replacements retain original audit blobs, drop changed-part and changed-entry replay including late arrivals, and commit transformed history. Apply only the effective aggregate, preserving whole-object replacement and event-specific input propagation; journal every producer independently. Individual hook timeouts cannot erase sibling results, and turn cancellation cannot become continue. Preserve today's direct BeforeModel and AfterModel control behavior, existing streamed controls and empty-synthetic reason-text fallback as P17 parity; D20 does not approve changing the three direct controls. Keep v2 boundary/compression behavior and per-chunk cadence. P01a supplies types/fixtures; P03 owns model-interceptor execution and attempts/accounting; P07 owns journal records; P11 supplies source projections; P17 proves parity and stated changes, including issue1749.
