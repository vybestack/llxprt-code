# Issue #2511 — Restored sessions misattribute prior AI turns to the wrong model

## Summary of the defect (reproduced, not inferred)

Reproduced on `main` (commit `b378389ce`) with the tmux harness:

1. Start `bun scripts/start.ts` with **no** provider configured.
2. Run `/profile load zai` (provider `anthropic`, model `glm-5.2`, base URL
   `https://api.z.ai/api/anthropic`).
3. Ask for a haiku. The UI correctly shows `Responding with: zai:glm-5.2`.
4. Inspect the session recording JSONL for that run:

   - `session_start` → `provider: "unknown", model: ""`
   - `provider_switch` → `provider: "anthropic", model: "glm-5.2"`
   - the AI `content` event →
     `metadata: { model: "claude-opus-5", providerBaseURL: "https://api.z.ai/api/anthropic" }`

   The turn was generated by **glm-5.2** but persisted as **claude-opus-5**
   (the ambient pre-switch model). The reporter observed the same class of
   defect with `claude-opus-4-8`.

5. On `--continue`, `iContentToHistoryItems` faithfully renders the persisted
   `metadata.model`, so every restored turn is labelled with the wrong model.

### Root cause

`metadata.model` is stamped from an **immutable `AgentRuntimeState` snapshot**
rather than from the provider that actually served the request:

- `ChatSession` captures `const model = this.runtimeState.model` at construction
  and hands that string to `ConversationManager`
  (`packages/agents/src/core/chatSession.ts`).
- `ConversationManager` stamps every freshly generated AI turn with that
  constructor-time snapshot (`stampAiTurnModel(iContent, this.model, this.baseURL)`).
- `TurnProcessor` reads `this.runtimeContext.state.model` — the same snapshot.

The snapshot goes stale during a mid-session profile load:
`applyProfileWithGuards` calls `switchProviderForProfile(...)` (which rebuilds
the runtime state via `initializeContentGeneratorConfig`) **before** STEP 5
applies the profile's model. Nothing rebuilds the runtime state afterwards, so
`runtimeState.model` keeps the pre-switch model while the provider itself
resolves the new one. The base URL escapes the bug only because it is read from
the live ephemeral setting, which is already updated at rebuild time.

The live display path does not use the snapshot — `buildEffectiveModelIdentity`
(`packages/agents/src/core/modelInfoHelpers.ts`) reads
`provider.getCurrentModel()` — which is why the misattribution is invisible
until the session is restored.

### What is *not* broken (verified)

- Session recording persists `metadata.model` and replay restores it verbatim.
- `iContentToHistoryItems` uses `content.metadata?.model` only; it never
  substitutes a provider default for a historical turn.
- `importInitialHistory` / `setHistory` / `addHistory` still do not stamp
  restored turns. That behaviour must be preserved.
- Starting with `--profile-load zai` (profile applied before `Config`
  construction) stamps correctly; only the mid-session change path is affected.

## Accepted behaviour (acceptance criteria)

**AC1 — Live-authority stamping.** A freshly generated AI turn is stamped with
the model reported by the **active provider at record time**
(`RuntimeProvider.getCurrentModel()`), which is the same authority the routing
and the "Responding with:" indicator already use — not the ChatSession
construction-time `AgentRuntimeState.model` snapshot.

**AC2 — Mid-session model change regression.** When the runtime-state snapshot
still reports model `A` but the live active provider reports model `B`, a newly
recorded AI turn carries `metadata.model === 'B'`. This is the direct #2511
regression test.

**AC3 — Bounded fallback, no foreign default.** If the live provider cannot
report a model (accessor absent, throws, or returns a blank string), stamping
falls back to `AgentRuntimeState.model`. If that is also blank, **no**
`metadata.model` is written (the turn stays unattributed). No additional
`getDefaultModel()` fallback is introduced anywhere in the stamping path.

**AC4 — Load-balancer turns.** For a load-balancer provider the stamp is the
selected sub-profile's model (`LoadBalancingProvider.getCurrentModel()` already
returns it), not the load balancer's top-level default. This falls out of AC1
and is covered by composition, not a dedicated test: AC1 proves the stamp comes
from `getCurrentModel()`, and
`packages/providers/src/__tests__/LoadBalancingProvider.getCurrentModel.test.ts`
already proves `LoadBalancingProvider.getCurrentModel()` returns the selected
sub-profile's model (and `''` when the sub-profile is missing, which the
resolver's blank check in AC3 correctly falls through from).

**AC5 — Preserved invariants.**
- `stampAiTurnModel` remains idempotent: a turn that already carries
  `metadata.model` is never re-stamped.
- Non-`ai` turns are never stamped.
- `importInitialHistory`, `setHistory`, and `addHistory` still do **not** stamp
  restored/externally supplied turns.
- Restored AI turns with no persisted `metadata.model` render with no model
  label (neutral), never with the current provider's default.

## Out of scope (explicitly deferred)

- Refreshing `AgentRuntimeState` after profile application (the broader
  snapshot-staleness defect). To be raised as a separate issue.
- `metadata.providerBaseURL` staleness in `ConversationManager` (owned by the
  cross-endpoint thinking-block work, #1469 / #2335).
- Repairing already-recorded session files that carry a wrong or missing model.
- Restoring the recorded session's provider/model on `--continue`.
- The unrelated observation that `--continue` with no configured provider
  silently starts a fresh session.

`getCurrentModel()` disagrees with the runtime-state snapshot. The issue-#2511

Vitest, no `vi`) and is registered in `scripts/bun-test-manifest.ts`, which is
what the `bun_native_test_parity` CI job executes.

### Coverage that composes rather than duplicating

- **AC4** needs no dedicated test: test 1 proves the stamp is taken from
  `getCurrentModel()`, and
  `packages/providers/src/__tests__/LoadBalancingProvider.getCurrentModel.test.ts`
  already proves `LoadBalancingProvider.getCurrentModel()` returns the selected
  sub-profile's model. The two compose to AC4.
- **AC5 (non-stamping restore paths)** is guarded by the pre-existing
  `ConversationManager.modelStamp.test.ts` Vitest suite, whose
  `importInitialHistory` / `setHistory` / `addHistory` assertions must keep
  passing unchanged. That file carries no issue-#2511 case — only the mechanical
  `ConversationManager` constructor-argument update.

### RED proof

With the resolver forced to return `runtimeContext.state.model` unconditionally
(simulating the pre-fix snapshot behaviour), tests 1 and 4 fail at both stamping
sites; restoring the resolver turns them green.

## Verification evidence (tmux harness, real provider)

Scenario, reproduced via
`scripts/tmux-script.issue2511-model-attribution.llxprt.json`: start with no
provider configured, load the `zai` profile at runtime, generate a turn, quit,
then inspect the session recording.

| | recorded `metadata.model` | recorded `providerBaseURL` |
| --- | --- | --- |
| Before | `claude-opus-5` (WRONG) | `https://api.z.ai/api/anthropic` |
| After | `glm-5.2` (correct) | `https://api.z.ai/api/anthropic` |

Both runs generated the turn with `glm-5.2` and displayed `zai:glm-5.2` live.
A separate `--continue` run against a correctly-stamped recording renders the
restored turn as `glm-5.2`, confirming the display layer reproduces the
persisted per-turn value verbatim.

## Implementation sketch

- Add a single shared resolver used by both stamping sites, e.g.
  `resolveGeneratingModel(runtimeContext): string | undefined` in the agents
  core, implementing AC1 + AC3.
- `ChatSession` passes the resolver (not a captured string) to
  `ConversationManager`; `ConversationManager` calls it at record time in
  `_recordUserTurn` (AFC branch) and `_recordModelTurns`.
- `TurnProcessor._commitSendResult` uses the same resolver for `currentModel`.
- No lint/complexity rule may be relaxed and no suppression directive added.
