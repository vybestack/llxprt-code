# Issues #3953 and #3954: provider-switch default restoration, and model-change publication

Branch `issue3953`, based on `99554d4ebe`.

## Scope

Two defects found while configuring a Fireworks session, both rooted in the same
state-transition area.

1. **#3953 — cleared settings block target defaults.** After a provider switch, a
   setting that was cleared (written as `undefined`) is still treated as a
   surviving override, so the target provider's model defaults for that key are
   skipped. In the reported case, `reasoning.enabled` and `reasoning.effort` from
   the previous profile were cleared but Fireworks' `minimax-m3` defaults did not
   apply.
2. **#3954 — model change does not publish.** `/model <id>` updates the selected
   model and replaces the inference client but emits no core model event, so the
   footer keeps rendering the previous model. The example: profile `gpt-sol-high`,
   provider switched to Fireworks, then `/model accounts/fireworks/models/deepseek-v4p1-flash-1017`;
   the footer still shows `gpt-sol-high:fireworks/minimax-m3`.

Not in scope:

- #3952 (an incompatible nonempty `reasoning.effortWireFormat` preserved across a
  provider switch). That is a separate decision about whether to drop an
  incompatible selector during a switch; it is not a null-versus-missing bug.
- The stale profile prefix in the footer. Retaining `currentProfile` is deliberate
  session identity behavior under #2501, and existing tests require it. After the
  #3954 fix the footer shows `gpt-sol-high:<new model>`, which is correct under
  current semantics.
- Any change to the reasoning resolver's compatibility validation.

## Evidence

### #3953

- `packages/providers/src/runtime/provider-switch-defaults.ts:75-95` clears by
  writing `undefined`.
- `packages/settings/src/settings/SettingsService.ts:407-428` writes nested keys
  with `Object.defineProperty`, so the property remains enumerable after a clear.
- `packages/providers/src/runtime/provider-switch-execution.ts:195-208` builds
  `preAliasKeys` from `Object.keys`, using presence rather than value.
- `packages/providers/src/runtime/provider-switch-defaults.ts:174-177` filters
  model defaults by `!preAliasKeys.has(key)`.

So presence of an `undefined` value suppresses the incoming default.

### #3954

- `packages/cli/src/ui/commands/modelCommand.ts:130-144` dispatches.
- `packages/cli/src/runtime/session-model-command.ts:17-24` awaits `setModel`.
- `packages/agents/src/api/agentImpl.ts:717-728` writes the model, refreshes the
  client, restores chat visibility, rebuilds the loop, updates facade state, and
  publishes nothing.
- `packages/cli/src/ui/containers/AppContainer/hooks/useModelRuntimeSync.ts:128-153`
  refreshes only on core `ModelChanged`, `ModelProfileChanged`, `SettingsChanged`,
  or `LoadBalancerSelectionChanged`.
- `packages/cli/src/ui/utils/modelIdentity.ts:85-94` formats `<profile>:<model>`.
- `packages/core/src/session/session-settings-owner.ts:643-660` provides
  `beginModelPublication()`, already used by profile application and provider
  switching.
- `packages/agents/src/api/providerSwitchAssembly.ts:65-105` shows the established
  pattern: begin publication, perform the transition, commit, emit the profile
  event.

## Design

### 1. Survivor detection uses values (#3953)

`survivingSwitchParameterKeys` becomes a value-aware collector: a key survives
only when its captured value is not `undefined`. Nested `reasoning` children are
expanded the same way, so `reasoning: { effort: undefined }` contributes nothing
while `reasoning: { effort: 'high' }` contributes `reasoning.effort`.

This is a source fix, not a defensive guard: the function's contract is
"settings that will still be in force after the clear", and an undefined value is
not in force. No change to `SettingsService` pruning, no new fallback layers.

Preserved keys whose values remain defined continue to block model defaults
(existing tests for `preserveEphemerals` and user-owned overrides must stay green).
User-owned ownership marks are untouched.

### 2. Publish the model transition (#3954)

`Agent.setModel()` runs its transition through `applyModelWithPublication`, which
opens a `beginModelPublication()` window relative to the facade's applied model
(`this.providerState.model`), performs `setOwnerModel`, `refreshAuth`,
`restoreChatVisibility`, `rebuild`, records the new model on the facade, and only
then commits. A thrown step rolls back and propagates unchanged.

Comparing against the applied model rather than the current selection is what
makes a retry publish: `setOwnerModel` writes the selection before later steps can
fail, so after a failed attempt of model B, retrying B would otherwise look like a
no-op. A genuine no-op (setting the model already applied) still publishes nothing.

Publishing at this boundary (not inside `chooseModel`) keeps compound transitions
such as provider and profile application, which have their own publication
windows, from double-emitting.

`beginModelPublication` refuses to open a second window. Rather than rely on idle
assertions that do not cover concurrent mutations, `setModel` and `setProvider`
both run inside `AgentExecutionCoordinator.withIdleBoundary`, so real contention
fails fast with `AgentBusyError` before any mutation. That also means the plan's
earlier expectation that the pre-existing idle checks alone made collisions
unreachable was wrong; the shared boundary is the actual guarantee.

A failing `ModelChanged` subscriber does not undo or fail a completed transition.
`withModelPublication` catches commit-time notification errors and reports them
through the module logger.

The `agentImpl.ts` size cap forced a small extraction: `withModelPublication`,
`applyModelWithPublication`, and `ModelTransitionSteps` live in
`packages/agents/src/api/modelPublication.ts`, and the duplicated loop dependency
object in `prepareReplacement`/`rebuild` became a single `loopDeps()` accessor.

## Test-first plan

Write these first, confirm each fails for the intended reason, then implement.

### #3953 — `packages/providers/src/runtime/provider-switch-defaults.reasoning-keys.test.ts`

Use the real `SettingsService`, real `SessionSettingsOwner`, real alias config
fixtures, and the real `switchActiveProvider` path via the existing
`__tests__/provider-switch-inputs.ts` helpers. No network, no credentials.

1. Profile-style switch with `reasoning.enabled` and `reasoning.effort` set,
   moving to a provider whose model defaults define both: after the switch, both
   defaults are present. (This is the reported failure.)
2. Same switch where `reasoning.effort` is preserved via `preserveEphemerals`:
   the preserved value wins over the model default.
3. User-owned (not preserved) override for `reasoning.effort`: the explicit value
   wins, proving ownership semantics are intact.
4. Nested clear only: `reasoning: { effort: undefined, enabled: true }` yields
   `reasoning.enabled` as a survivor and `reasoning.effort` not a survivor.

### #3954 — `packages/agents/src/api/__tests__/model-publication.behavior.test.ts`

Use the existing agent fixture patterns in that directory (`fromConfig` with local
fake providers) and a real `coreEvents` subscription; never emit the event under
test manually.

1. With a profile loaded and a provider selected, `setModel` to a new model emits
   exactly one `ModelChanged` carrying that model, and `getModel()` and
   `getActiveProfileName()` agree with the emitted state (profile unchanged).
2. Two consecutive `setModel` calls emit two events, in order.
3. `setModel` with the current model emits nothing.
4. A busy run rejects the change, emits nothing, and keeps the previous model.
5. A transition step that fails after the selection was written emits nothing; a
   later successful retry emits exactly once, including a retry of the same
   target, and a no-op afterwards stays silent.
6. A throwing `ModelChanged` listener does not reject the completed change.
7. Contention: `setModel` while a provider switch is in flight, and `setProvider`
   while a model change is in flight, each reject with `AgentBusyError` before any
   mutation; awaited `provider`→`model` and `model`→`provider` sequences both
   succeed with one publication each.

### Command to footer — `packages/cli/src/ui/utils/modelIdentity.publication.test.ts`

Drive the real `modelCommand.action` through `createSessionModelCommand` with a
mounted `useModelRuntimeSync` hook, and assert the label the hook sets moves from
`<profile>:<old model>` to `<profile>:<new model>` with no manual event emission.
The test must fail if `Agent.setModel` stops publishing.

## Risks

- Over-broad survivor change could let model defaults clobber genuinely preserved
  settings. Tests 2 and 3 above are the guard.
- Publishing from `setModel` could double-emit during provider switches that apply
  a model afterwards. Mitigation: publish only in `Agent.setModel`, keep the
  existing provider-switch publication untouched, and keep the "publish only when
  the model changed" rule in `commit()`.
- A `beginModelPublication` collision would surface as a thrown error rather than
  a silent skip. That is intended fail-fast behavior; the idle assertions keep it
  from occurring in supported flows.
