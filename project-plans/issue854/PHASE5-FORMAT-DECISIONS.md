# Persisted plain-chat lengths: first production slice

Starting revision: `0d5223237c09f7f764537d27279183ccd781bde8`. This slice adds an opt-in native writer/fill/query path. Existing provider sends and the history-backend default are unchanged. Phase 5, W23, W26 and provider cutover are not complete.

## Settings and slot identity

There was no declared `RowFormatSettings` before this slice. The new core type records format ID/revision, exact model, endpoint, OAuth mode and enumerated tool-name transform, URL-image support, reasoning enablement/field name, PDF enablement, unsupported-media policy and output-limit configuration. Its entire recursively sorted JSON representation is hashed with SHA-256; the first eight digest bytes, little-endian, are the stored key. Nested output-limit fields participate. This is deterministic serialization, with no package dependency or function-valued key input.

The settings inventory follows the approved design's converter audit. Chat's existing conversion functions read the tool format and output-limit configuration; thinking presence is represented by two measured variants. Anthropic additionally reads OAuth tool-name handling, URL-image support, reasoning enablement, exact model and endpoint during projection/finish. Responses reads PDF enablement and output limits. Those other formats have no measurer in this slice. `reasoningFieldName` is conservatively keyed and the plain-chat admission accepts only the current output field, `reasoning_content`. Endpoint normalization remains the registration caller's responsibility; the key never merges distinct supplied endpoints. Sampling, prompts, tool definitions, reasoning inclusion/strip selection and request-only configuration do not enter the persisted base key.

`JournalSession.registerRowFormat` captures and freezes a settings copy before its first await. The callback receives that captured object explicitly, rather than depending on a closure over mutable request options. Returned plans also retain captured settings. The complete request configuration is not replaced by this object.

The writer assigns one of three persisted format slots. Matching keys reuse their generation; a new key evicts the least recently used eligible slot and increments its unsigned 32-bit generation, refusing overflow. Bounded `format:last-used:N` metadata records recency. Repeated registration of the already complete most-recent key attaches its callback without a new trailer or LENS write. Access to an older complete key updates recency without remeasurement. Mapping-only Mistral reservations are excluded from length-slot assignment. Conversely, mapping-only activation refuses an assigned format slot. This preserves old mapping-only behavior without giving one slot conflicting meanings; integrating a future Mistral length format with those mappings remains open.

Runtime callbacks are bounded to the three assigned keys and are installed only after a successful publication. They are not serialized. A reopened journal can query its stored summaries immediately, but every active key needed for a later content mutation needs its callback registered. An old restored key whose callback was evicted likewise needs registration before another measurement-bearing edit. Clones inherit the bounded callback registry. Pins retain their own roots and slot generations across later fills and eviction.

## Native writer and stored facts

A format edit passes through `JournalStore`'s commit queue. After normalization facts and the tentative row tree are built, the group measures missing contributions, writes LENS records, replaces entry summaries/stamps and publishes one trailer. No separately visible partial fill is published. Core defines the callback interface and never imports a provider.

The LENS kind header is 32 bytes: label at 0 (u64), slot at 8 (u32), base generation at 12, image generation at 16, format revision at 20, and key at 24 (u64). The body is versioned provider data. Plain chat stores two variants of numeric per-unit message lengths/drop flags and pending-media part lengths/video flags. It stores no message text or serialized request body. Each row entry points to its LENS record and holds the encoded 296-byte chat summary and slot stamps. Existing whole-record copy relocates LENS references on clone/compaction; OffsetAudit checks the copied version in the native lifecycle test.

The provider measurer visits `journalEntryPlans` over the tentative indexed snapshot. It materializes one normalized unit, calls the existing message/media converters, counts UTF-8 JSON bytes including escaping, tool names and data-URI wrappers, retains numeric facts, and releases the unit as iteration advances. Two six-state summaries carry message separators and pending image/video media, including the affine pending-byte counter from the validated phase-zero model. Variants keep or remove thinking. Inclusion/strip policy selection beyond explicit variant 0/1 is not integrated with the request planner yet.

Incremental normalization changes invalidate the affected entries' stamps. The fill descends through stale/missing aggregates and path-copies measured entries; ordinary append does not walk or decode the journal prefix. Response arrival/better-response replacement remeasures the affected normalized holder contribution. Rebuilds invalidate and refill surviving contributions. This first version rereads selected unit blocks for remeasurement. Recomputing changed summaries directly from reusable LENS facts, Kimi all-holder name/token/byte repair, and image-only remeasurement are still open. LENS bytes are not yet included in the existing ROW-only `liveBytes` aggregation, so compaction accounting remains a follow-up.

## Query and measured cost boundary

`planStoredChatMessages` requires a matching registered key and current, complete base generation in the supplied pin. It throws on missing/stale facts instead of treating an all-zero summary as a zero length. It reads only the aggregate START column, then adds array brackets, the current system message and any final tool-media flush. This plans the messages array, not the whole request envelope or a Content-Length header. No send is switched to it here.

Cold registration measures the affected history explicitly. The read-count test uses 128 rows: cold fills read more than 128 physical ranges, a selected warm query reads zero, append stays below the unchanged test's 150-read bound, and a different endpoint triggers another cold fill. Repeated warm planning reads neither ROW nor LENS payloads. These are read-count observations, not a retained-heap or 100000-call construction proof. The initial fill bulk-builds the assigned slot; subsequent fills prune by missing/stale aggregates. A stale aggregate stamp can require visiting descendants to separate valid entries from missing ones.

## Accepted subset and remaining work

The only registered provider format is `openai-chat:plain`, revision 1, without OAuth tool-name transformation and with the existing reasoning output field. Text, normalized AI tool pairs, escaped/Unicode names, better-response holder changes, and inline base64/URL tool media have direct differentials against existing builders. Stored-media references and non-AI tool-call contributions fail explicitly, because their projection/global-call decisions are not implemented here. No image-budget input is accepted. `imageKeyHash` remains zero and `imageGen` is initialized to one; separate image generations, image-contribution tracking and image/media/PDF metrics are not implemented.

Also open: other chat formats, Responses and Anthropic conversion; all-format revision/hash pins; LENS-based recomputation; selected-range/tail corrections; last-kept reasoning composition; envelope/media/PDF limits and stream guard; tokens; remaining W23 eight-case planning/header acceptance; W26 scratch removal; full 10k/100k/1M retained heap and 100000-call construction. The 44 frozen provider fixtures and 5000-case corpus are not regenerated. Codec #3917 remains separately RED, without retry or suppression. Review skipped per Andrew 2026-10-09.
