# Kimi fallback counter prefixes, 2026-10-20

Starting HEAD: `3b608a8858ea0b4f5d603239802b0762a415fc1e`. This slice adds persisted consumed-counter prefixes, written-digit arithmetic and an opt-in native row resolver. Production provider sends and the backend default remain unchanged. No format/settings slot, LENS measurement or holder token/byte remeasurement is activated.

## Counts and occurrence order

The existing tools mapper observes every eligible call before conversion. Eligible means nonempty raw ID and name, across every emitted speaker. The conversion fallback counter begins at that eligible total, not at the number of distinct mapped IDs. A later eligible duplicate replaces the name and ordinal of every mapped use. An unnamed occurrence does not replace that mapping.

`RowOccurrences` now computes each row's consumed fallback occurrences in emitted unit/block order. Human calls do not invoke the mapper during conversion. AI calls and tool responses do. An unmatched tool response consumes its fallback before the converter checks adjacency and drops the message. Counts therefore include dropped responses, while written-ID and written-digit totals exclude them. Full native normalized histories give nonempty tool responses original or reconstructed calls; empty response IDs are removed by normalization, independently of fallback accounting.

`RowEntry.unmappedBlocks` stores the consumed count. Its existing aggregate sum supplies total and below-label counts without enumerating preceding rows. Each 20-byte emitted occurrence uses flag 8 for an unmapped conversion use. Its existing u16 rank stores fallback-within-row for that flag, eligible-within-row otherwise. Eligible and unmapped cannot both be set. The widths of row entries, aggregates, occurrence values and slot summaries do not change. In particular, occurrence values remain below the copier's IdFact size discriminator. File version 7 rejects CRC-valid version 6, whose activation did not imply these populated prefixes or rank semantics. No compatibility path is added.

Native fallback index is eligible total plus the aggregate below its row plus its stored fallback rank. `kimiUnmappedCount`, `kimiUnmappedBelow` and `kimiFallbackIndex` use the same pinned roots. Append and normalization-affected rows update counters before acknowledgement. If a new named call first maps an old unnamed ID, the incremental writer streams that ID's old holders and recomputes each holder row's emitted ranks and counter before publishing facts and tree roots together. This also changes ranks of other IDs in that row. No history-sized holder collection is retained. Repeated holders can revisit a row; this write cost is not represented as a constant-cost append. Rebuild/fill streams surviving row metadata, and clone/compaction carry the counters and offset-free occurrences. Old pins retain their own roots.

## Digits and request continuation

`kimiDigitRange(first, count)` sums decimal widths over a half-open counter range by decimal boundary, in work proportional to the number of digit widths. It checks inputs, end counter and accumulated totals as nonnegative safe integers. The complete native written-digit total combines twice the eligible ordinal sum, the existing mapped-exception correction, the fallback sequence starting at the eligible total, and subtraction of every dropped fallback response's indexed digit width. The global AI-call fact determines whether validation drops these unmapped responses. `kimiUnmappedWrittenCount` remains distinct from consumed count. These numbers describe ID suffix digits, not JSON bytes, token counts or full request length.

The request view corrects both eligible and consumed per-row totals over its existing affected-row/tail overlay. Newly mapped pending IDs remove earlier native fallback holders from prefixes; holders already in corrected rows are not subtracted twice. The selected row's own emitted metadata supplies the within-row prefix. `kimiCounterBefore(index)` accepts every normalized unit index and the end index. It uses the existing query hold and cleanup rules. Pending state contains only affected IDs/rows; no historical selection list is memoized.

Query work is tree depth plus selected-row metadata and pending-ID holder corrections. A pending ID with many earlier unmapped holders can require that holder stream per query. This is a sparse selected-ID cost, not an all-history ID pass; it does not establish a uniform O(depth) bound for adversarial dense duplicates. The fixed-tail read fixture measures the existing 40/4000/100000-row domain at unchanged call frequency and bounds. The 100000-row fixture has 4000 calls, so it does not resolve the earlier 100000-call construction timeout.

The opt-in native chat resolver prepares only one row's relevant occurrences. Repeated unmapped IDs remain separate entries because each conversion consumes a new counter. Its async lookups feed the existing synchronous converter callbacks in occurrence order, including responses subsequently dropped. Full-stream observation still supplies existing chat/thinking/media facts; the new ID resolver itself needs no whole-history map. This is not provider cutover or a completed removal of the old observation pass.
