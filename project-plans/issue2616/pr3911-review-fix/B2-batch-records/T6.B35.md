## Unobservable reads

Each needs an orchestrator decision before the scenario can lose the capture. Rows tried are named; no assertion was edited.

- U1 (scenario 2). Read: an asynchronous hold inside `#completeForeground` after the token is consumed (the tokenizer `prepareTokenizer` that `finishForeground` awaits). The handle was `capturedActivation(activation).owner.tokenizerFactory`. Rows tried: "Tokenizer readiness held or failing" (b) `AgentConfig.tokenizerFactory`: Route C only; `prepareAgentPreflight`, `preparePostConfiguration`, `preflight` and `createForegroundAgent` take no tokenizer factory, and the preflight builds the tokenizer from its own manager. Host hooks (the slice's proposal): `AgentForegroundHost.skillPolicy` is called only by `skills.reload` (`workspace-skill-owner.ts` `enqueue(true)`); `registerSkillTools` is called synchronously by skills initialisation only when skills are enabled and cannot hold; `onSkills`/`onExtensionRestart` run after `finishForeground`, when the agent already exists; `mcpHost` services run only on OAuth or feedback events; the GitHub broker selection is read synchronously. MCP discovery is not awaited by `initialize()` (`mcpRuntimeAssembly.ts` `initializeWorkspace` starts it and stores the promise). Proposed decision (tested in a scratch copy of the scenario, 2 pass, not committed): hold a public read instead, as scenarios 5 to 7 already do (`AgentClient.prototype.getHistory` spy with `activation.readHistory()`), so `createForegroundAgent` waits in `#joinPublicWork`; `activation.dispose()` stays pending, and after release the publication rejects `AbortError`. All assertions keep. Cost: the hold is before the token is consumed and before foreground MCP construction, so the rollback of a later-stage abort is no longer exercised by this scenario.
- U2 (scenarios 9 and 11a). Read: identity of the activation's message bus. Scenario 9 asserts the foreground agent's first subscription is on the activation's bus (`capturedActivation(activation).messageBus`, with a `bus.subscribe` spy); scenario 11a asserts that bus `toBe` the OAuth manager's `runtimeMessageBus`. The preflight's bus is the private `#bus` (`profile-preflight.ts:92`, handed to `activationBus` at `:708`) and no `AgentProfilePreflight` or `AgentActivationOperation` member exposes it; the OAuth manager is not exposed either. Rows tried: "Internal identity" (c) needs a covering assertion in the same scenario that fails when the bus is replaced; neither scenario has one (scenario 9's remaining assertions cover the client and history, not the bus; 11a's cover settings and activation state). ".messageBus used to answer or evaluate confirmations" needs a scripted tool call, which Route B with `provider: 'openai'`/`authMode: 'none'` does not have. Decision needed: drop the two bus lines under (c) naming a covering assertion the orchestrator adds (the T6.B09 precedent is a scripted tool call whose confirmation surfaces through `agent.tools.onConfirmationRequest` and is answered), or Replaced by a named test. The other seam reads in these two scenarios are done as designed in the slice and are ready: scenario 9's client history length becomes `activation.readHistory()` read before the transfer; 11a's `settingsOwnerOwnership` becomes the existing borrowed/transferred settings check.
- U3 (scenario 10). Read: the transferred client's `getContentGeneratorConfig()?.model` before the agent exists (before and after `finishPostConfiguration()`). Rows tried: "`.manager` reads" and Agent API: `agent.getModel()` reads the settings owner's selected model (`foreground-agent-assembly.ts` `finishForeground`), not the client, so it does not detect a client that was not initialised from the applied profile; `AgentProfilePreflight.readNamedParameter` covers only the `context-limit` line. "What the model sees on the next request" (a): a recording provider (H-b) contributed through `prepareAgentPreflight`'s `contributions`, profile snapshot provider set to its alias, a turn through the foreground agent, and the recorded request's model read; this observes the client's generator after the agent exists, so the two pre-agent reads collapse into one post-agent read. Decision needed: accept that form (changes the scenario's provider from `openai` to the contributed alias and adds a turn), or Replaced.

Read: the `'oauth'` and `'files'` stages, pushed by the observer after `initializePreparedActivation` (and its `state.providerFileLifecycle` defined and `state.oauthManager` not null checks).
