## Resolution of unobservable reads

The orchestrator decisions were applied. `withPreflight` no longer has the `observeActivation` flag (its last parameter is now optional provider `contributions`), the `observeActivationPreparation`, `captureActivationConstruction`, `capturedActivation` and `capturedSessionClient` imports are gone, and the file has no prototype capture of the activation or the session client. The only remaining spies are the ones that were in the file before the batch (`ProviderManager.prototype.setConfig`, `config.getPolicyEngineConfig`, `AgentClient.prototype.getHistory`, `AgentActivationBootstrap.prototype.createForeground`).

- U1 (scenario 2, 2 runs). The original held the acquired tokenizer's `prepareTokenizer` after token consumption. No production input fills the preflight's tokenizer (`activationTokenizer` is a protected field only the deleted test subclass filled), so a first pass moved the hold to a public `activation.readHistory()` before construction (scenario 2a). The phase 6 review found that this lost the rollback case for an abort that arrives after the token is consumed. T6.F10 restores it as scenario 2b through a production input: the Config's `toolDiscoveryCommand`. The foreground MCP runtime runs it inside `foregroundMcp.initialize()` (`workspace-tool-catalog-owner.ts` `initialize` -> `registry.discoverAllTools()`), after `#consume`, after `#constructForegroundMcp()` acquired the runtime, and before `finishForeground`. The command is `cat <fifo>`; the test's blocking open of the FIFO for writing is the "entered" signal (no polling) and writing `[]` then closing is the release. The scenario asserts what the original did (dispose pending while held, `AbortError` after release, closing resolves, borrowed settings, `readHistory()` rejects `disposed`) and adds `closed` true after the join. No new prototype spy.
- U2 (scenarios 9 and 11a). The two bus-identity lines (activation bus `toBe` the agent's first bus subscription in 9; activation bus `toBe` the OAuth manager's `runtimeMessageBus` in 11a) are dropped under the Observation rule's "Internal identity" row. The earlier covering reference to T6.B09 was wrong (T6.F12, phase 6 review finding 4): no turn runs in either scenario. The covering assertion is the named scenario `delivers OAuth bucket consent from the activation OAuth manager to the foreground agent`, which fails when either relationship breaks. It uses a contributed OAuth provider (`createRefreshableOAuthContribution`, alias `consent-oauth`, selected as the Config provider through `withPreflight`'s `provider` parameter) so the factory hands the test the OAuth manager the preflight acquired (`oauth.managers[0]`). With `auth-bucket-prompt` true it calls the manager's public `authenticateMultipleBuckets(alias, ['work', 'personal'])`, which publishes a bucket-auth confirmation request on the OAuth manager's bus (`AuthFlowOrchestrator.buildOnPromptCallback`). The test observes that request through the foreground agent's public `agent.auth.subscribeBucketConsent` (the agent's bus), answers it through `agent.auth.respondToBucketConsent(correlationId, false)`, and asserts the manager's call rejects with `Multi-bucket authentication cancelled after 0 of 2 buckets`. The request can only reach the agent's subscription, and the answer can only reach the manager, if the OAuth manager's bus, the activation bus and the agent's bus are one bus; the agent bus is the activation bus's handoff target (`createForeground`), so one path covers both dropped lines. It does not cover the pair "activation bus is X while agent and OAuth are both on a different bus X'": the activation bus has no public read. Also in 9: the client history length is the `activation.readHistory()` read before the transfer (`agent.getHistory().length - history.length` is 0); in 11a the `settingsOwnerOwnership` line is dropped because the scenario's closing borrowed/transferred settings check covers it (slice proposal). New scenario runs: 1 (the bus does not depend on settings ownership).
- U3 (scenario 10). Observed through a recording provider (H-b, alias `profile-recording`, contributed through `prepareAgentPreflight`): snapshot provider is the alias, model `profile-selected-model`, one `agent.chat('hello')` turn through the foreground agent, assert `requests[0].resolved.model` is `profile-selected-model`. - U4 (scenario 12). Domain-level Replaced of the preflight publication order was not constructible: the `'oauth'` and `'files'` stage names were pushed by the prototype observer after `initializePreparedActivation` as one point, and no public read shows when the OAuth manager or file lifecycle is acquired (`#files` exists from `create`, so `captureProviderFiles()` proves nothing).
