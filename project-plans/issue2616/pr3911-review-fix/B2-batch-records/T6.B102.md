## `useSubmitQuery.background-clear.test.tsx` (stop rule, unchanged)

18 cases from 8 blocks, all proposed **Kept** by the slice, none applied. The file stays exactly as it was (it still builds its agents through `buildAgent`/`task-notification-fixture.ts` and still reads `fixtureAgentResources`, so it passes: `before-2.log`).

Why nothing could be migrated: every case drives the background work and checks the result through `backgroundOwners(agent)`, which reads `taskOwner`/`shellOwner` out of `fixtureAgentResources(agent)` (the capture T6.D2a deletes). After the capture is gone the file needs those reads from somewhere else. The Observation rule's row "Task and shell owners" gives (a): start the job through a real tool call and observe through `agent.tasks` and the `check_async_tasks` result. That gives the status of a job (`AgentTaskInfo`: `id`, `status`, `launchedAt`, `completedAt`, `error`/`exitCode`) and nothing else. The assertions need the following, which have no public form (`AgentTasksControl` has `subscribeNotifications`, `list`, `listRunning`, `get`, `cancel`, `cancelAllRunning`):

1. `tasks.getPendingNotifications()` length (0 or 1) and `shell.getPendingNotifications()` length 0: cases 1 to 18 (every case).
2. `tasks.hasPendingWork()` and `shell.hasPendingWork()`: `TaskLaunchOwner.hasPendingWork()` is `launches.size > 0 || noticeDrains.size > 0 || noticeDeliveries > 0`, internal bookkeeping with no status equivalent. Used as the `waitFor` gate and as an assertion in cases 1 to 16 and 17.
3. `tasks.getTask('busy-ui-task')?.notifiedAt` `toBeUndefined()`: cases 6, 7, 8 to 11. `AgentSubagentTaskInfo` has no `notifiedAt`.
4. `tasks.join()` with `joinFailure instanceof AggregateError` expected true only for `provider error` (case 6) and `stream failure` (case 11): `join()` is owner-only (`TaskLaunchOwner.join`), and its aggregate holds the owner's cleanup `failures`.
5. The producer side: `tasks.start(...)` + `tasks.manager.registerTask/completeTask/failTask` with ids/messages `busy-ui-task`, `idle-recovered-output`, `idle-recovered-failure`, and `shell.launch`/`shell.current()?.cancel`/`shell.onJobCompleted|Failed|Cancelled`. A real `task` tool child (`launchHeldNotificationTask`) produces a failure with the message `Physical child failure` and a different id, so the asserted history text (`idle-recovered-failure`, `idle-recovered-output`) and the `getTask('busy-ui-task')` lookups cannot hold without changing assertions. The shell cases could be started by `run_shell_command` with `is_background: true` and the same commands, but their completion hooks (`onJob*`) are owner-only too.

Rows tried: "Task and shell owners" (a) as above; the T6.B61 ruling for owner-level task/shell reads (domain-level test of `TaskLaunchOwner`/`ShellJobOwner`). That ruling does not fit here: the subject of these cases is the CLI hook stack (`useSubmitQuery`, `useQueuedSubmissions`, `useAgentEventStream`) delivering through `agent.tasks.subscribeNotifications`, `agent.stream` and `agent.session.startNewSession()` against a real Agent, so the owners cannot be built apart from the agent. Rows "Internal identity" and the other rows do not apply (these are state reads, not identities). Cases 17 and 18 (`buildTaskNotificationAgent(manager, authority)`) additionally read `manager.getPendingNotifications()` and `owner.hasPendingWork()` from a caller-built `AsyncTaskManager`; the replacement fixture `buildTaskNotificationAgent(authority)` (T6.B95) drops that parameter, so even the manager is only reachable through the same owner read.

Orchestrator decision needed, one of: (c) with covering assertions the orchestrator names for reads 1 to 4 (for example, "pending notice" ≡ `startNewSession()` rejects `completion notices`, already asserted in most cases; `notifiedAt`/`join` aggregate have no such stand-in); Replaced by a domain-level test it names; or a bounded `T6.Pk` that adds a public read the CLI host then uses.
