## Decisions

- Path A approval: no `onApproval` is passed (not a `fromConfig` input). The test `Config` is built from `AgentConfig` fields only (`interactive: true`, `includeDirectories: [process.cwd()]`, the two `ConfigParameters` edits the old block made). `read_file` over `parity-toolcall.jsonl` runs to its single `done` without a handler, and Path A's projected events equal Path B's, so no approval mode field was needed.
- Path B client index: `ownerClients(builtRefCallerOwner)[1]`. The owner's client factory is called twice in that scenario: index 0 is the client built at owner creation, index 1 is the replacement `refreshAuth()` builds during `executeProviderActivation`. `capturedSessionClient` returned the current client (`publishedClient(owner.conversation)`), which is index 1. With index 0 the run failed (`Content generator config not initialized`, the retired client), which confirmed it.
- Scenario 5 of `config-initialization-boundary` is Replaced in the same file (see above), not in the file the slice named.
- `config-injection` T1 and the identity property: `internalConfig(agent)` identity dropped under row "Internal identity" (c), covering assertion `Config.setApprovalMode(AUTO_EDIT)` then `agent.getApprovalMode()`. In T1 the covering assertion runs after the stream so it does not change the Config the turn runs with. `internalConfig` is no longer imported by any file in this batch.
- `useConsumerPromptDirectory()` in `config-injection.spec.ts` is kept as written (suite-level prompt directory, unchanged).
- `config-injection.spec.ts` T7 half B keeps `buildAgent`, `captureProbe` and `agentClientDisposed` (see its row); those exports are rewritten in place by a later batch / T6.D2a.
- Property scenarios keep their `30000` ms test timeouts and the default `fc.assert` run counts. They open a Route A agent per generated value (5.9 s and 6.0 s on this machine, against 7.4 s before for the heavier caller).
