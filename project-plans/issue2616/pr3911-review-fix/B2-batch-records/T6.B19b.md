## Where the Replaced reads go

The reads T6.B19 could not observe through `createAgent` are the provider-scoped records of the `SettingsService` (`model`, `auth-key`, `base-url`, the outgoing provider's scope staying empty, the placeholder model not written) and `getContentGeneratorConfig() !== undefined`. The narrowest production owner that persists them is `executeProviderActivation` (`providerActivationExecutor.ts`), and the production caller that lets a test own the `SettingsService` is `fromConfig(config, settings, { activation }, authority)` (Route A: `openRouteAAgent`). So the new test drives `executeProviderActivation` through `fromConfig` with an intent shaped as `createAgent` synthesizes it from the legacy `provider`/`model`/`auth` inputs (`createAgent.ts` `applyActivation`: best-effort switch, the model unless it is the placeholder sentinel, credentials as `cliOverrides`), and reads `settings.getProviderSettings(...)` from the settings the test passed. Why not call `executeProviderActivation` with hand-assembled arguments: its `switchProvider`, `manager`, `refreshClient` and `selection` arguments come from `assembleProviderSwitch`, `acquirePreferredProviderManager`, `SessionClientOwner` and `assembleModelSelection`, which `fromConfig-session.ts` already composes for exactly this call (line 426 and 481); a hand-built copy would be a second composition of the same wiring.

The legacy synthesis itself (`parsed.activation ?? { ... }` in `createAgent.applyActivation`) has no export, so `legacyShape()` in the new test restates its output shape. The createAgent scenarios keep the legacy-versus-explicit equality on the Agent-observable state, so a divergence between the synthesis and the explicit intent still fails there.
