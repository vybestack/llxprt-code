## Unobservable reads

1. `providerActivation.behavior.test.ts` (g) and (h).
   - Needs: (g) a provider named `gemini` that streams `'gemini activation ok'`, registered on a manager next to `fake`; and `deletedManagerMember in liveManager` on the manager the executor used. (h) a real switch from active `fake` to `gemini`, then `getProviderSettings('gemini')` / `getProviderSettings('fake')` and the two ephemerals.
   - Rows tried: "`registerProvider` on a caller manager becomes a `providerContributions` entry (check the name against the built-in registry first, R-GEMINI)": `gemini` is a built-in id, which the contribution registry rejects. With `LLXPRT_FAKE_RESPONSES` set, `populateProviderManager` registers only `FakeProvider` and returns before built-ins and contributions (`providerManagerInstance.ts`, `tryActivateFakeProvider`, line 525), so no production input yields a manager holding both `fake` and any second provider (same finding as T6.B05 owner-9). Without the seam, `fake` does not exist. "`.manager` reads": `agent.getProvider()` gives the name only; no Agent, preflight or `AgentProfilePreflight` member returns the manager, so the dead-surface `in` probe has no allowed approach. Internal-identity row (c) does not apply: the dropped line is not an identity assertion.
   - Decision needed: for (g) and (h) replace the `gemini` literal and the outgoing `fake` by contributed aliases or a built-in outgoing provider (as T6.B10 scenario 12 and T6.B05b did), and decide the trap: Replaced by a domain-level surface check on a production-built `ProviderManager` (the member would be absent on the class), or Removed with the retired member as citation. Then T6.B51b migrates the whole file (including (a), (b), (c)).
2. `quota-registry-proxy-isolation.behavior.test.ts` (R-REG). Needs `modelRegistry.on('models:updated')` to wait for B's background refresh, `modelRegistry.refresh()` (explicit, returns `true`) on A and B, `modelRegistry.getById('fake/fake-model').contextWindow`, and an exact `models:updated` count of 2 (scenario 2). Rows tried: "Model registry": request counts and `agent.listAvailableModels()` are available (`listAvailableModels` initializes the registry, which starts the refresh in the background and does not await it, `modelResolver.ts`/`registry.ts` `loadModels`), but the `Agent` has no model-change subscription (`git grep "models:updated"` in `packages/*/src` outside tests finds only `registry.ts`), so there is no way to wait for the refresh, to trigger an explicit refresh or to read the registry entry or the publication count without a delay or a poll that would change the scenario. The registry is built inside `SessionClientOwner` (`session-client-owner.ts:284`) and bound into the manager; no production input supplies it. Decision needed: Replaced by a domain-level test of `ModelRegistry` with a forwarding proxy for the `refresh`/`getById`/publication-count assertions and an agent-level test for the proxy isolation and `listAvailableModels()` context windows, or a public model-change read that a host needs.
