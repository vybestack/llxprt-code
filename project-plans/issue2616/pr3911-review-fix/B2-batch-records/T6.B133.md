## Construction decisions

- The three `zed-provider-owner.connection-owner-N` files each carry one or two copies of a roughly 330-line hand-assembled "caller engine" (`Config`, `RuntimePolicyOwner`, `buildTestMcpRuntime`, `SessionSettingsOwner`, `acquirePreferred*`, `createCapturedSessionOwner`, `executeProviderActivation`, `assembleProviderSwitch`) built only to serve the host side of `serveZedConnection`. Production serves it from the foreground preflight (`handleActivatedZedIntegration`, `packages/cli/src/cli.tsx:823-848`): the `AgentProfilePreflight` is `profileApplication` and `trustPort`; `profileDefinitions` is `{ listProfiles: () => preflight.listProfiles() }`; `createSessionSettings` restores a new `SettingsService` from `preflight.captureSettingsSnapshot()`; and `ensureAcpProviderActivated` activates the config's provider when none is active. The migrated files build that host through H-e (`openRouteBPreflight`, then `route.prepare()`) and one new zed-acp test helper, `packages/zed-acp/src/__tests__/zed-preflight-connection.ts` (`openZedPreflightConnection`), which owns the profile files, the in-memory ACP stream pair and the `serveZedConnection` call with the production host shape. It is named for this subject and shared with T6.B134's `zed-provider-owner.connection.test.ts`. Helper created: `zed-preflight-connection.ts`.
- `zed-model-port.behavior.test.ts` scenario 2 needs a live-varying provider context limit. The old test assigned `provider.getContextLimit` on the engine's active provider instance, which an agent built through a public entry point does not expose (`agent.getProvider()` returns name and tool format only). No built-in provider reports a settable limit. The seam is a provider contribution (a documented public input; `AgentConfig.providerContributions` on Route C). The test builds the agent with `createAgent` and a test-local contributed provider whose `getContextLimit` reads a test variable and whose answer is `a plain text reply`, so that file is Route C, not the slice's Route A (Route A has no contribution input; observation rule row "What the model sees"). Created helper: `zed-acp/src/__tests__/live-context-limit-provider.ts`.
- Cross-package imports of agents modules and agents test helpers by relative path are kept as the batch ruling for providers and zed-acp allows; the files stop importing `adoption-fixture`, `session-client-capture`, `runtimeFactories`, `mcp-owner-fixture`, `providerActivationExecutor`, `providerSwitchAssembly`, `model-selection`, `confirmationForcing`, `preferred-provider-acquisition` and `adoption-release`.

## Scenarios

### zed-model-port.behavior (2 scenarios)

1. `ACP model selection without provider-manager authority > re-queries live models after switching and retains the current model outside the catalogue`. Pure `buildZedConfigOptions` and `setZedConfigOption` over local functions; initial options `[retained, first, second]`; after setting `'second'` the retained entry is gone and `currentValue` is `'second'`; `'unavailable'` rejects with code -32602. **Kept (unchanged).** No B2 fixture is used; nothing to migrate.
2. `... > retains public Agent model queries and provider responses while usage reads stay live`. Agent built over the engine through `adoptFixture` with positions 4, 6 and 7. Assertions: the port has none of `providerManager`, `agentClient`, `sessionClient`; after `agent.setModel('retained-model')` the model option has that `currentValue`; the Zed context window doubles when the provider's limit doubles; `agent.chat(...)` text contains `a plain text reply`. **Kept (agent-level, Route C).** The engine, `adoptProviderManager`, `adoptMessageBus` and `adoptMcpRuntime` drop out (never set in production: `adopt*` table; `AgentActivationBootstrap.adopt` writes only `adoptSettingsService`, `adoptIntent`, `adoptCredentialAuthority`). The agent comes from `createAgent` with `providerContributions` and the test's `CredentialAuthority`. All assertions stay on the `Agent` API; the one input that changes is how the limit is made live (the contributed provider's `getContextLimit` reads the test's `limit` variable instead of an instance assignment on the manager's active provider). Forced by the route: a turn through the agent honors the provider's reported limit. With the starting value 8192 (doubled to 16384) the final `agent.chat` ended `context-overflow` with an empty text (`tmp/pr3911/T6.B133/after-4.log`; the turn's request estimate was 11411 tokens). The starting value of the test's `limit` variable is therefore 100_000 (doubled to 200_000); the doubling assertion, the response assertion and every other line are unchanged. `capturedSessionClient(...).startChat()` and `ownerCallerManager.getActiveProvider()` were only engine plumbing: the chat starts with the turn.
