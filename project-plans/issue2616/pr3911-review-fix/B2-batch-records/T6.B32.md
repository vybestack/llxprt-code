## Decisions

- `createAgent` forces confirmations by default (`harness.forceConfirmations`, `agentRuntimeAssembly.ts:308`): a policy ASK rule for every tool and a registry wrapper whose invocations return a generic `info` confirmation. With the default, the scheduler never reached the MCP tool's own `ProceedAlwaysAndSave` handling and the failed save was not reported as a tool error (first Route C run: marker `invoked\n` instead of `''`). That is the documented harness seam, not a production-path defect: the CLI and `fromConfig` do not set it. The scenario is about the real MCP approval path, so it passes `harness: { forceConfirmations: false, includeProcessCwd: false }` (public `AgentConfig` input, defaults documented in `config-types.ts`); with it, every unchanged assertion passes. `includeProcessCwd: false` keeps the original `Config`'s workspace (only the working directory).
- The "B's decision stays `ASK_USER`" reads after A's approval use `agent.policy.getRules()` on B's own agent and are real isolation checks on the production route (A's rules hold the approval, B's do not). The same read after B's own failed save is Removed (see scenario 1).
- `mcp-connected-disposal` scenario 2 is Kept in a reduced, retitled form instead of Removed as the slice proposed (standing ruling: keep the rest of the scenario). If the orchestrator prefers the slice's Removed, delete the test and the counts change to Kept 6, Removed 1.
- H-a is not used by `mcp-config-lifetime` beyond `openRouteAAgent` in scenario 4; H-d is not used (no client is read any more).
- Logs: `tmp/pr3911/T6.B32/before-1..3.log`, `after-1..3.log`, `boundary-1.log`, `boundary-2.log`, `typecheck-1.log`.
