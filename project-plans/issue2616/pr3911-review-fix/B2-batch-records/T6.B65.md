#### 1. `joins the preflight client before media cleanup when adoption runtime construction fails`

Assertions today: a held `operation.preflight(intent)` receipt is adopted with `runtimeFactoryBindings.taskToolRegistration` throwing `Runtime assembly fault`; the owner's client is an `ObservedCleanupClient` (subclass of `AgentClient`) whose `dispose()` records whether `builtMedia.store.getStoredByteLength()` still resolves; `fromConfig(...)` `.rejects.toThrow('Runtime assembly fault')`; `cleanupStates` `not.toContain(false)`; afterwards `builtMedia.store.getStoredByteLength()` `.rejects.toThrow(/closed/i)`.

Outcome: **Kept, domain-level** (rollback and disposal order are never Removed). The adoption route (`adoptActivationPreflight`, `activationSuppliedClient`, `adoptRuntimeFactoryBindings.taskToolRegistration`) has no production writer, and `runtimeFactoryBindings` is not an observation input (T6.D2b), so the failing construction cannot be driven through `fromConfig`. The production rollback that orders client release before media release after a failed assembly is `cleanupFailedCreatedAgent`. The subject is that exported production function with real collaborators: a `SessionClientOwner` built through `SessionClientOwner.create` (`createCapturedSessionOwner`, H-d) and a `SessionMediaOwner` built through its constructor. Changes of form (recorded):

- The fault: `cleanupFailedCreatedAgent(new Error('Runtime assembly fault'), ...)` is called with the primary error, in place of the `taskToolRegistration` throw. Assertion `rejects.toThrow('Runtime assembly fault')` is unchanged.
- The client observation: `ObservedCleanupClient extends AgentClient` is a subclass of a production class, not allowed in a domain-level Kept. The factory passed to `createCapturedSessionOwner` (the parameter production fills with `buildAgentClientFactory()`) returns the real client with its `dispose` wrapped on the instance (Observation rule, fault row). The recorded state (`store.getStoredByteLength()` resolves while the client disposes) and both assertions (`cleanupStates` `not.toContain(false)`; store rejects `/closed/i` afterwards) are unchanged.
- The held `operation.preflight` receipt and `prepareActivationFixture` go (they existed only to feed the adoption route).
- One added assertion: `expect(cleanupStates.length).toBeGreaterThan(0)`. `not.toContain(false)` is vacuously true when the client never disposes, and the new trigger has no other disposal of that client (the original's `owner.refreshAuth()` inside the activation is not called: it would replace and dispose the first client before the rollback, and scenario 3's failing `dispose` would then throw from `refreshAuth`, which the original's activation never did). The added line makes the unchanged `not.toContain(false)` assertion fail if the rollback skips the client.
