The turns and `generate` reached the local endpoint, but `generateJson` failed with `Provider-backed content generation uses the IContent pipeline; direct ContentGenerator generation is not supported` (the default generator does not reach the endpoint for auxiliary requests). - `b.client.generateContent(...)` is Replaced (phase 6 review finding 5, T6.F13) by the domain-level test `carries each session client owner's MCP instructions into lightweight generateContent requests` in the same file: two real `SessionClientOwner`s built by `openClientOwner` (production `create`, MCP runtime from `mcpServers`, `contentGeneratorFactory` passed as `createAgent` passes it), each factory-produced client calls `generateContent` against the local endpoint; the owner's instruction is present and the peer's absent in the single request body. `b.agent.generateJson(...)` stays as the agent-level check for the `generateJson` route.
- Child scopes: the hand-composed `loadAgentRuntime`/`createSubagentScope` child is replaced by the production Task route. The local transport answers a parent request whose last message is the user turn `Run the child.` with a `task` tool call (`instruction-child`, saved subagent and profile under the test's `LLXPRT_CONFIG_HOME`, pointing at the same endpoint); the production child launches, and its request (identified by the user message `Return the requested text.`, asserted present in at least one body for each child observation) is checked in `observed(..., present, absent)` exactly like the old child(a)/child(b) bodies. - `onApproval: () => ToolConfirmationOutcome.ProceedOnce`: after `setTrustedFolderLive(false)` the `task` call needs a host approval (the old hand-composed child had none); the handler is the public host input.
