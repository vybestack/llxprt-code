## Decisions

1. `ide-client-independent` scenario A passes the shared `Config` to `fromConfig` directly (not through H-a's `openRouteAAgent`, which creates one `Config` per agent), each agent with its own seeded `SettingsService` and one `CredentialAuthority`. The `SessionSettingsOwner` fixture is gone; `fromConfig` creates and owns its settings owner (`adopted-agent-assembly.ts:536-541`), and no assertion read the caller-built one.
2. `ide-client-independent` scenario C failure trigger: `AgentConfig.tokenizerFactory.prepareTokenizer` throwing (the slice's candidate), which `createAgent` now accepts (T6.P1). The run reached `IdeClient.create` and disposed the acquired lease (the `streamClosed` wait would hang otherwise), so the rollback path is exercised.
3. `ide-client-independent` scenario D memory check: `agent.memory.getMemory()` throws `Instructions are disposed` after `dispose()`; this replaces `workspace.workspaceMemory.operations.snapshot()` on the hand-built workspace, whose `McpRuntimeOwner` production does not expose.
4. `instruction-publication-drain`: the surviving-agent settings write and read (`setModelParam('maxOutputTokens', 79)`, `getModelParams()`) replaces the borrowed `SessionSettingsOwner` write. When the peer closed first there is no live agent after the held close, so that arm has no surviving settings to write through; its second `expect` takes `undefined` (`survivor?.maxOutputTokens` is `undefined`, expected `undefined`), written without a conditional `expect` because the lint rule `jest/no-conditional-expect` forbids one. Basis for dropping that arm's write: the caller-owned settings owner (`adoptSettingsOwner`) and settings service sharing between two facades cannot be handed to a production agent (`AgentActivationBootstrap.adopt` sets only `adoptSettingsService`, `adoptIntent`, `adoptCredentialAuthority`), so "a closed facade does not poison caller-shared settings" has no production form when no agent remains.
5. The held operation in `instruction-publication-drain` is a `countTokens` call inside `updateSystemInstruction` (through `AgentConfig.tokenizerFactory`), not the original spy on `client.updateSystemInstruction`; `estimatePrompt` delegates to `legacyEstimate()`, as the existing `fromConfig-tokenizer-readiness` and `createAgent.injectedFactories` tests do.
6. `await publication` in `instruction-publication-drain` now awaits `agent.memory.refresh()`, which settles when the workspace refresh settles; the held instruction publication itself is joined by `agent.dispose()` (asserted by `closed` false while held, then `closing` resolving after release and the held call having counted a non-empty instruction). The original `publication` promise also covered the client update; no public handle exposes that promise on a production route.
