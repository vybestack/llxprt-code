## How each part is built

- Agent: `createAgent({ provider: <contributed alias>, model, sessionId, workingDir: root, folderTrust: true, telemetry: { enabled: false }, recording: { enabled: false }, credentialAuthority, onApproval, providerContributions, mcpServers })`. `onApproval` is a public `AgentConfig` input (`config-types.ts`). Discovery of the MCP tool is awaited with `awaitMcpDiscoveryReady(agent)` before the first turn (the turns keep `mcpDiscovery: 'skip'`).
- Model boundary: was an instance spy on the real `FakeProvider.generateChatCompletion` found through the caller's provider manager. Now a test-local provider registered through `providerContributions` (as `helpers/recording-provider.ts` does) whose `generateChatCompletionWithOptions` is the same gated generator: first request held until released; odd requests yield the `tool_call`; even requests yield `<owner> finished`; request contents recorded. H-b (`createRecordingProvider`) cannot be used because it only answers text and cannot script tool calls; it is not modified.
- Tool: was `prepareSessionTools` (position 33, never set in production). Now a stdio MCP server through `mcpServers`. H-c (`createGatedRecordingMcp`) returns the fixed text `recorded`, so owner-distinct output cannot be asserted through it; a sibling helper `helpers/gated-echo-mcp.ts` (+ `gated-echo-mcp-server.ts`) has the same shape and answers `<outputPrefix>:<arguments.invocation>`. H-c itself is not modified (see "Decisions needed"). `trust: false`, so each call asks for a confirmation, which `onApproval` answers (the approval-handler assertion stays).
- Tool held / entered / calls: `toolEntered` -> `mcp.entered()`, `toolRelease` -> `mcp.release()`, `calls()` -> `mcp.calls()` (the `invocation` argument of each call the server received).
