## Orchestrator decision (option 2) and how the refresh is built

The scenarios hold, answer, abort-observe and count the OAuth manager's token refresh. The built-in providers' token endpoint is a fixed HTTPS URL no fixture can serve, so a provider contribution registers a test OAuth provider on `context.oauthManager` under a contributed alias (`postcommit-oauth` in the lifetime file; `sibling-failing`, `sibling-held`, `sibling-plain` in the siblings file), never `claudecode`. New helper `helpers/refreshable-oauth-provider.ts`: `createRefreshableOAuthContribution(entries)` (one answering provider and one OAuth provider per `{ alias, refresh }`, plus the `OAuthManager`s the host handed the factories) and `createRefreshableOAuthProvider(entry)` (the same OAuth provider for a stand-alone `OAuthManager`). `refresh` is the test's own function, so each scenario decides to hold it, answer it, observe its `AbortSignal` or count it. The existing `helpers/oauth-contribution.ts` was not modified (its provider cannot refresh or answer a turn). Route C: `createAgent({ provider: alias, tokenStore, credentialAuthority, providerContributions })`, `enableOAuthProviders(configHome, [aliases])` for `oauthEnabledProviders`. `LLXPRT_FAKE_RESPONSES` is deleted for the run (the replay seam pins every agent to `fake`).
