## Unobservable reads and orchestrator ruling

Orchestrator ruling (iii): `prepare-preflight.ts` stays as is in this batch. Its importers' own batches move off it (T6.B115 `provider-switching.integration.test.ts` is the template) and the batch that removes the last importer deletes it. Nothing is outstanding for T6.B117 on this file.

Original analysis:

`prepare-preflight.ts`, the `RuntimeProviderManager` the preflight builds in `#acquire` (`profile-preflight.ts`, `this.#manager = new ProviderManager(...)`), published today through `observeActivationPreparation`'s override of `AgentActivationBootstrap.prototype.initializePreparedActivation` and its `SessionClientOwner.create` spy.

Rows tried (PLAN.md Observation rule):

- `.manager` reads, approach (a): `AgentProfilePreflight` exposes only `getActiveProviderName()`, `hasActiveProvider()`, `setActiveProvider()` and `captureSwitchOperation()` (a `ProviderSwitcher`); `Agent` exposes `getProvider()`, `listProviders()`, `listAvailableModels()`. None returns the manager object. No `RuntimeProviderManager` read exists on `AgentActivationOperation` either.
- `registerProvider` on a caller manager becomes a `providerContributions` entry: `prepareAgentPreflight(..., contributions)` accepts a registry, so mock providers can be contributed (the choice S21 asks to be made once for the six importers). That removes the registration need, but not the other uses.
- Activation prepared state, (b): `prepareAgentPreflight`/`preparePostConfiguration` take no manager input; the manager is built inside the preflight.
- (c) identity drop does not apply: the importers use the manager as an argument (`switchActiveProvider(name, {}, config, settingsService, providerManager, ...)`, `setProviderApiKey(..., providerManager.getActiveProvider())`, `providerManager.getActiveProviderName()`), not as an identity comparison.

What the importers need: a `RuntimeProviderManager` to pass to those CLI runtime functions, and, in `provider-switching` scenario 1 only, the activation owner's `assertProviderManager(providerManager)` on the very manager the preflight built.

Options considered (the orchestrator chose (iii)): (i) importers that only need a manager for the CLI runtime functions build their own domain-level manager with `acquirePreferredProviderManager` (as `provider-multi-runtime` does) and no longer depend on the preflight's manager, in which case `prepareIntegrationPreflight` keeps only `preflight` (and `contributions` for mock providers) and is replaced by a successor under rule 3; provider-switching scenario 1 then needs its own answer; (ii) a `T6.Pk` that adds a public manager read on `AgentProfilePreflight` if a production host needs it; (iii) fold `prepare-preflight.ts` into the importers' batches (B115, B144, B145) and delete it with the last importer. The coder did not choose: every option changes what the importers' assertions run against, and a rule-3 successor created here could collide with the same helper created by the parallel batch of the first importer (B115).

`prepare-preflight.ts` is therefore unchanged in the working tree.
