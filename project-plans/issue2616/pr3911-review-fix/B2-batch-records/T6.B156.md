It builds the `Config` and calls `initializeTestConfig(config)` (production `fromConfig`, Route A; the helper registers the agent and `Config` disposal). The local `SettingsService` and the caller `SessionSettingsOwner` go away.
- `ephemeral-settings.integration.test.ts`: the agent is read only through `getEphemeralSetting(s)` / `setEphemeralSetting`; `initializeTestConfig(config)` (Route A) replaces `initializeTestAgent`. The two scenarios that built a `ProviderManager` plus `configureProviderTokenizer` over the test's `SettingsService` read nothing from it (every assertion is on the agent's ephemeral settings), and the manager was bound to a settings service the agent no longer shares, so that dead setup is dropped (recorded decision; no assertion touched).
- `consumer-content-generation.integration.test.ts`: scenarios 1 and 2 passed a caller `ProviderManager` with a registered test provider to `initializeTestAgent`. They move to Route B (`openRouteBPreflight({ contributions })`): the test provider is a provider contribution (alias `test-provider`), activated by the intent `{ provider: 'test-provider', model: 'test-model' }`, as `provider-switching.integration.test.ts` (T6.B115) does. `configureProviderTokenizer(manager)` and `manager.setActiveProvider(...)` were setup on the caller manager; the preflight route installs the tokenizer and activates the provider itself, so both calls go. Scenario 3 builds no agent and is unchanged.
