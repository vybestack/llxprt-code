Created helpers (new, beside the unchanged `generation-owner-fixture.ts`, whose signature is untouched):

- `helpers/generation-provider.ts`: `createGenerationProvider({ alias, replies? })` returns `{ alias, contributions, requests, generating }`. A provider contribution (an `OpenAIProvider` subclass registered through `buildProviderContributionRegistry`, as `recording-provider.ts` does) that answers from a scripted list (`turn one reply`, `turn two reply`), records every request and runs the assignable `generating` hook between recording and answering. `recording-provider.ts` answers one constant text and was not modified. Alias `gemini` is allowed because Gemini is contributed by a plugin, not built in (`builtinContributions.ts`), so the alias selects the temporary-client path (`provider.name.toLowerCase() === 'gemini'`, `session-text-generation.ts`).
- `helpers/generation-client-owner.ts`: `withGenerationClientOwner(options, run)` builds a `SessionClientOwner` through `createCapturedSessionOwner` (production `SessionClientOwner.create`) over the same collaborators `client-owner-session.ts` assembles, with the contributed provider activated through `executeProviderActivation`. The client factory parameter (the one production fills with `buildAgentClientFactory()`) is wrapped: each real client it returns is wrapped on the instance (`initialize` and `dispose` count themselves and run assignable `initializing`, `initializedEffect`, `disposing` hooks). No class is subclassed and no prototype is patched. `prepareTokenizer` replaces tokenizer readiness only after the owner is open (the old fixture's `admit()`). It duplicates the assembly of `client-owner-session.ts` (`acquireProviderStack`) because `openClientOwner` takes no provider contributions, client observer or tokenizer hook and the protocol forbids changing shared helpers; folding both into one helper is a decision for the orchestrator.

## Production failures

1. `generate-history.behavior.test.ts` scenario 4, last assertion `expect(textHistory(await agent.getHistory())).toStrictEqual(seed)`: received the seed twice (4 entries). Red log: `tmp/pr3911/T6.B135/production-failure-1.log` (copy `tmp/pr3911/T6.P8/red-1.log`). **Fixed by T6.P8** (commit with trailer `Plan-Task: PLAN-20261023-PR3911FIX.T6.P8`). Cause: `SessionControl.startRecording` journals the history it reads from the native history (`seedOwnerRecording`) but, unlike the resume path (`publishPreparedHistory`), never told the new `RecordingIntegration` that this history was already recorded (`rememberRecordedHistory`); its subscribe-time memory reads only the `HistoryService`, which is empty while the seed still sits in the client's deferred history. The first `generate` starts the chat, `startChat` moves the deferred seed into the chat's `HistoryService`, and the integration journalled it a second time, so `resume('latest')` replayed four entries. Fix: `integration.rememberRecordedHistory(history)` before attaching. Without a generate the chat never starts, which is why the old harness (always a started chat) and the no-generate sequence hid it.
