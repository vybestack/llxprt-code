## Design decisions

These settle the "how" so coders do not have to choose.

- A1: `ExtensionEnablementManager`'s second constructor parameter becomes an optional selection object, `{ readonly enabledOverride?: readonly string[]; readonly disabled?: readonly string[] }`, replacing the bare `string[]`. Bootstrap passes `{ enabledOverride: argv.extensions, disabled: settings.merged.extensions.disabled }`.
- A2: declarative path. Extract the runtime-free steps of `loadCliConfig` (profile selection and load, context and environment, MCP server resolution, intermediate config) into one exported function in `packages/cli/src/config/` used by both `loadCliConfig` and `skills list`, and have `skills list` build `SkillDiscoveryIntent` from it. `skills list` never creates a preflight or authority.
- A3: `ProviderInvocationData` gains a required `fetch: NetworkFetch`, and `captureProviderInvocation` reads it from the data object (its sixth positional parameter goes away). `LoggingProviderWrapper`'s invocation reader supplies the owner fetch. `ProviderManager` loses the `globalThis.fetch` default: an unbound manager's `fetchNetwork` throws `Error('Provider request requires the owner transport')` when called. `RuntimeInvocationContext.fetch` and `createRuntimeInvocationContext`'s `fetch` become required. The `?? fetch` fallback in `vercelModelClient.ts` is deleted.
  Who supplies the fetch, per producer (decided from `inventory-phase2.md` findings F1-F5, F7 and table D):
  1. `SessionSettingsOwner.prepareProviderInvocation` keeps the fetch as its sixth parameter, and it becomes required; the three optional parameters before it (`modelParameters`, `signal`, `sessionId`) become explicit `T | undefined` positions, so the order does not change. The owner writes it into the `ProviderInvocationData` it builds. The settings owner holds no fetch: the root supplies it through the session (`this.fetch`, the root network, at `session-client-binding.ts` and `session-text-generation.ts`) and the child loader (`subagent-runtime-loader.ts`, the child root's `fetchNetwork`). The `PrepareProviderInvocation` closure type `(name, parameters, signal)` is unchanged, because the fetch is bound when the closure is built.
  2. Inside `ProviderManager`, every reader goes through `fetchNetwork` (the provider reader passed to `bindOwnerAuthentication`, and `admitRequest`); the private field is read only inside `fetchNetwork`, which throws `Error('Provider request requires the owner transport')` when no root bound it.
  3. Contract: `RuntimeProviderManager.fetchNetwork` is required, and `bindNetworkFetch` is not a contract member. Binding is the root's job, and every root holds the concrete `ProviderManager` it constructed.
  4. Providers get their transport only from their manager: `bindOwnerAuthentication`'s fetch reader is required, and an unbound `BaseProvider`'s `requestFetch` is a function that rejects with the same error (not `undefined`, which the SDKs would replace with the global fetch).
  5. A load-balancer call with no parent invocation throws the owner-transport error.

- A4: `authenticate` and `authenticateMultipleBuckets` run inside `foreground.accept` with the composed owner signal. `AuthFlowOrchestrator` keeps every started flight (including orphaned, aborted ones) until it settles and gains `dispose()` that aborts and awaits them. Lock release: in `AuthFlowOrchestrator.authenticate`, the `throwIfAborted(signal)` that runs after `waitForAuthLockOrToken` returns `'acquired'` moves inside the `try` whose `finally` calls `releaseAuthLock`, so an abort that lands during lock acquisition still releases the lock it got. The `'token-found'` and `'timed-out'` branches are unchanged (no lock held). Joining a flight then really does mean its lock is released. Interactive handlers: `InteractiveAuthCoordinator` keeps a `handlers: Set<Promise<void>>` of every started host-handler promise, added in `startSession` and removed only when that promise physically settles, independent of `sessions` (which `settleSession` empties early). Each step runs even if an earlier one rejects; their own failures are collected and reported together at the end. Joins wait for settlement and do not re-report caller-owned outcomes or aborts the owner caused; only the owner's own cleanup failures are reported.
- A5: joins of caller-owned work use `await Promise.allSettled(work)` and ignore the results; only the owner's own cleanup failures are reported. No new helper module. Ownership after the change: `AgentClient`'s `AuxiliaryWork` is the only owner of `generateJson` and `generateEmbedding` (it already wraps both); `SessionClientAcquisitionOwner`'s `AuxiliaryWork` stays and owns exactly the work that never passes through `AgentClient`: `SessionTextGeneration.generate` (temporary client acquisition and initialization, the standalone request, and the temporary client release). The acquisition owner's `generateJson`/`generateEmbedding` stop wrapping in its tracker and call the client directly. Disposal order: the acquisition owner closes its admission and aborts text generation, `AgentClient` closes its admission and aborts JSON/embedding, then each joins its own set. `AuxiliaryWork.close` stops putting the aborts it caused into its `AggregateError`.
  Two kinds of outcome, kept apart. Caller outcomes (a generation's own error, its abort) belong to the caller and are never reported by disposal; `AuxiliaryWork.close` joins them with `Promise.allSettled` and ignores the results. Owner cleanup outcomes (a temporary client's release: `client.dispose()` plus its provider-file scope release through `disposeClientAndFiles`) belong to the session and must reach disposal even though the generation that triggered them already returned. Today the temporary client is released inside the tracked generation (`session-text-generation.ts`, `cleanup` in `generate` and the setup `catch` in `#acquireTemporary`), and `OwnedClientLedger.release` deletes the ledger entry before the file scope finishes, so `settleOwnedClients` never sees it and a settled-only join would lose it. The fix is in the ledger, not in the generation wrapper: `OwnedClientLedger.dispose(client)` records any rejection of `disposeClientAndFiles` for that client in a private `#releaseFailures: unknown[]` and still rethrows it to its caller (the generation's caller keeps seeing the combined error it sees today). `settleOwnedClients()` returns the settled results of the remaining entries plus one rejected result per retained release failure, and clears the list. Consumption rule (one owner per failure): `#releaseFailures` holds only failures of releases that a caller started outside settlement (`dispose(client)` called by the generation's cleanup or by a replacement). Settlement itself disposes the remaining clients through a private path that does not record, for example `#disposeEntry(client, { retain: false })`, which public `dispose` calls with `retain: true`. `settleOwnedClients()` first takes and clears the retained list, then settles its own batch, and returns the retained failures followed by the batch results; a batch failure is in the batch result only. Every release failure is therefore produced by one disposal and enters one list. The session joins auxiliary work (`auxiliaryClosing` in `session-client-owner.ts` `dispose`) before it calls `settleClientReleases`, so no outside release is still running when settlement takes the list. The session's existing `finishCleanup(..., clients, ...)` then reports them. A release failure therefore reaches the caller once (as part of its request error) and disposal once (as an owner cleanup failure); the generation error itself never reaches disposal. No new wrapper is added around JSON or embedding work.

  3. Selection, in the library's order: explicit JSON, then `credentialsFile`, then `wellKnownFile` if it exists, then the metadata server. A file that cannot be read or parsed throws with its path and the original error as `cause`.
  4. ### Phase 6: delete unreachable adoption paths and move tests to production entry points (B2, E3, E9a)

#### Test conservation rule (applies to every task that deletes or rewrites a test, in any phase)

A fixture that writes an unreachable field proves only that its construction route is invalid. It does not prove the scenarios in the file are obsolete. So deletion is decided per scenario (`it`/`test` block), never per file:

- Each scenario is recorded with its name and its assertions (the `expect` lines, summarized) in the batch's section of `B2-batches.md` before any edit.
- Each scenario then gets exactly one outcome: Kept (migrated to a production entry point with the same expected behavior; assertions unchanged except how the agent is built), Replaced (the behavior is asserted by a named existing or new public/domain test; give its file and test name), or Removed (the behavior itself cannot happen in production; name the deleted field or option whose absence makes it impossible, and the production line that proves it, for example "production never sets `adoptLspOwner`: only `AgentActivationBootstrap.adopt` writes adopt fields, and it sets three, listed").
- Rollback, isolation between roots, disposal order and failure-reporting scenarios are never Removed just because their fixture is invalid; they are Kept or Replaced.
- Timers, timeouts and thresholds move unchanged.
- The commit body lists each scenario's outcome. The reviewer checks every Removed and Replaced entry, not a sample.

When a Kept scenario fails on the production path, it has found a real bug. The coder stops, saves the failing output to `W/tmp/pr3911/<task-id>/production-failure-<n>.log`, adds the scenario unchanged to `B2-batches.md` under "Production failures" with the log path, and writes a handoff. The orchestrator then creates a bounded fix task `T6.Pk` (scope: the production files the failure points at, red test: that scenario exactly as written), runs it under the normal protocol, and resumes the batch. The scenario's assertions are never adjusted to make it pass.

#### Bounded inventory rule (applies to every inventory task in this plan)

An inventory task that must read files one by one (scenario summaries, consumer member lists) covers at most 20 files. When the search behind an inventory returns more, the inventory is three kinds of task: one list task that runs the search, commits the sorted file list and cuts it into fixed slices; one slice task per slice that reads exactly its files and commits a complete section for them; and one aggregation task that checks coverage and produces the batches. A slice section is complete or not committed: a slice that cannot finish writes a handoff like any other task. Inventories produced by one mechanical command whose output is pasted unchanged (T2.0's test-site list, T5.5-inv, T7.0's script, T1.9d-inv's failing-test list) are exempt, because the command, not the reader, bounds them.

### Phase 7: composition instead of the assembly chain (B3, E1)

Inputs: `inventory-phase7.md` (every inherited member, where it is declared, and which chain files read or write it) and `ports-B6-B3.md` (the collaborator contracts). Behavior-preserving except where a task says otherwise.

How the edges are removed. Each task removes one complete dependency edge and changes every direct consumer of that edge in the same commit, so every commit compiles and passes. Two techniques keep scopes small and avoid bridges:

- A plain field that deeper classes still use moves its single declaration down to the class on the other side of the edge (same name, same type). Deeper consumers keep compiling unchanged. This is a move, not an alias: the old declaration is deleted in the same commit.
- A method or field that becomes a collaborator member is called through the collaborator by every consumer in the same commit (`this.providerReads.coordinator()`), including consumers in deeper chain files; those files are in that task's scope. No forwarding method is left on the old class.
