### Shared dependency: the caller engine (all 16 files)

Every `owner(name, ...)` helper builds, per agent, a full caller engine of about 330 lines (`Config` via `toConfigParameters` with `sessionId` label, `folderTrust: true`, `telemetry/recording` off; `SettingsService`; `RuntimePolicyOwner` + `injectConfirmationForcingPolicy`; `buildTestMcpRuntime`; `SessionSettingsOwner`; `ProviderFileLifecycle`; `acquirePreferredProviderManager`; `acquirePreferredOAuth`; `SessionMediaOwner`; `createCapturedSessionOwner(..., createAgentRuntimeFactoryBindings().agentClientFactory, ...)`; `executeProviderActivation`; `startChat()`). `createAgentRuntimeFactoryBindings` is used only to give `.agentClientFactory` to `createCapturedSessionOwner` in that engine (`...createAgentRuntimeFactoryBindings(), ...{}`); it is not passed to `fromConfig` (position 13 is `undefined`). When the engine goes, the usage goes; there is no literal to keep.

Three unreachable inputs carry real behavior and need a production replacement. Each scenario below says which it needs:
1. **Tool injection** (`adoptPrepareSessionTools`, position 33): the callback registers a `MockTool` on the session catalog (`external_record` in the client family, `parentRecord` + a real `TaskTool` with a test orchestrator in the child family). Production inputs that put a tool in an agent: `AgentConfig.mcpServers` (a stdio MCP server; the tests already have such servers, `packages/agents/src/api/__tests__/helpers/mcp-approval-stdio-fixture.ts`, `fakeMcpServer.ts`, and `useCommandOwners` passes `mcpServers`) and the built-in tools. A gated tool (the files' `entered`/`finish` gates) can be a stdio MCP tool that waits for a file or stdin message, or a built-in tool with a physical effect.
2. **Borrowed client** (`adoptAgentClient`, position 9, `capturedSessionClient(owner)`): production creates its own client per agent. The caller-owned client has no counterpart; the scenarios do not depend on sharing it except the one flagged below.
3. **Policy rules on the caller policy owner** (`builtCallerPolicy.session.confirmation.addRule({ toolName, decision })`): production reaches the same rules through `AgentConfig` approval settings (`allowedTools`, `settings`) or the `onApproval` handler; `PolicyDecision.ASK_USER` is the absence of an allow rule plus an `onApproval`/approval-bus consumer.

Where a scenario needs one of these and no production input can express it, the batch coder stops and writes a handoff naming the missing seam, as for S01. The scenario is not Removed: the behavior (UI scheduler/channel ownership, approval buses, cancellation, disposal joins) happens in production.

### Child family extra: the scripted child

The child files also build `createTestChildOrchestrator({... runtimeLoader, scopeFactory: SubAgentScope.create with fake createTurn ...})`, a real `TaskTool` with `launchChild: orchestrator.launch`, and a separate `childRegistry` holding the executing `child_record` tool (the parent registry's `child_record` throws `Parent registry must not execute the child tool`). Production route for a task child: `agent.workspace.profileWrites.saveProfile` + `agent.workspace.subagentWrites.saveSubagent`, then `agent.tools.get('task')` with `{ subagent_name, goal_prompt, tool_whitelist }`, the child's turns coming from a local OpenAI-compatible server or a fake-provider replay profile; this is how `cli/src/__tests__/task-notification-fixture.ts` (`launchHeldNotificationTask`) already drives a child through the real `task` tool. `a.getScope()?.output.terminate_reason` (`SubagentTerminateMode.GOAL`, read from the test-built scope) becomes the task tool result's reported termination. The "parent registry must not execute the child tool" separation has no production counterpart as written (production derives the child registry from the parent's catalog); the assertion that matters (the child ran the child tool exactly once, `effects`) is kept.
