Baseline: `issue2615-session-runtime` at `473900082`, after the merge of `origin/main`. This is an **existing-site ratchet**, not an assertion that workspace services have moved. No production owner changed in this stage. The existing slice E boundary remains separate.

Run from the repository root:

```sh
bun scripts/check-workspace-config-boundary.ts
bun scripts/check-session-config-boundary.ts
bun test scripts/tests/check-workspace-config-boundary.test.ts scripts/tests/check-session-config-boundary.test.ts
```

`project-plans/issue2615/workspace-config-sites.json` is the per-site baseline. Each row identifies the original path, line, column, member, TypeScript-resolved declaration path (where available), current package owner, expression, classification, and within-file occurrence. The checker reads each package tsconfig, adds all production `src` TS/TSX files even when excluded from that tsconfig, resolves imports and receiver/member types through TypeScript's checker, and deduplicates overlapping package programs. It compares `(file, classification, member, expression, occurrence)` against the tracked baseline, so new occurrences of an existing expression fail even when line numbers move. `--write-baseline` explicitly regenerates the tracked snapshot for a reviewed migration; normal lint does not rewrite it. Tests overlay actual production files in TypeScript compiler hosts rather than mocking Config or the checker. This also exercises a structural host whose method returns the resolved `SkillManager` type, a callback carrying that host, indexed value and indexed type access, and destructuring. The declarative `getModel` read does not produce a service site.

## Partial skill publication migration (stage 2, not F-ready)

The updated `workspace-config-sites.json` has 98 sites: 61 consumers, 2 projections, 26 ownership declarations and 9 constructions. `CoreSkillServiceAdapter` no longer takes Config; it receives a skill manager, storage, extension source and directory port. `SkillsControl` now reads an agents-owned `WorkspaceSkillSurface` rather than Config's skill manager. `fromConfig` and `createAgent` each discover a private skill snapshot before publishing their session tool registry. Skill activation declarations and controls update from that snapshot on extension transitions and skill reloads; a failed snapshot refresh leaves the prior published declaration in place. Session subscriptions are removed with the session task owner. Real two-session tests are in `packages/agents/src/api/__tests__/workspace-skills.behavior.test.ts`.

This is a **partial consumer migration**. `packages/agents/src/api/agentRuntimeAssembly.ts` still reads Config's skill manager for disabled/admin settings and Config's workspace context for activation. `packages/core/src/config/skill-tool-sync.ts` and `packages/zed-acp/src/zed-terminal-setup.ts` now assemble the adapter explicitly, but still read those three workspace services from Config. The Config-owned extension loader, skill manager, extension refresh callback, source registry and publication subscribers remain, as do CLI `/skills` and `/extensions` callers. The shared agents-owned skill surface now discovers once for all live borrowers of the same Config, replays the result to late borrowers, and releases its Config refresh subscription after the last borrower disposes (including partial bootstrap teardown). The two `getSkillManager` consumers in `agentRuntimeAssembly.ts` now read scalar Config settings (`getDisabledSkillNames`, `isAdminSkillsEnabled`) instead of the Config-owned service. The redundant rediscovery consumer in `fromConfig.ts` is deleted. These three removed consumers reconcile the 101-site snapshot to 98; the 26 ownership declarations and 9 constructions are unchanged. This does not remove Config's existing SkillManager or extension loader, and Config remains responsible for their source-level discovery, callback, and teardown. Do not describe this as F ownership completion. The regenerated baseline records the changed callsites rather than granting new ones silently. Extension lifetime is still Config-owned in `configConstructor.ts`, `configBaseCore.ts`, and `config.ts`; the extension loader still receives Config in `start()`. The CLI `/skills` and `/extensions` commands still reach the old services through `CliUiRuntime` (`skillsCommand.ts` and `extensionsCommand.ts`), with additional reach-through in `BuiltinCommandLoader.ts`, `cliUiRuntime.ts`, `contextManager.ts`, `skillDiscovery.ts`, `skill-tool-sync.ts`, and `zed-terminal-setup.ts`. The typed inventory records eight direct `getSkillManager` consumers and four direct `getExtensionLoader` consumers, but some CLI calls are against a structural UI runtime and are not counted. Shared owner subscription cleanup has a partial-bootstrap test; ownership deletion, CLI migration, and agents-owned extension teardown remain unproved. This stage must not be marked F-complete.

## LSP lifetime preparation (not a migrated site)

`packages/agents/src/api/workspace-lsp-lifetime.ts` now owns an independent LSP state and idempotent shutdown when explicitly started. `workspace-lsp-lifetime.behavior.test.ts` covers disabled startup, navigation registration before taking the first tool snapshot, partial discovery rollback, failed startup cleanup, concurrent disposal, and two independent lifetimes using one host. Core `initializeLsp` releases the client on startup failure rather than dropping its reference. No shipped agent or host constructs this lifetime yet. The Config-owned path still starts LSP on `Config.initialize` and tears it down through `shutdownLspService`; introducing a second startup on that path would create duplicate clients. **Migrated Config sites: 0.** The boundary snapshot remains at 98 sites, including four production `getLspServiceClient` consumers.

Remaining LSP work: move startup out of `packages/core/src/config/config.ts`, `_lspState` and parsed configuration out of `configBaseCore.ts`/`configConstructor.ts`, and the live client getter and shutdown from `configBase.ts`. Thread the one workspace-owned lifetime through `createAgent` and `fromConfig` without duplicating startup when adopting an already-initialized caller Config; bind navigation before `bindSessionTaskTools` publishes the session registry. Migrate `LspControl`/`buildNewControls` in agents, `CoreLspServiceAdapter` and registry construction in core, and `CliUiRuntime` in cli to explicit ports. `CoreToolHostAdapter` is another host seam to inspect for LSP-derived capability access. Update the existing core LSP tests that currently assert Config service ownership and the agent teardown tests that assert `shutdownLspService`, then delete those service paths in the same migration. Preserve caller Config identity and let independently owned LSP clients survive disposal of another borrowed session.


## MCP lifetime preparation (not a migrated Config site)

`packages/agents/src/api/workspace-mcp-lifetime.ts` now provides a narrow manager port, one discovery per workspace identity, shared borrowing, synchronous quarantine on trust revocation, and cancellation initiated before trust settlement on final release. Its behavior tests cover same-workspace borrowers, independent workspaces, background discovery, and concurrent disposal. The real-Agent mixed-server test in `mcp-discovery.spec.ts` checks that one failed server emits an advisory notice while a healthy server remains usable and the turn completes. That Agent test still runs through the existing Config manager. The new lifetime is not connected to `createAgent` or `fromConfig`; neither path starts it, avoiding a second manager. **Migrated Config sites: 0.** Do not claim MCP ownership has moved or regenerate the boundary ledger for this preparation.

Remaining live sites: `config.ts` constructs and starts the manager and discovery promise in `performInitialization`, routes trust transitions through it, reconciles reloads, and stops it during disposal. `configBaseCore.ts` stores `mcpClientManager` and exposes `getMcpClientManager`, `getMcpRuntimeStatus`, `refreshMcpServersWithContext`, `awaitMcpDiscoveryGate`, and `getMcpInstructions`; `configMcpRuntime.ts` implements the delegated operations. `extensionLoader.ts` calls the Config manager for extension starts/stops, and `contextManager.ts` reads instructions from it. `agentImpl.ts` awaits the Config gate; `mcpControlWiring.ts` uses Config status/refresh/reload and Config-owned prompt/resource registries. CLI paths still include `mcpAuth.ts`, `cliUiRuntime.ts`, `atCommandProcessor.ts`, and `slashCommandHandlers.ts`; `zed-terminal-setup.ts` still invokes the Config refresh. Migrate the registry and extension hooks with the owner, then remove these live Config manager paths together. In particular, adopting two agents from one initialized Config must not start a second manager, and disposing either agent must not dispose the borrowed Config.

## Deliberate limits

The ratchet only covers the ten inventoried getter names, return types resolved from those members, and the listed constructor identities under core config. It does not establish whole-Config closure. In particular, `_lspState` and the trust-transition lifecycle are not service-type members of this selected set, `getIdeClient`, `getPolicyEngine`, `getToolRegistry`, hooks and context-manager residue remain outside it, and a new unrelated service type not returned by any selected getter is not detected. Computed dynamic keys, `any`/unsafe casts, arbitrary higher-order callback flow after a method is stored, type-only mapped projections such as `Pick<Config, 'getSkillManager'>`, and a constructor outside `packages/core/src/config/` are not proven absent. The callback control catches its *named service source*; it does not prove downstream invocation identity. Tests/fixtures are intentionally excluded from the production ratchet; the earlier E census describes its own fixture and callback limits. The source signature may resolve through a package barrel or declaration file; the JSON records that resolved origin so migration reviews can distinguish a true Config caller from an unrelated same-named API.

Next stage: expand the typed inventory to the remaining workspace service types and structural callback/type projections, add the trust/LSP/MCP lifecycle and whole-Config disposition list, migrate callers bottom-up, then delete Config ownership and verify behavioral S7/S9 and host isolation before claiming F-ready. This baseline is supporting arithmetic, not a substitute for those tests or deletion.

## Workspace/filesystem session-port preparation (partial)

The inventory now has 94 sites. The agents assembly borrows the Config workspace context at its existing skill-surface consumer site, but can assemble a per-session workspace context and caller-supplied filesystem when `fromConfig` receives explicit workspace services. Session tool hosts and the Agent workspace control read that port; trust revocation blocks directory and filesystem access through it and hides the session tool registry. The borrowed Config and caller-supplied filesystem survive Agent disposal. Zed passes its ACP filesystem to `fromConfig`; the path resolver accepts an explicit filesystem and the two-directory behavior test covers that seam. Live Zed new/resumed sessions pass that filesystem directly to the path resolver, but the Config filesystem proxy remains for other Zed consumers and tests. This stage does **not** remove the proxy or Config ownership.

This is not the F ownership cutover. `Config` still constructs and stores both services. Without an explicit workspace option, agents still use the legacy Config-hosted tool access; the Agent workspace filesystem method is only available to sessions that supplied a filesystem. The CLI, Zed terminal, MCP, skill activation, context management, and other Config consumers listed above remain; the snapshot does not assert those paths have moved. Do not remove the Config fields, constructor assignments, or getters until these consumers are migrated.
