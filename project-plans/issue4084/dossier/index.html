Use code mode for mechanical tool work; keep subagents for investigation

Code mode lets the model write a program that calls existing tools, processes their results, and returns selected evidence. It can reduce intermediate data in the main context. A cheap subagent adds a separate reasoning context and can decide what to investigate next. Neither approach wins every workload, and the reviewed sources contain no controlled head-to-head benchmark between them.

For llxprt, the recommendation is an opt-in, read-only first release: JavaScript programs guided by TypeScript declarations, a fresh QuickJS-WASM runtime in a credential-free subprocess, and a separately owned scheduler for every script run. Each nested operation keeps the caller's tool restrictions, hooks and approvals. Only the outer result enters model history.

Existing behavior, vendor claims, illustrative examples and proposed contracts are identified separately. Sources: external survey and llxprt architecture analysis.

Three distinctions recur: discovery reduces loaded tool definitions; execution moves known control flow out of inference; delegation moves reasoning into another model context. These can be combined. Language isolation, process isolation and OS isolation are also separate guarantees.

Start with one task and follow the data#

Find every TODO in files touched in the last 10 commits and summarise by owner.

“Owner” here means the Git blame author of the current TODO line. It does not establish team responsibility. The search uses current workspace contents, including uncommitted lines, and the last ten reachable commits from a resolved HEAD. It counts lines containing the literal TODO, including occurrences in prose or strings. A different definition needs a different predicate. Deleted, unreadable, binary, truncated, or changing files must appear in coverage information. A shallow checkout cannot establish full history coverage. These choices follow the proposed example in internal research B10.

The following repository is an invented teaching fixture, not a measurement of llxprt. Its ten commits touch three current text files. src/parser.ts has TODOs on lines 12 and 35, src/cache.ts has one on line 8, and README.md has none. Ada authored two TODO lines and Bo authored one. Each result below is small enough to be acquired completely. The example makes no token or latency claim.

The proposed generated API#

The program below uses a proposed llxprt API surface. It is JavaScript guided by TypeScript declarations, matching the recommended first runtime. These selected structured adapters would need implementation and behavioral tests; they are not fields that can be read from today's human-oriented shell/read output. They must expose post-hook values, reject unsupported media, and report acquisition completeness. The original input schemas remain the validators.

type Reply<T> =
  | { ok: true; value: T; completeness: 'complete' | 'partial' | 'unknown' }
  | { ok: false; error: { code: string; message: string } };
interface ScriptTools {
  readonly run_shell_command: (args: {
    command: string; dir_path?: string; description?: string;
    timeout_seconds?: number;
  }) => Promise<Reply<{ stdout: string; stderr: string; exitCode: number }>>;
  readonly read_file: (args: {
    absolute_path: string; offset?: number; limit?: number;
  }) => Promise<Reply<{ text: string }>>;

The model first obtains those declarations and their revision, then submits the source below with language: "javascript", tools: ["run_shell_command", "read_file"], the returned api_revision, and a purpose. For that preset, the changed-file list can be gathered by a direct, approved tool call before running a script.

One script replaces the mechanical model turns#

This is one illustrative model-written program, not repository implementation code. It fails on ambiguous acquisition instead of treating missing data as an empty answer. It quotes filenames, validates commit IDs before placing them in commands, and never asks the guest for filesystem or process access. Each tools call still crosses the host policy boundary. The broker's call and byte budgets apply to the whole run.

const root = '/workspace/demo';
const problems = [];
const evidence = [];
const snapshots = new Map();
const quote = value => "'" + value.replaceAll("'", "'\\''") + "'";

function complete(reply) {
  if (!reply.ok) throw new Error(reply.error.code + ': ' + reply.error.message);
  if (reply.completeness !== 'complete') throw new Error('INCOMPLETE_ACQUISITION');
  return reply.value;
}
async function git(command) {
  const value = complete(await tools.run_shell_command({
    command, dir_path: root, description: 'Gather TODO ownership evidence',
  }));
  if (value.exitCode !== 0) throw new Error('GIT_FAILED: ' + value.stderr);
  return value.stdout;
}
const head = (await git('git rev-parse HEAD')).trim();
if (!/^[0-9a-f]{40,64}$/.test(head)) throw new Error('INVALID_HEAD');
const shallow = (await git('git rev-parse --is-shallow-repository')).trim();
if (shallow !== 'false') problems.push({ reason: 'shallow-history' });
const commits = (await git('git rev-list --max-count=10 ' + head))
  .trim().split('\n').filter(Boolean);
if (commits.length < 10) problems.push({ reason: 'fewer-than-ten-commits' });
const paths = new Set();
for (const commit of commits) {
  if (!/^[0-9a-f]{40,64}$/.test(commit)) throw new Error('INVALID_COMMIT');
  const names = await git('git diff-tree --root -m --no-commit-id ' +
    '--name-only -r -z ' + commit);
  for (const path of names.split('\0').filter(Boolean)) {
    if (path.startsWith('/') || path.split('/').includes('..')) {
      throw new Error('UNEXPECTED_PATH');
    }
    paths.add(path);
  }
}
let filesScanned = 0;
for (const path of [...paths].sort()) {
  const reply = await tools.read_file({ absolute_path: root + '/' + path });
  if (!reply.ok) {
    problems.push({ path, reason: reply.error.code });
    continue;
  }
  const file = complete(reply);
  snapshots.set(path, file.text);
  const todoLines = file.text.split('\n')
    .map((text, index) => ({ line: index + 1, text }))
    .filter(row => row.text.includes('TODO'));
  filesScanned += 1;
  if (todoLines.length === 0) continue;
  const blame = await git('git blame --line-porcelain -- ' + quote(path));
  const authors = new Map();
  let line = 0, author = '', uncommitted = false;
  for (const row of blame.split('\n')) {
    const header = /^([0-9a-f]{40,64}) (\d+) (\d+)(?: \d+)?$/.exec(row);
    if (header) {
      line = Number(header[3]);
      author = '';
      uncommitted = /^0+$/.test(header[1]);
    } else if (row.startsWith('author ')) {
      author = row.slice(7);
    } else if (row.startsWith('\t')) {
      authors.set(line, uncommitted ? 'uncommitted' : author);
    }
  }
  for (const row of todoLines) {
    const owner = authors.get(row.line);
    if (!owner) throw new Error('MISSING_BLAME_AUTHOR');
    evidence.push({ owner, path, line: row.line, text: row.text.trim() });
  }
}
for (const [path, before] of snapshots) {
  const after = complete(await tools.read_file({ absolute_path: root + '/' + path }));
  if (before !== after.text) throw new Error('WORKSPACE_CHANGED');
}
if ((await git('git rev-parse HEAD')).trim() !== head) throw new Error('HEAD_CHANGED');
const owners = [...new Set(evidence.map(row => row.owner))].sort().map(owner => ({
  owner,
  count: evidence.filter(row => row.owner === owner).length,
  locations: evidence.filter(row => row.owner === owner)
    .map(row => ({ path: row.path, line: row.line, text: row.text })),
}));
return {
  ownership: 'current-line Git blame author',
  commitsExamined: commits.length, filesScanned, todoLines: evidence.length,
  complete: problems.length === 0, problems, owners,
};

The reread detects changes between observations; it does not provide an atomic workspace snapshot. A product promising snapshot consistency needs an additional snapshot contract. This example also expects paths representable by the text transport. It deliberately errors on clipped file or blame output instead of adding a speculative text parser. Pagination, non-text files, unusual encodings, and budgets require explicit coverage handling before using this recipe on arbitrary repositories. Host-owned partial/error metadata accompanies the result regardless of what the guest returns.

The same task delegated to a cheap model#

Here cheap-research is a proposed configured subagent name, not a claim that this machine has that profile installed. The profile must explicitly select a cheaper model. The task schema selects a named agent; it does not make an arbitrary agent cheap by itself. A worker may still need a more capable model if it cannot use the tools or preserve evidence accurately.

Child turn Child action Context affected
1 Resolve HEAD, the history window, and shallow state using run_shell_command. Child receives commit IDs. Parent retains only its task call.
2 Batch changed-path queries, deduplicate the returned paths. Child receives path lists.
3 Read the three files; use further reads if any producer reports clipping. Child receives file text.
4 Blame matching lines/files; interpret uncommitted ownership. Child receives authors and blame metadata.

The semantic payload returned to the parent can be the same compact JSON above plus the evidence array. The actual task result includes its ordinary completion wrapper; this dossier does not invent a replacement wire envelope. The child's intermediate transcript stays separate, while its provider requests and tokens still count toward total use. A worker could miss a file or compress away uncertainty; explicit output fields and source locations make that easier to detect but do not guarantee correctness.

A child using code mode can perform the mechanical reads and joins in a script, then interpret the resulting evidence in its own model turn. That composition preserves the reason to delegate semantic work while avoiding needless model handling of repeated raw data. The proposed initial broker disallows nested task calls, so composition starts by delegating a child that has its own code-mode capability. It does not allow a script to spawn arbitrary model workers.

Survey conclusions and evidence limits#

Code mode moves loops, joins, filtering, and other tool orchestration into an execution environment. It can keep large intermediate payloads out of the model's context and avoid having the model copy data between calls. Tool discovery can be made lazy at the same time, but these are separate optimizations. Cloudflare's September 2025 article initially loaded the entire generated API; its current SDK adds discovery and a durable approval runtime. Anthropic's November 2025 MCP article describes filesystem-based discovery, while its current API offers a hosted Python implementation with a pause/resume protocol. CF25 CF-DURABLE A-MCP A-PTC

Adoption is broader than older surveys suggest. Pydantic AI Harness, Cloudflare, Anthropic's API, smolagents, Goose, OpenCode, Amp, Pi, UTCP, and pctx have documented implementations. Codex has a dedicated V8 code-mode host in current source, but the principal code_mode flag remains under development and off by default in the inspected snapshot. Claude Code announced an experimental opt-in JavaScript Code Mode on November 12, 2026, one day before this report; its linked documentation was unavailable during research. Gemini CLI, Cursor, and Cline have no native implementation verified in the reviewed primary sources. Their ability to connect to a code-mode MCP proxy is a separate matter. AI-DOC CODEX-FEATURES CC-RELEASE GEMINI CURSOR CLINE

Pydantic's October 28, 2026 internal benchmark reports 5,276 graded runs across eight models, with reported long-task reductions of 58% in cost and 51% in wall time. Those results used CodeMode(eager=True) and narrow CRUD applications, not arbitrary coding work. In that comparison, native tool calling already batched many independent calls, so request-count reductions were much smaller than cost reductions. Large savings came from context and generated-call-token reductions. This is vendor evidence, not independently reproduced evidence. AI-BENCH

Code mode and a cheap research subagent are complementary. A program can fetch 500 records and compute an exact aggregate without another model reading every record. A subagent can investigate an unfamiliar subsystem, interpret ambiguous evidence, and return a focused account. Both reduce the parent's context, but only delegation adds another reasoning context. No credible, controlled head-to-head benchmark comparing code mode with an otherwise equivalent cheap retrieval subagent was found in the reviewed sources. The available research supports workload-specific choices, not a universal winner. A-MULTI CC-SUB CODEACT

1. Definitions and scope#

For this report, code mode has three parts:

  1. A model-facing program surface, such as run_code, execute, or exec, in which generated code can invoke existing agent tools.
  2. A runtime and bridge that execute that program and dispatch calls to the real tools.
  3. An output boundary through which only selected results, errors, or artifacts reach the model.

Discovery is optional: functions can be described upfront, searched in a catalog, or represented as files. MCP remains the connectivity layer in many implementations. A code-mode wrapper changes how the model orchestrates calls; it does not require replacing the underlying MCP servers. Cloudflare's original post and FastMCP's server transform both make this distinction concrete. CF25 FASTMCP

A shell tool alone does not establish code mode. It might permit a model to write a script, but it does not necessarily expose the agent's existing tools as callable functions with preserved policy checks. Similarly, tool search alone changes definition loading, not execution. Roo's product mode named “Code” is a coding role, which does not by itself imply this pattern. A-SEARCH ROO

Native parallel calling is a valid baseline. Some explanatory articles describe ordinary tool calling as necessarily one call per model turn. That is too restrictive. Pydantic's measured baseline emitted as many as 200 calls in one response. Code mode additionally expresses dependent computation and dataflow between calls without another inference, and can suppress intermediate payloads. AI-BENCH

2.3 Async execution and policy#

Monty supports the async subset needed for this use case. await asyncio.gather(...) fans out host tool calls; the executor resolves pending external futures and returns their results to the interpreter. This is not a complete CPython event loop. In particular, the model-facing instructions say not to use gather keyword arguments or other task-creation/wait APIs. 10. Criticisms, failure modes, and tradeoffs#

Security and authorization#

The tool bridge grants authority. A program without sockets can still exfiltrate through a permitted “send message” tool or mutate production through an allowed API. Keeping credentials outside the isolate prevents direct credential reads only if tools/results do not re-expose them. The host must authorize the operation and arguments independently of the generated code. Monty's security docs explicitly discuss callback authority; OpenCode says authorization belongs in tool execution; Anthropic warns that caller hints are not a security boundary. MONTY-SECURITY OC-README A-PTC

Per-call approval can be lost, but need not be. If a host approves only the outer execute, a loop can perform many writes after one prompt. Goose preserves its permission flow; Amp remote tools can pause on each operation; Cloudflare's durable runtime pauses/replays; Pydantic routes through ToolManager but requires inline deferral handling. A deployment should test its actual bridge rather than assume either complete bypass or complete preservation. GOOSE-DOC AMP-MCP CF-DURABLE AI-CODE-TOOLS

Language isolation, process isolation, and OS isolation differ. Monty/OpenCode deliberately interpret a limited language; V8/QuickJS/Boa provide different VM boundaries; full CPython in IPython has host authority; UTCP Python's thread execution is not a disposable restricted process. Red Hat's Pyodide bridge incident shows that a seemingly isolated language can regain ambient host capabilities through imports. These facts justify reviewing exposed bridges and callback implementations, not just the runtime's brand. MONTY-SECURITY OC-README UTCP-PY AI-IPYTHON REDHAT

Context privacy has a narrow meaning. Not sending rows to the main model can reduce exposure and prompt-injection surface, but runtime logs, error traces, provider containers, tool providers, and returned summaries may still contain the data. Claude's current hosted execution retention is a concrete counterexample to “not in context means never sent to the provider.” PII replacement and destination allowlists are separate mechanisms. A-MCP A-PTC A-EXEC

Reliability, schemas, and debugging#

Weak models can write bad programs. Failures include invented identifiers, invalid imports, unsupported syntax, forgotten awaits, incorrect result fields, and code that is syntactically valid but filters away the relevant evidence. Red Hat reports exact tool-name mistakes with a smaller model; CodeAct's results vary by model; FastMCP's author reports more mistakes from Haiku-class than Sonnet-class models in early use. These are observations, not a universal parameter-count cutoff. REDHAT CODEACT FASTMCP

Type generation is only as useful as its contracts. JSON Schema recursion, union/null handling, invalid language identifiers, names colliding after sanitization, missing output schemas, and text/structured/multimodal responses all affect the generated surface. Goose deliberately returns original recursive JSON schemas. Pydantic checks sanitized-name conflicts and generates stubs. OpenCode separates schema rendering from Effect runtime decoding. Amp distinguishes structured replies from text. Static types cannot repair a wrong server schema or authorize a side effect. GOOSE-DOC AI-CODE-TOOLS AI-TOOLSET OC-README AMP-MCP

The MCP repository's November 2025 discussion raises output-shape brittleness and argues that execution strategy is above the protocol. Its historical claim that output schemas were not standardized should not be repeated as a current fact: current Amp/Goose/MCP implementations explicitly support output schemas. The lasting criticism is incomplete or unenforced output contracts. MCP-DISCUSSION AMP-MCP GOOSE-DOC

Completed side effects survive partial failure. A program may update records 1–19, fail on 20, and then be retried by the model. Whole-script retries can duplicate effects. Pi documents surviving prior side effects; Amp warns to check whether the operation already ran; Pydantic records started calls even when a budget failure interrupts the snippet; Cloudflare's optional replay/compensation addresses parts of the problem but is not a cross-service transaction. PI AMP-MCP AI-TOOLSET CF-DURABLE

Debugging requires nested traces. A single outer call can hide many operations from a simplistic transcript. Capture program text, discovered contracts, each nested tool/argument/outcome, policy decisions, cancellation, and relevant artifact references. Pydantic, Goose, OpenCode hooks, and Codex have explicit nested-call plumbing; a custom wrapper must not assume the model-facing final output is an adequate audit log. This is a design recommendation grounded in those implementations. AI-CODE-TOOLS GOOSE-EXEC OC-README CODEX-DELEGATE

Latency, cost, and resource use#

Discovery, generation, type checking, sandbox startup, data marshaling, and recovery can make a one-tool lookup slower and more expensive. For large independent calls, ordinary parallel invocation may already achieve much of the latency gain. A script can reduce inference overhead while leaving network/service latency unchanged, and unbounded fan-out can overload services or hit quotas. Model requests, tool requests, input/cache/output tokens, and wall time should be measured separately. AI-BENCH A-PTC REDHAT

Limits are not interchangeable. Monty distinguishes execution from suspended time; Claude has a cell limit and a pending-tool deadline; Pi's optional script timeout differs from worker-queue limits. Host calls need cancellation/deadlines even when the language heap is bounded. Otherwise a cheap-looking loop can become an expensive or stuck tool workload. MONTY-SECURITY AI-TOOLSET A-PTC A-EXEC PI

When ordinary tools are preferable#

Direct tools are often preferable for one or two small operations, tasks where the model must interpret every intermediate result, high-risk writes that need an easily reviewed individual request, or models that cannot reliably use the code surface. They also avoid maintaining a new interpreter/bridge when the existing tool schema is already compact. A well-designed bulk/search/aggregation endpoint may remove the need for generated orchestration altogether. The first cases are documented by Anthropic/Goose/Red Hat; the bulk-endpoint observation is an architectural inference, not a benchmark claim. A-PTC GOOSE-DOC REDHAT

11. Code mode versus “send a cheap subagent to gather context”#

11.1 What the published sources establish#

Anthropic's June 13, 2025 multi-agent research article describes an Opus 4 lead with Sonnet 4 workers and reports 90.2% better performance than a single Opus 4 on its internal research evaluation. It attributes gains to parallel exploration and additional context windows. This is a useful real-system account but does not isolate topology from model mix and compute. Sonnet workers in that setup are not evidence about an arbitrarily small/cheap retrieval model. A-MULTI

The same article says agents use about 4× chat tokens and multi-agent systems about 15× chat tokens. The denominator is chat, not 15× a single agent. It favors breadth-first, relatively independent research and says tightly interdependent coding tasks are a poorer fit. Token usage explaining much of benchmark variance is observational evidence about effort, not proof that simply spawning more agents causes better answers. A-MULTI

Claude Code's current subagent docs directly recommend delegating side work that would flood the main context. Each worker has its own context, prompt, tools, and permissions; its requests still count toward usage. A custom agent can choose a cheaper model. However, current built-in Explore is not universally Haiku: its documented model selection is now parent/provider-dependent, and a custom Explore with model: haiku is one route to explicitly cheaper exploration. Amp's current Task documentation likewise says it uses the thread's model and effort. Delegation does not automatically imply a cheap model. CC-SUB AMP-TOOLS

Cognition's Walden Yan, June 12, 2025, argues against multi-agent designs that split interdependent work without shared context, because actions contain implicit decisions that summaries lose. It favors shared context/full traces and compression. This is a maintainers' design argument with examples, not a controlled proof against all delegation; its references to then-current Claude Code do not define today's product. The concern remains relevant when a worker silently chooses assumptions the parent does not receive. COGNITION

A simple cost model explains why “cheap” is not sufficient:

Program route = main-model program tokens + selected-result tokens
                + runtime/tool cost + expected repair cost

Worker route  = parent delegation/result tokens
                + worker input/output/reasoning at worker prices
                + runtime/tool cost + expected rework/escalation cost

This is an accounting model, not a measured estimate. Include prompt-cache rates, retained state, tool/service charges, and failed attempts. A worker that reads everything can consume more total tokens while still costing less money; a program that emits a huge table can fail to save parent context. AI-BENCH A-MULTI CC-SUB

11.3 Which approach to choose#

For “fetch every open issue, group by label, return counts and the IDs of unassigned blockers,” code mode has a natural exact-data path once the API contract and blocker definition are known. A small worker adds little value to the counting operation. For “find why this authentication behavior differs between two code paths,” a worker can make relevance decisions and follow unfamiliar dependencies that a short fixed program cannot infer. The program can still gather candidate files and compress mechanical output for that worker. These are workload judgments, not claims of measured superiority. A-PTC CC-SUB COGNITION

The patterns compose at several levels:

  • A worker can use code mode to search, filter, and aggregate before doing semantic analysis.
  • A parent's generated program can invoke a tool that represents a bounded worker, provided the host authorizes that tool and the implementation allows it.
  • Programs can return IDs, file paths, source spans, or structured evidence; the parent or worker can then reason over only the relevant material.

smolagents exposes managed-agent callables; Amp's plugin API can register a tool backed by a custom agent; Anthropic's research system used artifact references to reduce lossy handoffs. Conversely, Pi's models surface explicitly does not run chat models, showing that composition must be checked against the actual product interface. SMOL-SOURCE AMP-PLUGIN A-MULTI PI

11.4 A useful evaluation design#

Before selecting a default, compare four arms on the same tasks and tools: direct tool calling with native parallelism; direct plus deferred search; code mode; and a deliberately cheap worker. Add a worker-with-code-mode arm if composition is the intended design. Hold tool permissions, output budgets, and success criteria fixed. Record task success, omitted evidence, main-context growth, total/cache/output tokens by model, tool calls, wall time, policy prompts, partial side effects, and repair/escalation cost. This is a proposed test plan, not an experiment performed here.

Include small lookups, paginated structured queries, large-result filtering, ambiguous repository research, malformed output schemas, unsupported syntax, and a write that fails halfway through. These cases discriminate the mechanisms identified in Pydantic's scaling study, Red Hat's failures, current approval implementations, and the subagent literature. AI-BENCH REDHAT CF-DURABLE A-MULTI COGNITION

A2. Declaration, registration, and schema publication#

Definition and invocation are separate objects. DeclarativeTool<TParams,TResult> implements ToolBuilder; it carries name, description, kind, parameter schema, display properties, and build. Its schema getter memoizes a neutral function declaration by parameter-schema identity. BaseDeclarativeTool.build calls schema validation through SchemaValidator, custom value validation, then createInvocation. BaseToolInvocation supplies the shared invocation behavior; concrete invocations implement execution. ToolResult contains llmContent, returnDisplay, optional metadata, error, and display suppression. It has no general typed programmatic output field or output-schema contract. T1

buildAndExecute and validateBuildAndExecute are convenience methods on DeclarativeTool. They build and execute directly. They are not scheduler entrypoints and must not be used by a code-mode broker to dispatch nested work. T1

Registration is composed rather than globally static. createToolRegistry registers filesystem/search/edit/AST tools, shell, memory/todos, web tools, optional GitHub operations, image operations, and agent-related tools. Core injects host capabilities through adapters. Task implementation is supplied through TaskToolRegistration, avoiding a core-to-agents implementation dependency. The factory records disabled/missing registrations and honors configured builtin inclusion/exclusion. T3

ToolRegistry stores tools in a map, normalizes names for registration/lookup, injects ToolContext into context-aware tools, and checks live governance for lookup and schema publication. getAllTools/getAllToolNames are inventory, not permission-filtered discovery APIs. getEnabledTools is the appropriate starting point for an authorized index. getFunctionDeclarations applies schema transforms and lazy-MCP deferral; getFunctionDeclarationsFiltered(names) applies governance/transforms but does not impose that same deferral. T2

Command discovery is a separate registry path: discoverAllTools invokes the configured command, parses declarations, and installs DiscoveredTool instances under the discovery prefix. A DiscoveredTool invocation invokes its configured command with JSON parameters. It is not an in-process typed API already suitable for arbitrary scripts. T2

Session wrapping matters. SessionToolCatalogOwner.selection exposes the ToolSelection structural interface. Its initialization constructs session builtins with workspace discovery handled elsewhere, and its resolution/definition paths combine workspace and builtin tools. MCP tools receive session approval rebinding. ToolDispatchAdmission guards accepted operations and retained callbacks against closed lifetimes, combines abort signals, and joins accepted work when closing. Code mode must retain this behavior rather than returning raw tools into a long-lived guest context. T4-T6

A5. Isolation and credential boundaries#

The existing CLI sandbox runs the CLI, not a secret-free tool program. start_sandbox selects runSeatbeltSandbox or runContainerSandbox. loadSandboxConfig recognizes Docker, Podman, and macOS sandbox-exec. buildContainerRunArgs mounts the workspace, global config directory, and session temporary directory, configures network/resource settings, and permits additional user flags. These are suitable composition points for an interactive coding environment, not defaults to copy into a no-authority code runner. A2-A4

Container credential setup starts a host credential proxy and passes LLXPRT_CREDENTIAL_SOCKET plus a capability token using an environment file kept outside mounted paths. ProxySocketClient authenticates the channel; ProxyProviderKeyStorage.getKey invokes get_api_key. CredentialProxyServer.handleGetApiKey deliberately returns the actual credential for known names, including sandbox connections. The capability authenticates access to credentials; it is not an operation-only tool capability. Never pass this socket, token, client, or provider storage to script code. A1, A5

Seatbelt setup removes credential-proxy transport markers but starts from the parent environment. ShellExecutionService uses PTY or child_process; it owns process-group cancellation and output collection. Its sanitizer returns the full environment outside sandbox/CI and allows LLXPRT_* variables inside sandbox/CI. Consequently, neither a normal shell invocation nor its environment sanitizer establishes the proposed no-credentials boundary. A6, A8

Reusable pieces are bounded acquisition primitives (ByteBudget, BoundedStreamCollector), cancellation/join ownership patterns, and carefully reviewed IPC framing concepts. The existing framing module provides length-prefixed frames and finite frame bounds, but the new channel should have a distinct, smaller operation protocol. Do not reuse the credential client's operation dispatcher or ambient socket discovery. A9, S8, T5

“No credentials” means no runtime credential provisioning, ambient authority, or credential retrieval API in the guest. It cannot mean “no sensitive data can ever appear”: an authorized read tool may return a repository secret, and an authorized shell command may print host environment data. The first release should expose a selected read-only set, with filesystem access still governed by existing tool policy. Strong data-loss prevention would be a separate product contract.

Proposed llxprt design#

B1. Feature boundary and dependency direction#

Add two ordinary model-facing tools:

  • discover_tool_api: paginated search/index plus explicit description of selected enabled tools. Return short descriptions, generated declarations, result-format information, and an API revision. It must not execute tools or authorize use.
  • execute_tool_script: accepts language, source, tools, api_revision, and a short purpose. tools is an exact list of requested capabilities, never an authorization grant. The list is intersected with feature eligibility and caller authority; unavailable requested names cause a preflight error rather than silent removal.

Implement the execution tool and run owner in packages/agents, following the existing agent-owned task/tool pattern. Extend factory injection in core and session catalog composition; do not add an import from tools or core into agents. Put schema projection and neutral programmatic data contracts in packages/tools. Keep the QuickJS adapter private to the agent execution implementation until there is an actual second consumer. No new workspace package is needed initially. T1-T6, G1

Separate what is advertised from what is authorized. In compact mode, model requests advertise the two new tools plus a small set of direct control tools. The broker still resolves ordinary tools through the full admitted selection. Hiding a declaration must not remove the underlying tool from authorization, and advertising a meta-tool must not grant every nested tool. Preserve tools.allowed, tools.disabled, excludeTools, task whitelist restrictions, and any parent hook restriction independently. Existing governance and declaration-selection seams are the integration points. T2, T4, S2, C2

First release: opt-in, selected read-only builtin tools only, no remote tools merely because they claim to be read-only. No task, execute_tool_script, todo_pause, settings/auth/approval control, or background shell jobs inside scripts. No recursive meta-tool dispatch. Ordinary direct tools remain available as a model-selected alternative after a failed script, never an automatic runtime fallback.

B3. API projection and progressive disclosure#

Generate declarations from session-visible registered schemas, not provider-converted schemas. Provider conversion can discard expressiveness for wire compatibility. Use an exact name map and string-literal property names, for example tools["read_file"](...); do not splice MCP names into executable identifiers. Escape descriptions as data/comments and limit description size. Remote descriptions remain untrusted text.

Proposed declaration shape:

type JsonValue =
  | null | boolean | number | string
  | readonly JsonValue[]
  | { readonly [property: string]: JsonValue };

type ScriptToolResult<T extends JsonValue = JsonValue> =
  | {
      readonly ok: true;
      readonly value: T;
      readonly completeness: 'complete' | 'partial' | 'unknown';
      readonly nextCursor?: string;
    }
  | {
      readonly ok: false;
      readonly error: {
        readonly code: string;
        readonly message: string;
      };
    };

interface ScriptTools {
  readonly read_file: (
    args: ReadFileArgs
  ) => Promise<ScriptToolResult<TextReadResult>>;
}

ReadFileArgs is generated from its real input schema. TextReadResult requires an explicit, tested host adapter or a new structured tool result; it cannot be inferred from input properties. Existing generic tools initially return a text envelope, with completeness unknown unless the producer supplies evidence. Never parse a human display string and pretend it is an authoritative structured result.

Schema projection supports objects, required/optional properties, additional properties, arrays, enum/const, unions, and local references. Unsupported constraints remain in the host JSON Schema validator and are documented; unresolved or unsupported type fragments project to unknown with a diagnostic rather than a falsely precise type or any. No remote $ref fetching. Recursive local schemas use named types with bounded generation. Generated declarations provide model guidance; the original schema remains the execution validator. T1

discover_tool_api searches getEnabledTools through session admission, with a bounded page of names/descriptions. A describe operation returns selected declarations and a revision hash over names, schemas, programmatic adapters, and relevant feature settings. This does not activate unauthorized MCP servers. Integrate existing lazy-MCP publication deliberately rather than assuming all registered tools are advertised. T2, T4

Bind the described tool identities and schema revision at script admission. Each call rechecks live availability/policy, so disablement or session closure takes effect mid-script. A changed implementation/schema fails that call as API_CHANGED; it is not silently replaced with another tool. Adding an unrelated tool need not invalidate a running script. Bound discovery results, declarations, schema depth, and the host cache by bytes/items, not just tool count.

These signatures omit concrete config/bus/provider objects intentionally. Limits and identity are bound by the run owner's constructor, not accepted as guest overrides. The transport uses discriminated call, result, log, complete, and failure frames with protocol version, run ID, and monotonically assigned request ID. The host creates actual tool-call IDs and parent links. Guest-supplied policy identity, agent ID, server name, paths to credential sources, or approval outcomes are not protocol fields.

Add an explicit per-invocation execution context at the scheduler-to-invocation boundary. The existing invocation execute parameters do not carry the parent call ID, prompt ID, or hook-restriction set; ToolContext supplied during lookup is not a complete execution scope. Extend the neutral tools contract with immutable provenance and a host-only nested-execution port, assembled by the agents scheduler owner with the current hook owner and approval handler. The meta-tool must fail if that scope is missing. Do not infer its parent from a shared mutable tool instance, a global current-call variable, or guest-supplied IDs. This is a required extension to ToolInvocation/ToolExecutor composition, not functionality already provided by registry lookup. T1, S2, S4, S7

Do not recurse into the active parent scheduler. It queues new work while a tool is executing; the parent execute_tool_script would wait on a child queued behind itself. Instead, a CodeModeRunOwner creates a separate TurnToolExecutionOwner and SessionSchedulerOwner with the same admitted selection/policy and the parent's interactive status. This mirrors existing child execution ownership without allocating a second model/history/provider. S1, S8-S10

The broker constructs a normal ToolCallRequestInfo, preserves prompt/agent identity and inherited restrictions, and dispatches through its lease. The child completion callback resolves the corresponding guest promise. It must wait for terminal completion, not merely for schedule() to return: interactive scheduling can return with calls awaiting approval. L2, S3

Initially serialize nested calls through one FIFO broker, even when the guest uses Promise.all. Place queued calls in the broker; do not submit a new scheduler batch while the previous batch is active. This avoids relying on scheduler reentrancy or queue behavior and gives predictable side-effect order. Enforce finite outstanding requests, count, and cumulative bytes at acceptance. Promise jobs must be pumped after each response and in bounded slices so cancellation and transport progress cannot starve.

A script returning while host requests are still pending fails with UNAWAITED_TOOL_CALLS: close admission, cancel queued requests, abort/join accepted work, and report any completed effects. It must not publish success and leave work running. Duplicate/out-of-order IPC request IDs fail the run rather than replaying a tool call. An ordinary tool error that the script intentionally handles remains visible in the host-owned summary; the guest cannot erase policy failures, partial-acquisition flags, or unfinished work by returning a custom object.

For a later concurrency phase, drain an admitted wave into one scheduler batch and retain its mutation ordering. Do not create one unrelated scheduler per parallel call. Before enabling nested mutations across parent/client/subagent schedulers, extract shared workspace execution arbitration: ordinary overlapping file mutations must keep their ordering across owners, and opaque shell/MCP mutations require an exclusive lane. The orchestration meta-tool must not hold a mutation lease while awaiting its children. Keep this out of the read-only MVP, but make it a prerequisite for write-capable release. Existing ordering is within a scheduler batch. S1, S11

B5. Policy and confirmation semantics#

The execution contract is:

feature eligibility + caller governance + request allowlist
  -> resolve/build through admitted selection
  -> prepare effective hook-adjusted invocation
  -> evaluate existing policy for concrete tool and effective arguments
  -> existing confirmation if required
  -> execute exact authorized invocation
  -> hooks/result processing
  -> guest response and audit event

A declared allowlist only limits names. It cannot safely preapprove future loop-generated arguments. The recommended interaction is pause at each nested call requiring approval. The guest awaits a promise while the existing UI displays the real tool, effective arguments/diff, originating script, parent call ID, and progress. A script-level approval allows starting the program, not bypassing child confirmations. Existing explicit user “always allow” choices retain their ordinary scope; code mode creates no blanket allow rules.

Use a child TurnToolExecutionOwner.begin() subscription so nested IDs are owned and approval requests reach the actual approval handler. The parent owner currently admits only IDs scheduled through its own lease; merely sharing its message bus is insufficient. Retire the child subscription on all exits and discard late replies. Headless execution returns an explicit approval-required/denied failure instead of waiting for a nonexistent UI. S3, S9

Hook ordering must be made explicit before shipment. The inspected ToolExecutor.execute runs BeforeTool after scheduler policy/approval, rebuilds input, and does not visibly re-evaluate policy there; rebuild errors warn and retain the prior invocation. This dossier does not assert an exploit or diagnose the full hook trust model. It does establish that “we reuse the scheduler, therefore the final arguments were checked” is too strong. Add tests for effective-argument authorization, then move input preparation into a shared scheduler step before policy evaluation. A changed/invalid hook input must fail or be reauthorized, never silently execute a different invocation. Do not add a code-mode-only policy check alongside the existing one. S3-S4

Approval edits also require validation/authorization of the final invocation. Avoid rerunning BeforeTool after approval, which could produce another mutation or duplicate a hook side effect. Carry an immutable prepared invocation and its effective arguments through execution. Apply the same contract to normal and nested calls.

DENY, user cancellation, revocation, and runtime/budget violations terminate the run and reject pending guest requests. Ordinary tool failures can return {ok:false,...} for explicit script handling. Policy failure cannot be caught in guest code to continue making unrelated calls. Completed external side effects are not rolled back; the final failure includes a bounded list of completed call IDs/statuses and states that execution may be partial.

B6. Output, budgets, cancellation, and data lifetime#

Add a scheduler result-delivery seam. ResultAggregator.publishResult currently formats ToolResult.llmContent for the model. Add a typed completion payload or sink exposing a bounded, post-hook programmatic value before model-token formatting. Normal execution keeps the existing model result path. Script execution resolves its broker response from this new sink while retaining ordinary status, policy, hooks, telemetry, and UI callbacks. Do not reconstruct data from responseParts after truncation. S4-S6

Extend ToolResult with a neutral optional programmatic result, explicit completeness, and producer truncation metadata. Preserve useful MCP structuredContent and optional output schemas explicitly; otherwise return a documented text envelope. Output-affecting hooks must apply consistently to the programmatic channel. If a hook supplies only replacement text, invalidate the typed value and return the replacement text envelope; never expose a hidden pre-hook result. Binary/media responses use bounded metadata or opaque host-owned references in a later phase, not full image/audio bytes in the initial guest.

Existing acquisition limits stay in force. Skipping the model-token limiter for intermediate values does not undo truncation already performed by a tool or its acquisition layer; shell retention and MCP result bounds are concrete inspected examples. Selected tools need pagination/completeness contracts to support exhaustive scripts. A claim such as “every TODO” is invalid when a producer reports partial or unknown coverage. A6, A9, M2, S6

Proposed initial finite defaults, to validate with measurements rather than treat as performance claims:

An over-limit final value returns a small explicit RESULT_TOO_LARGE error; do not silently cut JSON in the middle or fabricate a successful partial answer. Intermediate oversize results require narrower/paginated calls. Serialize incrementally with depth and byte checks; cyclic values, unsupported values, non-finite numbers, and malformed frames fail with a bounded diagnostic. These checks handle genuinely untrusted data and are not speculative fallback layers.

On cancellation or deadline: close broker admission; abort the child scheduler signal and in-flight host call; interrupt/terminate the wrapper; cancel outstanding confirmation routing; join accepted real executions; close pipes and dispose interpreter handles. cancelAll alone is insufficient because the scheduler explicitly tracks real executions separately from its prompt cancellation result. No persistent VM/session filesystem and no script-resume facility in the first version. Do not automatically replay a failed script: a previous call may already have changed external state. Recovery is a new model/user decision with the recorded completion summary.

B9. Proposed class diagram#

Every new class below is a proposed contract. The existing base classes and scheduler owners are reused; the typed completion sink and immutable execution scope are new extensions. The runtime adapter deliberately has no registry, policy, provider or credential dependency.

The interpreter interface earns its cost by separating untrusted execution from host policy and allowing protocol/lifecycle testing. The catalog exists because disclosure, revision binding, and schema projection share actual state. Do not introduce a generic plugin framework, workflow DSL, distributed execution service, or multiple runtime implementations for hypothetical future users.

B12. Risks, decisions, and remaining product questions#

Implementation decisions already made: JavaScript guest first with TypeScript declarations; QuickJS-WASM only; dedicated process; no credential channel; session-admitted registry; sequential broker initially; child scheduler rather than parent reentrancy; per-call approvals; one model response; separate operational records; explicit structured outputs and completeness; no recursive scripts/tasks; no automatic retry or fallback.

Engineering risks with defined next steps:

  • Hook/effective-argument gap: write policy-parity tests and correct the shared preparation stage before enabling the feature. Do not certify final-argument authorization from source inspection alone. S3-S4
  • Early output truncation: measure selected producers and add explicit pagination/completeness contracts. A higher guest byte budget cannot repair already truncated output. S6, A6, M2
  • Reentrant scheduling/deadlock: separate run owner and sequential admission; test completion callbacks rather than assuming scheduling completion means execution completion. S1, S8-S9
  • Concurrent mutation scope: existing path ordering is batch-local. Require shared arbitration before write concurrency. S1, S11
  • Interpreter distribution: prove package assets, supported OS launch behavior, Bun execution, and cleanup with the exact pinned dependency. No runtime switching if unavailable.
  • Sensitive data through permitted tools: keep runtime provisioning credential-free; document that approved tool results can contain secrets. Read-only is not equivalent to confidential-data-safe.
  • Prompt injection in schemas/tool results: descriptions remain untrusted, host policy remains authoritative, no guest access to approval/configuration controls.
  • Persistent logs replacing context bloat: byte-bound transcripts/events and avoid raw intermediate persistence. Existing telemetry metadata must not become a second path around prompt privacy. H3
  • Result accuracy: expose partial/unknown coverage; validate deterministic aggregation against direct tools. Never infer full coverage from successful process exit.

True product-direction questions, with recommended defaults so implementation need not wait:

  1. Is broad write/network automation a launch goal? Recommend shipping read-only opt-in first. If broad automation is required at launch, Phase 4 ownership/arbitration and approval tests become release requirements rather than follow-on work.
  2. Should ordinary tool schemas disappear by default? Recommend alongside during evaluation, then offer compact explicitly. Default replacement should follow comparative evidence for the actual supported models.
  3. Does the product require protection against a compromised interpreter/runtime, or isolation within a trusted interpreter? This design assumes a trusted WASM runtime and audited bindings. If an OS-level boundary against runtime compromise is mandatory, require a distinct no-mount/no-network runner container profile and accept its deployment requirements; do not imply that a scrubbed subprocess already supplies that guarantee.
  4. How much nested data should remain inspectable after the run? Recommend bounded operational records and excerpts, with no raw intermediate persistence by default. Full evidence retention would require a separate storage/privacy budget and user-visible setting.
