Revision notes — read these before the rest of the document.

Rev.1 → Rev.2 (storage). A single file rotated on an in-process byte counter cannot bound a shared file across concurrent instances. Measured under 8 writers: ceiling breached 1.5×, 49% of records destroyed. Corrected in §06.

Rev.2 → Rev.3 (the measurement model itself). Review found the headline arithmetic algebraically invalid. A provider request’s wall duration contains our stream handling and Ink rendering, so llxprtMs = turnBusy − agentActive subtracts away the very work it claims to measure, and coreMs = llxprtMs − uiMs can go negative on an ordinary sequential turn. Provider/tool figures are also sums while the residual is a union, so the three were never a partition. §02’s waterfall is retained below only as a record of the rejected model — see the correction immediately after it. PLAN.md carries the replacement: directly measured client phases, provider/tool reported as overlapping sum and union, and the leftover named unclassified_elapsed_ms rather than “llxprt time”.

Also withdrawn in Rev.3: the “~49 us per turn” budget (primitive costs only, not end-to-end), the “frames” counter (a stdout write is not a frame — Ink exposes onRender), the “load-invariant counters” claim, pid-as-ownership, startup-only maintenance, and the “negative mtime age” finding, which was a test artifact.

01The problem, precisely

SessionMetricsAggregator already tracks provider and tool timing well. But packages/cli/src/ui/utils/computeStats.ts:70 says this: 

// Percentages are relative to accumulated work (API + Tool), which is
// the denominator that makes the parts sum to 100%.
apiTimePercent  = totalApiTime  / accumulatedWork
toolTimePercent = totalToolTime / accumulatedWork

The denominator is accumulatedWork = API + Tool, so API% + Tool% = 100% by construction. llxprt’s own time is not merely unmeasured — it is structurally excluded from the arithmetic. That is why the UI can feel like it regressed while every number on /stats looks perfectly healthy.

02The time-accounting model

Change the denominator from API + Tool to wall − humanIdle, and the remainder is llxprt. Every bucket below either exists today, is one of the two new measurements, or is arithmetic on the other two.

Why the waterfall above is invalid.

It presumes provider time and llxprt time are disjoint. They are not. ApiAttemptRecord.durationMs is the whole request wall duration including TTFT (sessionMetricsAggregator.ts:38-43) and the entire interval goes into the active union (:404-410). While that request streams, we are decoding deltas and Ink is painting — inside the provider interval. So an ordinary sequential turn can look like: 

busy        = 10,000 ms
API union   = 10,000 ms      (the whole turn was one streaming request)
Ink render  =    200 ms      (which happened DURING that request)

llxprtMs = busy - active = 0
coreMs   = llxprtMs - uiMs = -200      <-- negative, on a completely normal turn

Second defect: accumulatedApiTimeMs and accumulatedToolTimeMs are sums (:93-100, :435-436, :594-596) while the residual subtracts a union (agentActiveTimeMs). Parallel tools, a subagent request nested inside a tool, and failover attempts all make the sums exceed elapsed active time, so provider + tool + residual was never a partition of anything.

Third defect: SessionMetricsAggregator holds one session-global interval union and no per-turn or per-runtime identity (:274-301, :23-50), and uiTelemetry.ts:358-390 discards prompt_id on the way in. Per-operation attribution cannot be recovered by differencing session snapshots while intervals cross the boundary.

Replacement: measure client phases directly (client_prepare_ms, stream_handler_ms, ink_render_ms from Ink’s onRender, stdout_write_sync_ms, client_finalize_ms); report provider_attempt_sum_ms and provider_union_ms, tool_call_sum_ms and tool_union_ms as explicitly overlapping metrics; and name the leftover unclassified_elapsed_ms. Do not promise they sum. Full specification in PLAN.md.

03Where the measurements attach

Both new measurements land on seams that already exist. Neither requires touching the @jrichman/ink fork, and nothing is added to the per-delta path.

Both seam claims were corrected in review. See the two panels below.

A stdout write is not a frame, and this seam cannot time rendering. Ink computes layout and serialises output before writing, and already exposes that work through RenderOptions.onRender. Writes then happen on several branches — static output can clear, write and render separately, and normal output can be throttled or suppressed when unchanged. One write may be zero, one, or part of a render. Timing around the call also measures only the synchronous invocation, not callback, drain, or terminal flush.

Corrected split: ink_render_ms and render count come from onRender; the Proxy contributes stdout_bytes (encoded via Buffer.byteLength / Uint8Array.byteLength, not string length), stdout_write_calls, and stdout_write_sync_ms. If React reconciliation is needed, that is a separate Profiler concern.

Scope, too: createInkStdio() is not Ink-exclusive — Zed calls it at runZedIntegration.ts:105-112, and interactive title writes bypass it via writeToStdout. Instrument the instance passed by inkRenderOptions.ts, not the helper globally. Any wrapper must delegate to writeToStdout (not target.write) and preserve every overload, encoding, callback and the backpressure boolean.

useStreamingState is not a sound busy/idle boundary. It is derived React display state (useAgentStreamLifecycle.ts:35-76). It gives WaitingForConfirmation precedence whenever any tool awaits approval — even while another parallel tool, request, or subagent is still active, so subtracting that whole window as idle can make active time exceed busy time. Completed tools keep it in Responding until displayCleared. It starts after query preparation and ends before the recording flush (useSubmitQuery.ts:671-727), so it excludes real client work at both ends. And a queued-drain gap passes through Idle, which is our scheduling, not human think time.

Corrected: bound the operation on useSubmitQuery’s existing ownership acquire/release (~:620-640 / :650-659), measure approval waits at the confirmation seam, and mark queued operations explicitly.

04Counters over timers: how noise is handled

Counters are strong covariates. They are not load-invariant, and not a gate.

Rev.2 claimed stdout_bytes and write counts are “identical on a busy laptop and an idle one”. Review rejected that, correctly: React batching, Ink throttling and output coalescing all respond to load, and terminal width/height, screen-reader mode, resize, static output, and the alternate-buffer / incrementalRendering settings (inkRenderOptions.ts:34-48) all change them independently of our code quality.

They remain the most useful signal we have — far less machine-sensitive than milliseconds — but they must be recorded alongside terminal geometry and render mode, and compared only within matched dimensions. Similarly llxprtMs / turnBusyMs does not normalise machine speed: the denominator contains provider, network and human components that do not scale with local CPU.

Normalizing the timers we do keep

  • llxprtMs / turnBusyMs — a ratio; a slow machine inflates numerator and denominator together.
  • coreMs per 1k context_tokens — removes context growth, which otherwise looks like a regression.
  • uiMs per 1k output_tokens — removes response length.
  • p50 across many turns per version, never single samples. High load inflates the tail, not the median.
  • contended and concurrent_instances let us discard polluted samples rather than trying to filter noise statistically (§06).

05Memory: two slopes, not one number

Absolute RSS tells you nothing — contexts legitimately get large. The #3114 leak grew with uptime, not activity, and that distinction is the whole diagnostic.

Curves are schematic. external and arrayBuffers are first-class here — under Bun/JSC that is where the mass hid in #3112. Cost is one memoryUsage() call per turn at 0.42 µs. No GC hooks are involved (see §07).

Each process counts only its own bytes, so none of them knows the shared file is full; and simultaneous rename + unlink destroys data another process just rotated.

So the fix is not a better counter and not a lock. Give every process its own file and move the bound to the directory. Then no file ever has two writers, and the only shared operation is “delete the oldest” — which is idempotent, so losing that race is harmless.

This is rotateReports() applied to a directory instead of a file. packages/core/src/utils/errorReporting.ts already bounds on file count and total bytes simultaneously and unlinks oldest-first, best-effort. Count-only fails when records fatten; byte-only fails when files multiply. The per-file shape matches TokenUsageLogger — which the data shows is fine (50 MB across 1,281 files). The lesson of #3164 was never “per-file is bad”; it was “per-project-hash directories are unreachable and nothing sweeps.” One global directory with a sweep has neither problem.

Long-lived processes: the filename must be time-driven

“One file per process” alone is not enough — llxprt often runs 24/7, and a process that lives for weeks would write one unbounded file. The file a record lands in is therefore chosen by the UTC day of the record’s own timestamp, with a sequence suffix when the process’s own file gets large: 

perf-<YYYYMMDD>-<runUuid>-<nnn>.jsonl        (Rev.3: runUuid, not pid)
     |          |         └─ sub-roll when THIS file passes 8 MiB
     |          └─ per-run UUID, created with the exclusive 'wx' flag
     └─ UTC day taken from the record's ts, never from a timer

Corrected in Rev.3: a pid is not an ownership claim. Rev.2 used perf-<day>-<pid>-<nnn> and asserted a sole writer forever. Pids are reused across reboots, two containers sharing a mounted home can hold the same pid, and a second run on the same day would reopen -000 — at which point both the sole-writer invariant and the private byte counter are wrong. Discovering the next sequence with an existence check is also check-then-use. The shipped name uses a per-run UUID with exclusive creation (wx) and initialises its byte counter from stat. errorReporting.ts:367-373 already adds random bytes for the same reason.

Deriving the day from the record rather than a scheduled timer means a process that is idle or suspended across midnight still rolls correctly on its next write, with no wakeups and no clock callbacks. UTC avoids DST ambiguity. And the per-process byte counter that was wrong in rev.1 is correct here — the bug was never private counters, it was a private counter on a shared file. Re-running the same 8-process test against this scheme:

Compression: worth it, but it must not tax an interactive session

Measured on a heavy 24/7 day-file (3,000 turns, 2.29 MiB) — these records are almost all numbers, so they compress extremely well:

LevelResultRatioCPU
gzip -12.29 → 0.374 MiB6.1×7 ms
gzip -62.29 → 0.291 MiB7.9×24 ms
gzip -92.29 → 0.277 MiB8.3×37 ms
gunzip (read side)——2 ms
30 heavy days, uncompressed69 MiB
30 heavy days, gzip -69 MiB

So compression buys roughly 8× more history for the same disk, and the cost of a whole day-file is 24 ms — less than one render frame. The concern is therefore not the cost, it is the unboundedness: a janitor that might compress fifty files is not something an interactive session should discover. Four rules make it safe:

Who compresses? Any instance — but only because every step is made idempotent

There is no elected janitor and no lock. Any instance may compress at startup, and concurrent attempts are made harmless rather than prevented. That requires five rules, three of which came out of testing rather than reasoning.

  1. Private scratch path. x.jsonl.gz.<pid>.tmp, never a shared .tmp. With 8 concurrent compressors on a shared tmp path, 1–3 workers per run threw ENOENT on rename; the archive happened to survive only because gzip is byte-deterministic (verified) and every worker compressed identical input. That is luck, not safety — mixed llxprt versions or gzip levels would produce differing bytes into one file. A private tmp is correct by construction and costs nothing.
  2. Refuse to overwrite an existing archive. If x.jsonl.gz exists, skip. See the boundary hazard below — this is the rule that prevents catastrophic loss.
  3. Idle grace, not just a day check. Eligible only when the file’s UTC day is past and its mtime is older than ~1 h — and the file is not claimed by a live writer, because an idle mtime does not prove a 24/7 process is dead.
  4. Bounded work. At most 1–2 files per startup, oldest first. Worst case ~48 ms, once, before the UI is interactive; a backlog drains over several launches. Concurrent duplicate work costs at most N×24 ms of wasted CPU, never correctness.
  5. Startup only, never mid-session — so it can never land during streaming, which is the thing we are measuring. Crash safety comes from the atomic rename: a crash leaves either the intact original or a complete archive, never a truncated one.

The boundary hazard, and why rule 2 is not optional. A turn that begins at 23:59:50 and is recorded after midnight carries a timestamp belonging to yesterday, so it appends to a day-file that may already have been archived. Without the refuse-to-overwrite rule, the next pass compresses that one-record file to the same .gz name and destroys the whole day:

NAIVE
  after archive           : 2000 records readable (of 2000)
  after late append       : 2001 readable (of 2001)   files=2
  after 2nd compress pass :    1 readable (of 2001)
  >>> 2000 RECORDS DESTROYED — a full day wiped by one late record

GUARDED (idle grace + refuse-if-exists)
  pass 1 (file fresh)       -> SKIP: 0.0s since last write (< 1h grace)
  pass 2 (3h idle)          -> COMPRESSED
  late record appended      -> readable 2001 of 2001
  pass 3 (archive exists)   -> SKIP: refuse to overwrite
  pass 4 (stray 3h idle)    -> SKIP: refuse to overwrite
  FINAL: 2001 of 2001 readable, lost: 0

The stray one-record .jsonl is simply left beside the archive. Both are read by gzcat -f, so nothing is lost, and the sweep evicts both together by age.

Withdrawn: the “negative mtime age” finding. Rev.2 reported that Date.now() - mtimeMs going negative on APFS (−0.65 ms) made an age < grace check “silently skip forever”, and treated a Math.max(0, …) clamp as a required fix. That is wrong. For any positive grace the clamp does not change the verdict:

grace = 1h : raw (age < grace) = true , clamped = true   -> same verdict
grace = 0  : raw = true , clamped = false                -> differs, but grace=0 is not the design

The original test used grace = 0, a configuration this design never uses, so it was green for the wrong reason and the conclusion was over-generalised. The genuine hazard is a materially future mtime (an NTP step) delaying eligibility until mtime + grace — a benign delay. Retained as a test case, not a design constraint. Recorded here because a green test that never exercised the code under test is worse than a red one, and this one fooled me twice.

Eviction must not depend on compression. The sweep evicts oldest-first on age and bytes regardless of whether anything was ever compressed. Compression buys history depth; the sweep is what bounds the disk. Because of that independence, Rev.3 defers compression to last (PLAN.md Phase 7) — it is an optimisation, not a prerequisite, and it is the riskiest concurrency state machine in the design.

Three further Rev.3 corrections to this section.

1. Startup-only maintenance cannot bound a 24/7 process. The diagram above says startup sweep, and the requirement explicitly names processes that never restart. Maintenance must also run on file-roll boundaries and on a coarse interval.

2. A hard instantaneous ceiling, zero record loss, and no coordination cannot all hold. Rev.2 claimed all three. Concurrent appends overshoot between scan and delete, and many active files can collectively exceed the ceiling while each stays under its sub-roll threshold. The honest guarantee is an eventual bound with a documented maximum overshoot. Relatedly, on a read-only or full volume eviction itself cannot run, so the guarantee there is “no further growth”, not “the cap is enforced”.

3. The sweep must not delete a live writer’s file. An idle mtime does not prove a 24/7 process is dead, and unlinking a live writer’s file makes already-written records vanish while the next appendFile silently recreates the path. Live files need an explicit claim, and only closed generations may be swept. rotateReports() is a weaker precedent than Rev.2 implied: it scans a 20-file / 1 MiB cohort, protects only in-process paths, and decrements its accounting even when unlink fails (errorReporting.ts:354-408). Reuse the shape, not the guarantees.

Rejected alternative, for the record: gzip members are concatenable (verified — two members decode to "a b "), so we could append pre-compressed records. But compressing 800-byte records individually gives a poor ratio and puts a codec on the write path. Not worth it.

Why not a lock?

Two lock protocols already exist in-tree and both argue against it here. reconcileLock.ts takes an O_EXCL lock with deliberately no PID-liveness reclaim (“safety over availability”) — applied to rotation, one crash would stop rotation permanently. CredentialWriteLock does it properly with a fenced O_EXCL owner protocol, process probing and TIMEOUT — far too much machinery for a log file. And we have just filed #3164 about 417 stale locks. Adding another lock is the wrong direction. Per-process files need no lock at all.

A bonus we get for free. With 2+ instances running 98.9% of the time, the dominant source of “llxprt feels slow” may be llxprt competing with itself. Recording concurrent_instances (countable from live files in the perf dir) makes that measurable for the first time — and lets you filter it out of trend comparisons instead of guessing.

08Observer-effect budget

This budget is WITHDRAWN. It sums isolated primitive costs and calls the result an instrumentation budget. It omits recorder dispatch, argument evaluation on the disabled path, byte-length work, record allocation and JSON.stringify, promise and microtask cost, roll checks, queue growth, filesystem contention, GC, maintenance scans, and compression. It also prices one memory sample while the design asks for turn-boundary and interval sampling, and treats the drift probe as free when ~180 ticks per turn implies an added ~10 Hz timer — existing intervals are 1 s, 2 s and 60 s, so there is nothing to piggyback on. The table is kept only as the primitive-cost measurements it actually is. A real end-to-end figure, enabled and disabled, under streaming load, with p50/p95/p99 event-loop impact, is a Phase 0.5 deliverable in PLAN.md, and no overhead claim ships before it exists.

What actually causes observer effect (and how each is avoided)

  1. I/O on the hot path. One async append per turn, to this process’s own file. Nothing per delta.
  2. Allocation per sample. Fixed preallocated accumulators — count/sum/min/max plus a fixed integer bucket array. No per-sample objects, no per-sample attribute maps (an OTel allocation trap).
  3. Emitting events per sample. Perf samples never flow through uiTelemetryService; that would build a render-triggering feedback loop.
  4. A HUD that re-renders on every sample. /perf reads a mutable ref on a slow interval — the pattern Footer’s memory display already uses.
  5. Global async instrumentation. No new AsyncLocalStorage / async_hooks usage.
  6. Extra timers. Piggyback on intervals that already exist rather than adding wakeups.

Enable/disable: the mechanism stands, the justification does not. Installing a recorder object at init — real or no-op — is still the right shape, because it keeps if (perfEnabled) branches out of the hot path.

But “monomorphic call sites, the JIT inlines the no-op away” is a hypothesis, not a verified fact, and it was stated as fact. A no-op method does not prevent evaluation of its arguments — performance.now(), byte sizing, object construction all still run. React closures, proxies, and runtime setting changes can make a site polymorphic, and JSC and V8 behave differently. The disabled fast path must be designed so the expensive work is structurally absent, not merely passed to an empty function, and proven with an exact-path benchmark on both runtimes.

09Reading the trend

A shell one-liner is not a deliverable. It is macOS-oriented (gzcat), breaks on argument limits once the directory holds thousands of entries, aborts on a single malformed or truncated line, has no schema-version dispatch, and does not exist on Windows. Without a real consumer this feature accumulates JSONL nobody reads. PLAN.md Phase 5 makes a Bun/TypeScript report command a requirement, including telemetry self-health (records dropped, queue high-water mark, last write error, evictions) — without which a flat trend is indistinguishable from broken instrumentation. The example query and field table that stood here have been deleted, not marked. They referenced core_ms, ui_ms, llxprt_ms and turn_busy_ms — every one of them a field from the model rejected in §02. Keeping superseded prose in place is defensible; keeping a runnable-looking code block and a field list that looks like a schema is not, because that is exactly what an implementer copies. The record schema does not exist yet: it is a Phase 1 deliverable in PLAN.md, to be written once as a Zod schema from which both the writer and the reader derive their types.

This is the same failure mode as #3164, where a reader drifted from its writer’s format and consequently deleted nothing for months, with green tests, because the fixtures encoded the legacy shape. The round-trip test must therefore assert against a record produced by the real writer — never a hand-authored fixture.

The dimensions a trend must be grouped by, as distinct from the measurements themselves, are listed in PLAN.md: version and commit for the x-axis; provider, model, render mode and terminal geometry as matched comparison dimensions; and concurrent_instances for contamination. Two facts worth carrying forward from the version investigation in §10: llxprt_version comes from CLI_VERSION, baked at build time, and git_sha needs no build change at all because getGitCommitInfo() already exists.

10Correlating a slow turn to what was happening

A perf number nobody can trace back to a conversation is a curiosity, not a diagnostic. I checked what join keys actually exist by scanning 120 recordings / 173,129 events. The vocabulary is narrow: 

event types : content(170555)  compressed(1982)  session_event(387)
              session_start(120)  provider_switch(85)
every event : { v, seq, ts, type, payload }

session_start payload: sessionId, projectHash, workspaceDirs, provider, model, startTime
content payload      : { content: IContent }  -- carries IContent.metadata verbatim

#3130 changed this for the better. It landed as #3155 and mints turn_id / prompt_id before the request is sent, stamping them onto the content that gets persisted (packages/agents/src/core/turnIdentity.ts). Since recordContent() enqueues { content } whole, recordings now carry the turn id. Verified in live recordings on this machine: 

metadata keys seen: ['chronology', 'model', 'providerBaseURL', 'turnId', 'usage']

So the turn-level join is exact, not a timestamp approximation. An earlier draft of this design assumed otherwise and planned a ts-window join; that is no longer necessary.

Implementation gotcha. SESSION_FILE_ID_PREFIX_LENGTH = 12 (SessionRecordingService.ts:49,262), so the recording filename carries only the first 12 characters of the session UUID — e.g. session-2026-07-15T12-04-48-ca59252d-f60.jsonl for ca59252d-f604-4355-b2db-d4e22ee4fdbc. Join on the full sessionId in the session_start payload, never on the filename, which is both lossy and collision-prone.

Adopt #3130’s shipped key names verbatim

#3130 has landed, so these are no longer a proposal to align with — they are the schema on disk. From docs/token-usage-log.md, the identity block the perf record must reuse character for character: 

prompt_id          joins to metadata.promptId on recorded content
session_id         the session identifier
turn_id            minted pre-send, stamped on the persisted turn
runtime_id         the agent runtime that served the request
parent_runtime_id  null for the main agent
subagent_name      null for the main agent
record_type        turn | compression | provider_switch | model_switch | ...
schema_version

Inventing parallel names would produce three logs — perf, token-usage, session recording — that cannot be joined, which is precisely the reader-drift failure that produced #3164.

Do not join on user_turn or step. docs/token-usage-log.md documents that both name the newest turn already in history, not the turn being sent, and are null on a session’s first request. They are useful context, and wrong as join keys. Use turn_id / prompt_id.

The commit SHA is already there — use it, don’t rebuild it

There is a complete commit-stamp pipeline in the tree already, the one /about displays and that nightly versioning uses. Nothing new is required:

One freshness caveat. The artifact is only regenerated by generate, bundle and prepack — plain npm run build (bun scripts/build.ts) does not refresh it. Observed live in this checkout: git-commit.json said a4f6067ad while HEAD was d604b4db3, one commit and ~30 minutes apart. Released and nightly artifacts are correct (prepack / bundle run the generator), so cross-release trending is sound; a local dev build can report a stale sha. Worth recording llxprt_version alongside it, since nightly versions already embed the same short sha independently.
