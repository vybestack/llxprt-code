## 1. Goal

Delete the in-memory tool-call tracking pipeline that once fed "executing / recent tool
calls" underneath the active TODO. The write side of that pipeline no longer exists in
production; the read side is still constructed, mounted and subscribed to, and can never
receive data. Remove writer, reader, subscriber, React provider/context, the suppression
hook, the dead core-package context tracker, the unused CLI re-export module, and the
formatter option that exists only to serve them.

**Preserve, unchanged in observable behavior:** persisted `Todo.toolCalls` and
`subtask.toolCalls` rendering, `TodoToolCall` / `TodoToolCallSchema`, `groupToolCalls`,
`formatTodoListForDisplay`, `TodoPanel`, `ToolGroupMessage`, `transformTodoToolCall`,
`todo_read`, `todo_write`, the **tools-package** `TodoContextTracker`, the `ITodoService`
boundary, and interactive TODO continuation.

   threshold increase, no new `ignores:` entry. Enforced by
   `npm run lint:eslint-guard`.
6. **No defensive fallback layers.** Removing a code path means removing it. Do not add
   `if (x)` guards, optional-chaining hedges or `try/catch` around the removal. Fail fast:
   if something still needs the removed data, that is a finding to report, not a hole to

10. **No opportunistic refactoring.** Specifically: do **not** deduplicate the two

## 7. Fail-fast expectations during execution

When the provider is unmounted and the context deleted, anything that still genuinely
needed the removed data will surface as a **TypeScript error or a red behavioral test**.
That is the desired signal. Do not:

- add an optional-chained fallback (`toolCallContext?.getExecutingToolCalls?.()`),
- default a removed option back in,
- wrap a call site in `try/catch`,
- or reintroduce the context "just for tests".

If a genuine consumer appears that §4 did not predict, **stop, document it, and report it**
— the preflight assumption was wrong and the plan needs revision, not a workaround.

## 8. Test-first execution sequence

### 8.0 Why there is no artificial RED test

`dev-docs/RULES.md` forbids reverse testing and forbids tests that assert incorrect or
absent behavior. For a deletion of code that has **no observable behavior**, there is no
honest failing test to write first: any test asserting "the tracker no longer exists" is a
structural test, and any test asserting the current merged output would pass identically
before and after. Inventing one would be exactly the fraud pattern the rules target.

The test-first discipline is therefore satisfied as follows, in this order:

1. **Phase 1 writes the safety net first**, on the *pre-removal* tree, for preserved
   behavior that is currently untested (§4.9). These tests must pass before any deletion.
2. **Each Phase 1 test must satisfy the RULES.md litmus test.** For every new test the
   implementer must be able to answer yes to: *would this fail if the preserved production
   behavior were removed or stubbed?* Concretely, assert **exact rendered strings**
   (e.g. the literal `↳ read_file(path: 'src/app.ts')` line, the `2x` grouping suffix, the
