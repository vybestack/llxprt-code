# Issues #3909 and #3517: tokenizer init stickiness, local failure display, Bun PTY groups

Branch `issue3909-3517`, based on `85fdd73b`.

## Scope

Fixed, each with a mechanism that was verified in code or by a real probe:

1. **Sticky encoder initialization.** `packages/providers/src/tokenizers/o200kBaseCounter.ts` cached a
   rejected initialization promise forever, in both the process-wide shared encoder and in each
   `createO200kBaseEncoderResolver(loader)` resolver. One transient failure poisoned every later call.
2. **Raw Claude history counting.** `createClaudeRuntimeTokenizer().countTokens` let encoder
   initialization, encode and `JSON.stringify` failures escape as raw errors with no model, stage or cause.
3. **Local failures displayed as API errors.** A `ModelPromptEstimatorError` reached the CLI as
   `[API Error: ...]` on every route, and `buildStructuredError` dropped everything but the message.
4. **Bun foreground PTY cleanup.** `supportsProcessGroupKill` was hard-coded false for `bun-pty`, although
   `Bun.spawn` with an inline terminal makes the child a process-group leader (probed: pgid == pid
   immediately after spawn). Abort, inactivity timeout and `terminatePty` therefore signalled only the
   shell and left its children alive.

Explicitly not done (not approved, and not established by evidence):

- No input size ceiling, no new heuristic fallback, no change to `toolOutputLimiter`. The huge-allocation
  probe reproduced an allocator error. It does not show that the original user's input was oversized, and a
  successful encode after one trap does not show that every trap leaves the WASM instance healthy. This
  change does not claim to fix the original incident's root cause. It fixes the three mechanisms above.
- No claim about children that leave the PTY's group (`setsid` daemons).

## Design

### 1. Encoder cache (`o200kBaseCounter.ts`)

One helper, `createRetainOnSuccessResolver(loader)`, backs both caches. Concurrent callers share the single
in-flight attempt, so each sees the failure. The failed attempt clears the cache entry, and the next
independent call initializes again. A resolved encoder stays cached. There is no retry loop and no
heuristic counting. At most one attempt is pending, and only a failed attempt clears the entry, so a
failure cannot overwrite newer state. `getO200kBaseEncoder()` and `createO200kBaseEncoderResolver()` with the
default loader both return the same shared resolver, so the one-WASM-instance property is unchanged.
The shared cache cannot be fault-injected (its loader is the module's own dynamic import), so its failure
path is covered through the per-loader resolver, which is the same function.

### 2. Claude counting errors

`createClaudeRuntimeTokenizer` takes an optional encoder resolver, as `createGpt56RuntimeTokenizer` already
does, and `createRuntimeTokenizerFactory` passes its factory-scoped resolver. Failures become
`ModelPromptEstimatorError`: `asset-unavailable` for encoder initialization, `tokenization-failed` for
serialization and encoding, each with model, protocol, family and the original `cause`. Exact/calibrated
accounting is untouched, and nothing is swallowed or replaced by a fallback.
`ModelPromptEstimatorError` now appends `; cause: <detail>` to its message itself when a cause is given.
The two `formatCausalDetail` call sites in `Gpt56O200kPromptEstimator.ts` were removed so the detail is
not formatted twice.

### 3. Local tokenization classification

- `LocalTokenizationError` (core `utils/errors.ts`, next to `UnauthorizedError`) is the marker.
  `ModelPromptEstimatorError` extends it.
- `STRUCTURED_ERROR_CATEGORIES` gains `local_tokenization`. The agents event schema, the JSON output
  schema and the provider observation guard all derive from that constant.
- `buildStructuredError` (agents, used by `Turn.handleRunError` for the stream error event) sets the
  category for a `LocalTokenizationError`. It now reads the category list from core instead of keeping a
  second copy.
- `parseAndFormatApiError` (core) formats a `LocalTokenizationError`, or a structured error with that
  category, as `[Local Tokenization Error: <message>]` followed by a line saying it is not a provider API
  response. This one function serves interactive stream events, the non-interactive path (which rebuilds
  an `Error` carrying `category`), `handleError`, `formatNonInteractiveError` and the a2a server.
- `handleSubmissionError` (CLI) used to pass only the message string, which always formatted as
  `[API Error: ...]`. It now passes a `LocalTokenizationError` through unchanged. Auth handling
  (`UnauthorizedError`, `AllBucketsExhaustedError`) is evaluated first and is unchanged. Provider
  failures keep `[API Error: ...]`.

### 4. Bun PTY process group

`initializePtyExecState` asks `ptyLeadsProcessGroup` once. node-pty stays true (forkpty always makes a
group leader). For `bun-pty` the answer is the existing signal-0 probe `isProcessGroupAlive(pid)`. A live
group whose id equals the freshly spawned pid can only have been created by that child, and a pid is not
reused while a group carries it. If the child already exited and left no group, the probe is false and the
existing direct-kill path runs, which is correct because there is nothing to signal. With the flag set,
abort, inactivity and `terminatePty` use the existing TERM, KILL and reap code unchanged. `-pid` is only
ever the spawned child's own pid; `isGroupTargetPid` still rejects 0 and 1.

### 5. Explicit terminate and shutdown disposal (same owned group)

Assessment of the existing lifecycle: abort and inactivity already ran a group TERM, KILL, reap chain that is
independent of the registry (`armPtyGroupAbortKill`). Two normal paths were not:

- `terminatePty` hung its KILL escalation on a timer stored on the registry entry. When the leader exits on
  SIGTERM, teardown removes the entry and clears that timer, so a member that ignores SIGTERM survived.
- `destroyAllPtys` only destroyed the PTY and direct-killed the leader. Under bun-pty the child is not
  hangup-signalled through the session, so ordinary descendants survived CLI exit.

Fix: `terminateOwnedProcessGroup(pid)` in `shellProcessKill.ts` sends SIGTERM to `-pid` synchronously, waits up to
`SIGKILL_TIMEOUT_MS` (ending early when the group is empty, via `reapProcessGroup`), sends SIGKILL only if the
group is still alive, then reaps for the bounded window. It does not read the registry, so the leader exiting
cannot cancel it. Chains are shared per group id while in flight, so `terminatePty` followed by shutdown does not
run two sequences. Non-group-target pids (0, 1) resolve true without signalling. `terminatePty` uses it for POSIX
PTYs that own a group; Windows and group-less PTYs keep the previous entry-timer path. `destroyAllPtys` is now
`async`: it still releases registry entries and resources synchronously, then awaits each group's termination.
`runExitCleanup` awaits it, so exit waits at most the grace plus reap window (about 1.7 s) and only when a group
is still alive after SIGTERM. Only groups of spawned PTYs are signalled, never borrowed groups. setsid escapes are
out of scope.

### 6. Final-review remediation (two findings)

**P1: disposal must wait for terminations that the registry no longer lists.** `destroyAllPtys` used to await only
the chains it started from `activePtys`. After `terminatePty` the leader exits, teardown empties the registry, and
the SIGKILL stage of the (fire-and-forget) chain was still pending, so `await handle.result; await destroyAllPtys()`
returned while a TERM-ignoring child lived, and a second concurrent `destroyAllPtys()` returned at once because the
first had already emptied the map. Fix: `shellProcessKill.ts` exports `awaitOwnedGroupTerminations()`, which waits on
the in-flight chains it already keeps per group id (`ownedGroupTerminations`, the dedupe map; entries are removed in
the chain's `finally`) and loops until the map is empty. `destroyAllPtys` starts a chain for each registered group,
releases the entries, then awaits that. No new state: the existing per-group map is the single owner of "termination
in flight". Every call to `destroyAllPtys`, whether first, concurrent or later, therefore waits for explicit
`terminatePty` chains and earlier disposals.

Abort and inactivity chains (`armPtyGroupAbortKill`) are not added to that map. Their result is gated on the chain,
and the registry entry is removed only when that result resolves, so a registered PTY with such a chain in flight is
still enumerated by `destroyAllPtys`, which starts its own owned chain for the same group and waits for the group to
be empty. There is no path where the abort chain is the only thing keeping a group alive while its entry is gone.

**P2: `runExitCleanup` returned immediately for a second caller.** The in-progress boolean made an overlapping
SIGINT/SIGTERM handler's `runExitCleanup().finally(() => process.exit(...))` run its exit callback while the first
caller was still awaiting PTY group teardown. Fix: `cleanup-state.ts` holds the one run's completion promise
(`getCleanupCompletion` / `beginCleanup(completion)`) instead of a boolean. `runExitCleanup` returns that same
promise to every caller and starts the side effects once (`Promise.resolve().then(performExitCleanup)`, recorded
synchronously, so a re-entrant call from inside cleanup also joins it). `__resetCleanupStateForTesting` clears it, so
the reset behavior is unchanged. A completed run still short-circuits later callers exactly as before.

## Known limits

- `Turn` still names its error report `Error when talking to <provider> API` for a local failure, and
  `StreamProcessor` still records it through `logApiError` telemetry. Only the user-facing display was
  reclassified.
- Abort and inactivity still use their own TERM, sleep, KILL, reap chain (`armPtyGroupAbortKill`), which gates the
  tool result. Explicit terminate and shutdown use `terminateOwnedProcessGroup`. Both are group-liveness gated and
  signal only the PTY's own group; they were not merged because the abort chain's timing and result gating are
  asserted by existing tests.
- A group that empties and whose id is reused by an unrelated new group inside the 200 ms grace window would be
  probed as alive. The abort chain has the same exposure. Not addressed.
- The shared-encoder failure path is exercised only through the per-loader resolver (see above).
