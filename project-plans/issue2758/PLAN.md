# Issue #2758 — Explicit runtime plugin manifests and alias-aware provider contributions

Plan ID: `PLAN-20260825-ISSUE2758`

## 1. What the issue asks for

Define a **minimal, explicit** runtime-plugin seam so a trusted, user-configured
npm package can contribute provider factories (and optionally alias configs)
into the CLI's provider composition — **without** creating a global plugin
framework, registry, service locator, scanning, or hot reload.

Non-goals (explicitly out of scope, do not implement):
MCP auth, Google movement, package topology, global registries / service
locators / scanning, hot reload, extension unification.

## 2. Current state (research findings)

- `packages/providers/src/composition/providerAliases.ts` reads `*.config` /
  `*.json` alias files from the user dir (`<globalDataDir>/providers`) and the
  built-in dir, producing `ProviderAliasEntry[]`.
- `packages/providers/src/composition/aliasProviderFactory.ts::registerAliasProviders`
  dispatches on `entry.config.baseProvider` through a hard-coded `switch`
  (`openai`, `openai-responses`, `openaivercel`/`openai-vercel`, `gemini`,
  `anthropic`) and **warns-and-skips** on an unknown base provider.
- `providerManagerInstance.ts::createProviderManager(context, options)` is the
  single composition seam. It calls `loadProviderAliasEntries()` then
  `registerAllProviders(...)` → `registerAliasProviders(...)`. It caches an
  `OpenAIRegistrationContext` per manager in a `WeakMap` so
  `refreshAliasProviders()` can re-run registration later.
- `createProviderManager` is **synchronous**; therefore dynamic `import()` of
  plugin packages must happen *before* it, in the CLI, and be passed in.
- CLI composition chain:
  `cli.tsx` → `cliSessionBootstrap.bootstrapRuntimeAndConfig(settings: LoadedSettings, …)`
  → `loadCliConfig(settings.merged, …, runtimeOverrides)`
  → `bootstrapAndLoadProfile` → `profileBootstrap.prepareRuntimeForProfile` (async)
  → `assembleCliProviderRuntime` → `createProviderManager`.
  The post-Config re-assembly happens in `postConfigRuntime.setupRuntimeContext`,
  which also calls `assembleCliProviderRuntime` and already receives
  `runtimeOverrides`.
- `LoadedSettings` (`packages/cli/src/config/settings.ts`) exposes the raw
  per-scope layers (`system`, `systemDefaults`, `user`, `workspace`) — the only
  place provenance can be observed. `mergeSettings` drops workspace settings
  when the folder is untrusted, so the **merged** view cannot be used for
  provenance decisions.
- `zod` is already a dependency of `packages/providers` and `packages/cli`.
- Settings schema lives in `packages/cli/src/config/settings-schema/*`;
  `schemas/settings.schema.json` is generated by `npm run schema:settings` and
  `docs/cli/configuration.md` by `npm run docs:settings`.
- Lint guardrails: `max-lines` 800, `max-lines-per-function` 80,
  `complexity` 25, `sonarjs/cognitive-complexity` 30. No `max-params` rule.

## 3. Accepted behavior (acceptance criteria)

### AC1 — `runtimePlugins` setting exists and is startup-only

- New top-level setting `runtimePlugins`, `type: 'array'`, `default: []`,
  `requiresRestart: true`, `showInDialog: false`.
- It is read exactly once, during CLI startup, before the provider manager is
  constructed. Nothing re-reads it later; there is no reload path.

### AC2 — Trusted provenance: user/global and system only

- Values are accepted from the **user (global)**, **system**, and
  **systemDefaults** settings layers.
- If `runtimePlugins` is present in the **workspace/project** settings file,
  startup **fails** with an actionable error that names the setting, the
  rejecting scope, and the workspace settings file path. It is never silently
  ignored and never merged.
- Deterministic order when several trusted layers define it:
  `systemDefaults` entries, then `system` entries, then `user` entries, each in
  its own array order.
- A non-array value, or an array containing a non-string, is an explicit error
  naming the offending layer and value.

### AC3 — Specifier validation: bare package roots only

Each entry, after trimming, must be a bare npm package root. Every rejection is
an error (never a skip) whose message names the offending value and the reason.

Accepted: `my-plugin`, `@scope/my-plugin`.

Rejected, each as its own named category:

| Category            | Examples                                              |
| ------------------- | ----------------------------------------------------- |
| empty               | `""`, `"   "`                                          |
| Node built-in       | `fs`, `path`, `node:fs`                                |
| URL                 | `file:///x`, `http://x`, `https://x`, `data:…`         |
| path                | `./p`, `../p`, `/abs/p`, `~/p`, `C:\p`, `a\b`          |
| subpath             | `pkg/sub`, `@scope/pkg/sub`, `@scope/pkg/a/b`          |
| malformed pkg name  | `.hidden`, `_leading`, `@scope`, `@/x`, `Upper`        |

### AC4 — Manifest v1 is Zod-validated and immutable

Plugin modules must export a named binding `llxprtRuntimePlugin`. There is no
default-export guessing and no alternative export names.

```ts
interface RuntimePluginManifest {
  readonly apiVersion: 1;
  readonly id: string;               // non-empty
  readonly providers: readonly RuntimeProviderContribution[]; // >= 1
}

interface RuntimeProviderContribution {
  readonly providerId: string;       // non-empty; the provider/base ID
  readonly createProvider: ProviderAliasFactory;
  readonly builtinAliases?: readonly ProviderAliasConfig[];
}

type ProviderAliasFactory = (
  entry: ProviderAliasEntry,
  context: ProviderFactoryContext,
) => IProvider | null;
```

`ProviderFactoryContext` carries exactly what the current built-in factories
need: `openaiApiKey`, `openaiBaseUrl`, `openaiProviderConfig`, `oauthManager`,
`config`, `authOnlyEnabled`.

- Validation is Zod-based; a validated manifest is **deep-frozen**
  (`Object.isFrozen` true for the manifest, its `providers` array, each
  contribution, and each `builtinAliases` array).
- `apiVersion !== 1` → explicit *incompatible plugin* error naming the observed
  version and the supported version.
- Any other schema violation → explicit *malformed manifest* error naming the
  specifier and the Zod issue paths.

### AC5 — Loading is explicit, ordered, once, into a local immutable map

`loadRuntimePlugins(specifiers, deps)` (async, providers package):

- Imports each specifier **once**, in the configured order.
- Produces a **local** `ProviderContributionRegistry` — a plain immutable object
  with a frozen internal `Map`. It is returned to the caller; nothing is stored
  in module state, no global registry, no ambient lookup.
- Error categories, each an explicit throw with an actionable message that names
  the specifier:
  1. import failed (missing module, or module threw) — original error preserved
     as `cause`;
  2. missing `llxprtRuntimePlugin` export;
  3. malformed manifest (AC4);
  4. incompatible `apiVersion` (AC4);
  5. duplicate plugin `id` across specifiers;
  6. duplicate `providerId` within a plugin or across plugins (message names
     both contributing plugin ids);
  7. contributed `providerId` collides with a built-in provider id;
  8. duplicate contributed alias name (across plugins, or colliding with another
     plugin's alias).
- `deps.importModule` is injectable so tests exercise the real loader logic
  against a stubbed module-resolution boundary (infrastructure mocking only —
  the loader itself is always real).

### AC6 — Built-ins use the same factory path; aliases resolve through the map

- `createBuiltinProviderContributions()` returns contributions for
  `openai`, `openai-responses`, `openaivercel`, `openai-vercel`, `gemini`,
  `anthropic`, each delegating to the existing
  `create*AliasProvider` function. No behavior change for built-in aliases.
- `registerAliasProviders` resolves `entry.config.baseProvider.toLowerCase()`
  through the registry instead of a `switch`.
- **Alias requesting an unloaded factory** (a base provider that is neither
  built-in nor contributed by a loaded plugin) → explicit throw naming the
  alias, the requested base provider, and the known provider ids. This replaces
  today's `debugLogger.warn(… skipping)`.
- Contributed `builtinAliases` are merged with file-loaded alias entries
  deterministically: file entries first (user dir, then built-in dir, as today),
  then plugin-contributed aliases in plugin-configured order. A contributed
  alias whose name collides with another contributed alias is an error (AC5.8);
  a contributed alias whose name collides with a **file** alias loses to the
  file alias (the user's own config file is the higher-authority layer) and this
  precedence is asserted by test and documented.
- `anthropic`'s existing identity rule (`entry.alias === 'claudecode'` gets the
  OAuth manager) is preserved inside the built-in anthropic contribution.

### AC7 — Wiring, once, before alias construction

- `ProviderManagerFactoryOptions` gains `providerContributions?: ProviderContributionRegistry`.
- `createProviderManager` threads it to `registerAliasProviders` and stores it in
  the per-manager `OpenAIRegistrationContext` so `refreshAliasProviders()` reuses
  the same registry (no reload, no re-import).
- `assembleCliProviderRuntime` input gains `providerContributions?` and forwards
  it.
- `loadCliConfig`'s `runtimeOverrides` gains `providerContributions?`, forwarded
  to both `prepareRuntimeForProfile` and `postConfigRuntime.setupRuntimeContext`
  re-assembly, so the post-Config recomposition does not lose plugin providers.
- `cliSessionBootstrap.bootstrapRuntimeAndConfig` performs the single startup
  load (it is the only place holding `LoadedSettings` before Config exists) and
  passes the registry down.
- Layer access goes through the public `LoadedSettings.forScope(scope)`
  accessor rather than the raw `.user` / `.workspace` properties. `forScope`
  already covers exactly the four scopes this needs, is the intended public
  surface, and keeps existing `LoadedSettings` test doubles working (they all
  implement `forScope`) without forcing unrelated test files to change.
- Callers that do not supply a registry (headless factory, agents API, sandbox
  partial config, `skills list`) get a built-ins-only registry — identical to
  today's behavior.

### AC8 — Documentation

- New `docs/runtime-plugins.md`: states plainly that runtime plugins are
  **trusted, unsandboxed executable code** that runs with the full privileges of
  the CLI process, that they may only be configured in user/global or system
  settings, that project settings cannot introduce them, and that the CLI fails
  fast rather than skipping a broken plugin. Documents manifest v1, the export
  name, the factory contract, alias precedence, and each failure category.
- Link it from `docs/cli/providers.md` and `docs/index.md`.
- Regenerate `schemas/settings.schema.json` (`npm run schema:settings`) and
  `docs/cli/configuration.md` (`npm run docs:settings`).

## 4. Explicitly NOT in scope (decisions recorded)

- The pre-existing warn-and-skip when an OpenAI-family alias has **no base URL**
  (`createOpenAIAliasProvider` etc. returning `null`) is left as-is. Turning it
  into a hard startup failure is a user-visible behavior change unrelated to the
  plugin seam and is not authorized by this issue.
- No plugin discovery/scanning, no lifecycle hooks, no plugin-contributed tools,
  commands, or agents. Providers only.
- No changes to `ProviderManager` itself — registration reuses
  `ProviderManager.registerProvider` unchanged.
- No sandboxing/permission model for plugins (documented as trusted instead).

## 6c. Review triage

Findings from independent review, with disposition.

Fixed:

- **Blocker — CLI wiring had no behavioral coverage.** The
  `providerContributions` threading could be deleted with every test still
  green. Added `packages/cli/src/config/runtimePlugins.wiring.test.ts`, which
  drives the real resolver, loader, registry, and `assembleCliProviderRuntime`
  and asserts a plugin-contributed alias reaches the assembled
  `ProviderManager`. Verified by mutation: removing the forwarding in
  `assembleCliProviderRuntime` fails the test.
- **Manifest freeze was shallow.** Nested alias-config data (`staticModels`,
  `providerConfig`, and so on) stayed mutable, so a plugin could rewrite its own
  validated manifest between refreshes. `manifest.ts` now freezes recursively;
  covered by a nested-mutation test.
- **Registry leaked mutable origin objects.** `getProviderOrigin` returned the
  internal record by reference. Origins are frozen now, with a test asserting a
  hijack attempt throws and the reported origin is unchanged.
- **Alias registration was not atomic.** One unresolvable alias could throw
  after earlier aliases had already been swapped on a live manager during
  `refreshAliasProviders`. All factories are resolved and all providers built
  before any `registerProvider` call.
- **Collisions were detected only after every plugin had executed.** The loader
  now rebuilds the registry after each manifest, so a duplicate id or alias
  fails before the next configured package is imported. Importing runs plugin
  code, so this is a real fail-fast improvement.
- Smaller items: npm's 214-character package-name limit is enforced; the schema
  entry declares `items: { type: 'string' }`; the unknown-base-provider error
  names the alias file; docs no longer claim a factory runs only once per alias;
  a stale "exactly as before" comment now states the warn-to-throw change.

Deferred (recorded, not done):

- Full Zod validation of every known `ProviderAliasConfig` field inside
  `builtinAliases`. The manifest validates the contribution shape and the
  required `baseProvider`; validating the whole alias-config surface would
  duplicate the sanitizers in `providerAliases.ts` and expand this issue's
  public API beyond the manifest itself.

Rejected:

- Changing `builtinAliases` to the plan's original `readonly
  ProviderAliasConfig[]`. A file alias derives its name from its filename; a
  contributed alias has no file, so it needs an explicit name. The
  `{ alias, config }` wrapper is the correct shape and this plan is amended to
  record it as the intended public contract.
- Removing the parity tests that exercise `createOpenAIAliasProvider` directly.
  They are deliberate regression coverage proving built-in alias behavior did
  not change; other tests cover the new path.

## 6d. Open code review triage

Fixed:

- Same package listed in two trusted layers previously failed with a confusing
  "Duplicate runtime plugin id 'x' is declared by both 'x' and 'x'".
  `resolveRuntimePluginSpecifiers` now deduplicates on first occurrence, so the
  loader's duplicate-id failure is reserved for genuinely different packages
  claiming the same id.
- Documented on `loadRuntimePlugins` that specifier trust is the caller's
  responsibility: the providers package resolves whatever `importModule`
  resolves, and the CLI owns the bare-package-root and provenance policy.
- Two import-failure tests exercised the same rejected-promise path. One now
  covers a resolver that throws synchronously.
- Added a test pinning that a plugin cannot shadow a built-in alias file: built-in
  aliases arrive as file entries, so the file-wins rule protects them.

Rejected:

- Rejecting `runtimePlugins` in `SettingScope.Session`. `LoadedSettings` has
  exactly four layers and `forScope(Session)` throws
  (`packages/cli/src/config/settings.ts:181-193`), so no Session layer can carry
  the setting. The suggested guard would crash startup.
- Duplicating specifier validation inside `loadRuntimePlugins`. That is
  explicitly defense in depth, which this repo's architecture preference rules
  out; specifier policy belongs to the CLI settings layer that owns it, and the
  providers API takes an injected resolver. Documented instead.
- Deriving the expected built-in provider id list in tests from
  `createBuiltinProviderContributions()`. That would assert the implementation
  against itself and could never fail; the hand-written literal is the point.
